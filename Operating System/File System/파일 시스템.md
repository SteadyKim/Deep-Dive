# 파일 시스템

## 개요

프로그램과 사용자는 데이터를 영구적으로 저장하고 이름으로 다시 찾아야 합니다.  
메모리는 전원이 꺼지면 사라지기 때문에, 운영체제는 디스크 같은 영구 저장 장치 위에 데이터를 구조화해 관리하는 계층이 필요합니다.

이 계층이 `파일 시스템(File System)`입니다.  
파일 시스템은 **데이터를 파일이라는 단위로 추상화하고, 그 파일들을 디렉터리 구조로 조직화하며, 디스크 블록에 매핑하는 방법 전체**를 말합니다.

어떻게 데이터를 디스크에 배치할지, 어떻게 빈 공간을 관리할지, 어떻게 갑작스러운 장애에서 데이터를 보호할지가 파일 시스템 설계의 핵심 문제입니다.

## 파일 시스템이란 무엇인가

파일 시스템은 운영체제가 저장 장치 위에 올려놓은 소프트웨어 계층으로, 크게 두 가지 역할을 합니다.

첫째, 사용자와 프로그램에게 **이름 기반의 파일 추상화**를 제공합니다.  
덕분에 프로그램은 물리적으로 어느 디스크 플래터, 어느 섹터에 데이터가 있는지 신경 쓰지 않아도 됩니다.

둘째, 디스크의 **블록 주소 공간을 파일과 디렉터리에 효율적으로 매핑**합니다.  
디스크는 고정 크기 블록(보통 4KB)의 배열이며, 파일 시스템은 어떤 블록이 어느 파일에 속하는지 추적합니다.

## 1. 파일과 메타데이터

### 파일이란 무엇인가

`파일(File)`은 운영체제가 제공하는 논리적인 저장 단위입니다.  
파일 자체는 바이트 스트림이지만, 운영체제는 각 파일에 대한 **메타데이터**를 별도로 관리합니다.

파일 메타데이터에는 보통 다음 정보가 포함됩니다.

- 파일 이름
- 크기
- 소유자와 권한
- 생성 시간, 최근 수정 시간, 최근 접근 시간
- 데이터 블록 위치

### inode

Unix 계열 파일 시스템에서는 파일 메타데이터를 `inode(Index Node)`라는 고정 크기 자료구조에 저장합니다.

```
inode
├── 파일 크기
├── 권한, 소유자
├── 타임스탬프
└── 데이터 블록 포인터들
     ├── 직접 블록 포인터 (Direct Block Pointer)
     ├── 단일 간접 포인터 (Single Indirect)
     ├── 이중 간접 포인터 (Double Indirect)
     └── 삼중 간접 포인터 (Triple Indirect)
```

파일 이름은 inode에 저장되지 않습니다.  
이름은 디렉터리 항목에서 inode 번호로 연결되며, 하나의 inode에 여러 이름이 붙을 수 있는 것이 `하드 링크(Hard Link)`의 원리입니다.

## 2. 디렉터리 구조

`디렉터리(Directory)`는 파일 이름과 inode 번호의 매핑 목록입니다.  
운영체제는 이 구조를 통해 사람이 읽을 수 있는 이름으로 파일을 찾아갑니다.

### 경로 해석 과정

`/home/user/file.txt`를 열 때 운영체제가 하는 일은 다음과 같습니다.

1. 루트 디렉터리의 inode를 읽습니다.
2. 루트 디렉터리에서 `home` 항목을 찾아 그 inode로 이동합니다.
3. `home` 디렉터리에서 `user` 항목을 찾아 그 inode로 이동합니다.
4. `user` 디렉터리에서 `file.txt`를 찾아 그 inode로 이동합니다.
5. 해당 inode의 데이터 블록 포인터로 실제 내용을 읽습니다.

즉, 하나의 파일을 열 때도 여러 번의 디스크 I/O가 발생할 수 있습니다.  
이를 줄이기 위해 운영체제는 `디렉터리 캐시(dcache)`와 `inode 캐시`를 메모리에 유지합니다.

### 심볼릭 링크

`심볼릭 링크(Symbolic Link)`는 다른 파일의 경로를 내용으로 가지는 특수 파일입니다.  
하드 링크와 달리 원본 파일이 삭제되면 심볼릭 링크는 끊긴 상태가 됩니다.

| 구분 | 하드 링크 | 심볼릭 링크 |
| --- | --- | --- |
| 가리키는 것 | 동일한 inode | 다른 파일의 경로 |
| 원본 삭제 시 | 데이터 유지 | 링크가 깨짐 |
| 디렉터리 링크 | 불가 (대부분) | 가능 |
| 파일 시스템 경계 | 불가 | 가능 |

## 3. 파일 할당 방식

파일을 어떻게 디스크 블록에 배치하느냐에 따라 파일 시스템 성능과 관리 방식이 크게 달라집니다.

### 연속 할당 (Contiguous Allocation)

파일 데이터를 **디스크의 연속된 블록**에 저장하는 방식입니다.

- 장점: 순차 읽기가 빠르고, 블록 위치 계산이 단순합니다.
- 단점: 파일 크기가 늘어날 때 공간을 확장하기 어렵고, 삭제를 반복하면 블록 사이에 사용할 수 없는 빈 공간이 흩어지는 `외부 단편화(External Fragmentation)`가 발생합니다.

CD-ROM 같은 읽기 전용 매체에 적합한 방식이며, 일반적인 범용 파일 시스템에서는 잘 쓰이지 않습니다.

### 연결 할당 (Linked Allocation)

각 블록이 **다음 블록의 주소를 포인터로 가지는** 연결 리스트 구조입니다.

- 장점: 파일 확장이 자유롭고, 외부 단편화가 없습니다.
- 단점: 임의 접근(Random Access)이 느립니다. n번째 블록에 접근하려면 앞의 n-1개 블록을 순서대로 따라가야 합니다. 또한 포인터 하나가 손상되면 이후 데이터가 모두 유실됩니다.

`FAT(File Allocation Table)` 파일 시스템은 이 방식의 변형입니다.  
포인터를 블록 내부가 아닌 별도의 FAT 테이블에 모아서 관리해 임의 접근 성능을 개선했습니다.

### 인덱스 할당 (Indexed Allocation)

파일마다 **인덱스 블록**을 두고, 그 안에 실제 데이터 블록의 주소 목록을 저장하는 방식입니다.

- 장점: 임의 접근이 빠르고, 외부 단편화가 없습니다.
- 단점: 작은 파일에도 인덱스 블록이 필요해 공간 낭비가 생길 수 있습니다.

Unix의 inode 구조가 이 방식을 따릅니다.  
직접 포인터로는 작은 파일을 빠르게, 간접 포인터 체인으로는 큰 파일도 주소 지정이 가능합니다.

| 할당 방식 | 순차 접근 | 임의 접근 | 외부 단편화 | 파일 확장 |
| --- | --- | --- | --- | --- |
| 연속 할당 | 빠름 | 빠름 | 있음 | 어려움 |
| 연결 할당 | 보통 | 느림 | 없음 | 쉬움 |
| 인덱스 할당 | 보통 | 빠름 | 없음 | 쉬움 |

## 4. 여유 공간 관리

파일이 삭제되면 그 블록은 다시 쓸 수 있어야 합니다.  
운영체제는 어느 블록이 비어 있는지 추적하기 위해 별도의 자료구조를 유지합니다.

### 비트맵 (Bitmap)

디스크의 각 블록에 대해 **1비트로 사용 여부**를 표시하는 방식입니다.

- `0`: 빈 블록
- `1`: 사용 중인 블록

구현이 단순하고 연속된 빈 블록을 찾기도 비교적 쉽습니다.  
그러나 비트맵 자체가 메모리에 올라와 있지 않으면 검색이 느려질 수 있습니다.

### 연결 리스트 방식 (Free List)

빈 블록들을 연결 리스트로 연결해 관리합니다.  
블록 할당이나 해제는 리스트 앞뒤를 조작하면 되어 빠르지만, 연속된 빈 블록을 찾는 것이 어렵습니다.

실제 파일 시스템에서는 비트맵 방식이 더 보편적으로 사용됩니다.

## 5. 저널링

### 왜 저널링이 필요한가

파일 시스템은 대부분의 작업이 여러 단계로 이루어집니다.  
예를 들어 파일을 생성하면 inode 할당, 디렉터리 갱신, 데이터 블록 기록이 순서대로 일어납니다.

이 중간에 갑자기 전원이 꺼지거나 시스템이 충돌하면 파일 시스템이 **불일치 상태**가 됩니다.  
inode는 할당됐는데 디렉터리가 갱신되지 않은 상태가 되는 식입니다.

`저널링(Journaling)`은 실제 파일 시스템에 변경을 적용하기 전에, **무엇을 할 것인지 먼저 별도의 로그 영역(Journal)에 기록**하는 기법입니다.

### 저널링의 복구 흐름

1. 변경 내용을 Journal에 기록합니다(Commit).
2. 실제 파일 시스템에 변경을 적용합니다.
3. 완료되면 Journal에서 해당 항목을 지웁니다.

재시작 시 Journal에 완료되지 않은 항목이 있으면 해당 작업을 다시 수행하거나 취소하여 일관성을 복구합니다.

### 저널링 모드

저널링을 어떤 범위에 적용하느냐에 따라 성능과 안전성이 다릅니다.

| 모드 | 설명 | 성능 | 안전성 |
| --- | --- | --- | --- |
| `Write-back` | 메타데이터만 저널링 | 빠름 | 낮음 |
| `Ordered` | 메타데이터 저널링, 데이터를 먼저 쓴 후 커밋 | 중간 | 중간 |
| `Data` | 데이터와 메타데이터 모두 저널링 | 느림 | 높음 |

ext4의 기본 모드는 `Ordered`로, 대부분의 상황에서 충분한 안전성과 성능을 제공합니다.

## 6. 대표적인 파일 시스템

### FAT (File Allocation Table)

`FAT32`는 MS-DOS에서 출발한 단순한 파일 시스템입니다.  
FAT 테이블에 파일의 블록 체인을 저장하고, 디렉터리 항목에 파일 크기와 시작 클러스터 번호를 저장합니다.

- 장점: 구현이 매우 단순하고 이식성이 높습니다.
- 단점: 파일 크기 4GB 제한, 파티션 크기 제한, 저널링 없음.
- 용도: USB 드라이브, SD 카드처럼 여러 OS 간에 호환성이 중요한 경우.

### NTFS (New Technology File System)

Windows의 기본 파일 시스템입니다.  
`MFT(Master File Table)`에 모든 파일의 메타데이터를 저장합니다.

- 장점: 파일 권한, 저널링, 심볼릭 링크, 파일 압축, 암호화(EFS) 지원.
- 단점: Linux/macOS와의 호환성이 제한적입니다.

### ext4

Linux의 대표 파일 시스템으로, ext2 → ext3 → ext4로 발전했습니다.

- 장점: 저널링, 지연 할당, `Extent` 기반 블록 할당으로 큰 파일 처리에 유리, 수 테라바이트 이상의 파티션 지원.
- 단점: 파일 삭제 후 실제 디스크 블록 정리에 TRIM 지원이 필요합니다.

### 기타

- `XFS`: 대용량 파일과 병렬 I/O에 강한 고성능 파일 시스템. RHEL 기본값.
- `Btrfs`: 스냅샷, RAID, 압축을 파일 시스템 수준에서 지원하는 차세대 Linux 파일 시스템.
- `APFS`: Apple이 SSD 최적화를 위해 설계한 파일 시스템. Copy-on-Write 기반.

## 정리

- `파일 시스템`은 디스크의 블록 배열 위에 파일과 디렉터리라는 추상화를 올려, 데이터를 이름으로 저장하고 찾을 수 있게 해주는 운영체제 계층입니다.
- `inode`는 파일 메타데이터와 데이터 블록 위치를 저장하는 자료구조이며, 파일 이름은 디렉터리 항목에서 inode 번호로 연결됩니다.
- 파일 할당 방식은 `연속 할당`, `연결 할당`, `인덱스 할당`으로 나뉘며, 현대 범용 파일 시스템은 인덱스 할당 방식을 기반으로 합니다.
- 여유 공간 관리는 보통 `비트맵`으로 처리하며, 삭제된 블록을 추적해 재사용합니다.
- `저널링`은 충돌 복구를 위해 변경 전에 먼저 로그를 기록하는 기법으로, 파일 시스템 일관성을 보장합니다.
- 대표적인 파일 시스템으로는 `FAT32`, `NTFS`, `ext4`가 있으며, 각각 이식성, Windows 기능성, Linux 성능에 강점을 가집니다.

결국 파일 시스템의 핵심은 **물리적인 블록 배열을 이름으로 접근할 수 있는 계층 구조로 추상화하고, 장애 상황에서도 데이터의 일관성을 유지하는 것**입니다.
