# DB 샤딩

## 개요

샤딩은 대규모 데이터를 여러 개의 독립적인 데이터베이스 서버에 나누어 저장하는 수평 확장 방식입니다.  
단일 데이터베이스 인스턴스의 CPU, 메모리, 디스크 I/O 한계를 넘어서기 위해 데이터를 여러 샤드로 분산하고, 각 샤드가 전체 데이터의 일부만 담당하도록 구성합니다.

샤딩의 핵심 2가지

1. 데이터를 어떤 기준으로 나눌지 결정하는 `샤드 키`
2. 요청이 어느 샤드로 가야 하는지 결정하는 `라우팅 방식`

즉, 샤딩은 단순히 데이터를 잘게 쪼개는 것이 아니라, 분산된 데이터베이스를 하나의 서비스처럼 운영하기 위한 아키텍처 전체를 의미합니다.

## 샤딩과 파티셔닝의 차이

파티셔닝과 샤딩은 모두 데이터를 나누는 기법이지만, 나누는 위치와 확장 목적이 다릅니다.

| 구분 | 파티셔닝 | 샤딩 |
| --- | --- | --- |
| 분할 범위 | 하나의 DB 인스턴스 내부 | 여러 독립 DB 인스턴스 |
| 확장 방향 | 주로 단일 서버 내부 최적화 | 수평 확장 |
| 저장 위치 | 같은 서버 또는 같은 인스턴스 | 서로 다른 서버 또는 클러스터 |
| 관리 단위 | 파티션 | 샤드 |
| 주요 목적 | 조회 범위 축소, 관리 편의성 | 처리량 확장, 저장 용량 확장 |
| 조인/트랜잭션 | 비교적 단순 | 샤드 간 처리 시 복잡 |

정리하면, 파티셔닝은 하나의 데이터베이스 안에서 데이터를 효율적으로 관리하는 기술이고, 샤딩은 데이터베이스 자체를 여러 대로 분산해 시스템 규모를 키우는 기술입니다.

## 샤딩 아키텍처의 기본 구성

일반적인 샤딩 아키텍처는 다음 흐름으로 동작합니다.

1. 애플리케이션이 데이터를 조회하거나 저장하려고 요청합니다.
2. 라우터 또는 애플리케이션 로직이 샤드 키를 기준으로 대상 샤드를 결정합니다.
3. 결정된 샤드에만 요청을 전달합니다.
4. 필요한 경우 여러 샤드의 결과를 애플리케이션에서 다시 합칩니다.

주요 구성 요소는 다음과 같습니다.

- `Shard Key`: 데이터 분산 기준이 되는 컬럼 또는 값
- `Router / Proxy`: 요청을 적절한 샤드로 전달하는 계층
- `Shard`: 실제 데이터를 저장하는 독립 데이터베이스 인스턴스
- `Metadata / Lookup`: 어떤 데이터가 어느 샤드에 있는지 관리하는 정보

샤딩을 도입하면 각 샤드는 독립적으로 확장하거나 유지보수할 수 있지만, 반대로 전체 시스템은 단일 DB보다 훨씬 복잡해집니다.

## 데이터 분산 방식

### 레인지 샤딩

샤드 키의 값 범위를 기준으로 샤드를 나누는 방식입니다.

예를 들어 다음처럼 나눌 수 있습니다.

- `user_id 1 ~ 1,000,000` -> 샤드 1
- `user_id 1,000,001 ~ 2,000,000` -> 샤드 2

장점은 분산 기준이 직관적이고 운영자가 이해하기 쉽다는 점입니다.  
반면 특정 범위에 요청이 몰리면 한 샤드만 과부하가 걸리는 핫스팟이 생기기 쉽습니다.

### 해시 샤딩

샤드 키에 해시 함수를 적용한 결과로 샤드를 결정하는 방식입니다.

예를 들어 `hash(user_id) % 4`와 같은 방식으로 샤드를 선택합니다.

장점은 데이터와 트래픽을 비교적 균등하게 분산하기 쉽다는 점입니다.  
단점은 샤드 수가 변경될 때 기존 해시 결과가 달라져 대규모 데이터 재배치가 필요하다는 점입니다.

### 디렉토리 샤딩

샤드 키와 실제 샤드의 매핑 정보를 별도 룩업 테이블이나 메타데이터 저장소에서 관리하는 방식입니다.

장점은 특정 고객이나 특정 데이터 집합을 원하는 샤드로 유연하게 이동시킬 수 있다는 점입니다.  
단점은 룩업 시스템이 병목 지점 또는 단일 장애 지점이 될 수 있다는 점입니다.

## 샤드 키 설계가 중요한 이유

샤딩에서 가장 중요한 설계 포인트는 샤드 키입니다.  
샤드 키를 잘못 고르면 샤드를 여러 개 두더라도 부하가 한 곳으로 몰려 확장 효과가 거의 사라집니다.

좋은 샤드 키는 보통 다음 조건을 만족해야 합니다.

- 데이터가 여러 샤드에 고르게 분산될 것
- 조회 패턴과 잘 맞아 자주 사용하는 요청이 단일 샤드에서 처리될 것
- 값이 자주 바뀌지 않아 데이터 이동이 최소화될 것
- 특정 시간대나 특정 고객군에만 부하가 쏠리지 않을 것

예를 들어 사용자 기반 서비스에서는 `user_id`가 자주 샤드 키 후보가 되지만, 시간 순으로 증가하는 값이라면 최근 데이터가 특정 샤드에 집중될 수 있으므로 보완이 필요합니다.

## 샤딩 도입 시의 기술적 난제

### 샤드 간 조인 어려움

서로 다른 샤드에 저장된 데이터를 데이터베이스 내부에서 자연스럽게 조인하기는 어렵습니다.  
이 때문에 다음과 같은 우회 방법이 필요합니다.

- 애플리케이션 레벨에서 여러 샤드의 결과를 수집 후 병합
- 자주 함께 조회하는 데이터를 중복 저장
- 조인이 많은 테이블은 같은 샤드에 배치되도록 설계

즉, 샤딩 환경에서는 정규화만으로는 해결되지 않고 조회 패턴 중심의 데이터 모델링이 더 중요해집니다.

### 리샤딩과 데이터 재배치

서비스가 성장하면 샤드를 추가해야 하는데, 기존 데이터를 새 샤드로 옮기는 리샤딩(Resharding)은 매우 까다롭습니다.

리샤딩이 어려운 이유는 다음과 같습니다.

- 대량 데이터 이동 자체의 비용이 큼
- 이동 중 정합성을 유지해야 함
- 라우팅 정보도 함께 변경해야 함
- 잘못 처리하면 일부 요청이 오래된 샤드로 향할 수 있음

따라서 샤딩은 처음 도입보다 이후의 확장 전략을 더 신중히 설계해야 합니다.

### 분산 트랜잭션과 정합성 문제

하나의 비즈니스 작업이 여러 샤드의 데이터를 동시에 수정해야 하면 분산 트랜잭션 문제가 생깁니다.

대표적인 대응 방식은 다음과 같습니다.

- `2PC(Two-Phase Commit)` 같은 분산 트랜잭션 기법 사용
- 보상 트랜잭션 기반의 최종 일관성 모델 적용
- 샤드 간 쓰기 작업을 줄이도록 도메인 경계 재설계

하지만 어떤 방식을 택하더라도 단일 DB보다 구현과 운영이 훨씬 복잡해집니다.

### 운영 복잡도 증가

샤드 수가 늘어날수록 모니터링, 백업, 장애 대응, 스키마 변경도 복잡해집니다.

- 장애가 발생한 샤드만 부분적으로 영향받을 수 있음
- 반대로 샤드마다 상태가 달라 운영 일관성이 깨질 수 있음
- 스키마 변경 시 모든 샤드에 순차 또는 병렬 반영이 필요함

즉, 샤딩은 성능 확장의 대가로 운영 복잡도를 크게 높이는 선택입니다.

## 샤딩이 적합한 경우

다음과 같은 상황에서는 샤딩이 유효할 수 있습니다.

- 단일 DB 서버의 저장 용량이나 처리량 한계에 도달한 경우
- 데이터 양이 매우 크고 지속적으로 증가하는 경우
- 사용자나 테넌트 단위로 데이터 접근 경계가 비교적 명확한 경우
- 대부분의 요청을 단일 샤드에서 처리할 수 있도록 설계 가능한 경우

반대로 데이터 규모가 아직 크지 않거나, 여러 엔터티를 복잡하게 조인하는 조회가 많다면 샤딩은 이점보다 비용이 더 클 수 있습니다.

## 정리

- 샤딩은 데이터를 여러 독립 데이터베이스에 분산하는 수평 확장 아키텍처입니다.
- 파티셔닝은 단일 DB 내부 분할이고, 샤딩은 물리적으로 분리된 서버 간 분산입니다.
- 대표적인 방식은 레인지 샤딩, 해시 샤딩, 디렉토리 샤딩입니다.
- 샤딩의 성패는 샤드 키 설계와 리샤딩 전략에 크게 좌우됩니다.
- 샤딩은 성능과 확장성을 얻는 대신 조인, 정합성, 운영 복잡도 문제를 동반합니다.

결국 샤딩은 "데이터를 나눈다"는 수준의 기법이 아니라, 데이터 모델링과 애플리케이션 로직, 운영 방식까지 함께 바꾸는 아키텍처 선택입니다.
