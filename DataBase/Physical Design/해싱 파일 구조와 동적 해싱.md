# 해싱 파일 구조와 동적 해싱

## 개요

해싱은 검색 키에 해시 함수를 적용해 데이터가 저장될 버킷(bucket)을 바로 찾는 저장 구조입니다.  
B+Tree가 키 값을 정렬된 구조로 관리해 범위 검색에 강하다면, 해싱은 특정 키 값이 정확히 주어지는 `동등 조건(=)` 검색에 강합니다.

예를 들어 `user_id = 1004`인 행을 찾는다고 할 때, 해싱 구조는 다음과 같이 동작합니다.

1. `user_id` 값을 해시 함수에 넣습니다.
2. 해시 결과를 기준으로 접근할 버킷을 결정합니다.
3. 해당 버킷 안에서 원하는 레코드를 찾습니다.

즉, 해싱의 핵심은 "정렬된 순서로 탐색한다"가 아니라, **키 값을 저장 위치로 직접 매핑한다**는 점입니다.

## 해싱을 이해하기 위한 기본 개념

해싱 구조를 볼 때는 다음 개념을 먼저 구분해야 합니다.

- `Search Key`: 해시 함수에 입력되는 값입니다.
- `Hash Function`: 키 값을 버킷 번호로 변환하는 함수입니다.
- `Bucket`: 실제 레코드나 레코드 위치 정보가 저장되는 공간 단위입니다.
- `Overflow Bucket`: 기본 버킷이 가득 찼을 때 추가로 연결되는 보조 공간입니다.

버킷은 데이터베이스의 블록 또는 페이지 단위와 연결해서 이해할 수 있습니다.  
하나의 버킷에는 여러 레코드가 들어갈 수 있고, 해시 함수는 특정 키가 어느 버킷으로 가야 하는지를 결정합니다.

좋은 해시 함수는 키 값을 여러 버킷에 고르게 분산시켜야 합니다.  
분산이 나쁘면 특정 버킷에 데이터가 몰리고, 결국 오버플로우 버킷을 따라가며 읽어야 하므로 성능이 급격히 떨어질 수 있습니다.

## 1. Static Hashing

### 원리

`Static Hashing`은 버킷의 개수를 미리 정해 두고, 해시 함수의 결과를 고정된 버킷 번호로 매핑하는 방식입니다.

대표적으로 다음과 같은 형태를 사용할 수 있습니다.

```text
bucket = hash(key) mod N
```

여기서 `N`은 전체 버킷 수입니다.  
예를 들어 버킷이 4개라면 해시 결과를 `mod 4`로 나누어 `0 ~ 3`번 버킷 중 하나를 선택합니다.

### 장점

- 구조가 단순합니다.
- 해시 함수와 버킷 수만 알면 접근 위치를 바로 계산할 수 있습니다.
- 데이터 양이 크게 변하지 않는 환경에서는 구현과 관리가 쉽습니다.

### 단점

정적 해싱의 가장 큰 문제는 데이터 증가에 약하다는 점입니다.

처음에는 버킷 수가 충분해 보여도 데이터가 계속 증가하면 일부 버킷이 가득 차게 됩니다.  
이때 기본 버킷에 더 이상 레코드를 넣을 수 없으면 오버플로우 버킷을 연결해야 합니다.

오버플로우가 많아지면 해싱의 장점이 약해집니다.

- 원래는 한 번에 찾아야 할 버킷 접근이 여러 버킷 탐색으로 늘어납니다.
- 특정 버킷에 데이터가 몰리면 체인 길이가 길어집니다.
- 결국 검색 비용이 예측하기 어려워집니다.

반대로 처음부터 버킷을 너무 많이 잡으면 사용되지 않는 공간이 많아져 저장 공간 낭비가 커집니다.

### 유리한 상황

- 데이터 크기가 비교적 안정적일 때
- 동등 조건 검색이 주로 발생할 때
- 저장 공간 증가 패턴을 어느 정도 예측할 수 있을 때

## 2. Extendible Hashing

### 원리

`Extendible Hashing`은 데이터 증가에 맞춰 버킷과 디렉터리를 동적으로 확장하는 해싱 방식입니다.  
정적 해싱처럼 버킷 수를 고정하지 않고, 필요할 때 특정 버킷을 분할합니다.

핵심 구성 요소는 다음과 같습니다.

- `Directory`: 해시 값의 앞쪽 또는 뒤쪽 비트를 보고 실제 버킷을 가리키는 포인터 배열입니다.
- `Global Depth`: 디렉터리가 해시 값의 몇 비트를 사용하는지 나타내는 값입니다.
- `Local Depth`: 각 버킷이 해시 값의 몇 비트까지 구분되어 있는지 나타내는 값입니다.

예를 들어 `Global Depth`가 2라면 디렉터리는 해시 값의 2비트를 사용하므로 `00`, `01`, `10`, `11` 네 개의 엔트리를 가질 수 있습니다.  
각 디렉터리 엔트리는 실제 버킷을 가리킵니다.

중요한 점은 디렉터리 엔트리 수와 실제 버킷 수가 항상 같지는 않다는 것입니다.  
여러 디렉터리 엔트리가 같은 버킷을 가리킬 수 있습니다.

### 버킷 분할 과정

새 레코드를 삽입하려는 버킷이 가득 차면 다음 절차가 진행됩니다.

1. 해당 버킷의 `Local Depth`를 확인합니다.
2. `Local Depth`가 `Global Depth`보다 작으면 버킷만 분할합니다.
3. `Local Depth`가 `Global Depth`와 같으면 디렉터리 크기를 두 배로 늘립니다.
4. 해시 비트를 하나 더 사용해 기존 레코드와 새 레코드를 재분배합니다.

즉, 모든 버킷을 한 번에 재구성하지 않고, **충돌이 발생한 버킷 중심으로 확장**합니다.

### 장점

- 데이터 증가에 따라 필요한 버킷만 분할할 수 있습니다.
- 정적 해싱보다 오버플로우 버킷 사용을 줄일 수 있습니다.
- 검색 시 디렉터리를 한 번 거쳐 버킷을 찾기 때문에 동등 검색 성능이 안정적입니다.

### 단점

- 디렉터리 자체를 관리해야 하므로 구조가 복잡합니다.
- 디렉터리가 커지면 메모리 사용량이 증가할 수 있습니다.
- 디렉터리 크기를 두 배로 늘리는 순간에는 메타데이터 확장 비용이 발생합니다.

### 유리한 상황

- 데이터 증가량을 정확히 예측하기 어려울 때
- 동등 조건 검색이 많고, 안정적인 접근 비용이 중요할 때
- 오버플로우 체인이 길어지는 것을 피하고 싶을 때

## 3. Linear Hashing

### 원리

`Linear Hashing`은 디렉터리를 두 배로 확장하는 방식 대신, 버킷을 순서대로 하나씩 분할하는 동적 해싱 방식입니다.  
확장 가능한 해싱과 달리 큰 디렉터리에 의존하지 않고, `split pointer`를 이용해 다음에 분할할 버킷을 추적합니다.

기본 아이디어는 다음과 같습니다.

- 처음에는 낮은 레벨의 해시 함수 `h0`를 사용합니다.
- 데이터가 증가하면 `split pointer`가 가리키는 버킷을 분할합니다.
- 분할된 버킷의 데이터는 더 높은 레벨의 해시 함수 `h1`로 재배치합니다.
- `split pointer`는 다음 버킷으로 이동합니다.
- 한 라운드의 모든 버킷이 분할되면 레벨을 올리고 다시 처음부터 진행합니다.

즉, 선형 해싱은 전체 구조를 한 번에 크게 바꾸지 않고, **버킷을 점진적으로 분할**합니다.

### 삽입과 분할 흐름

레코드를 삽입할 때는 현재 레벨의 해시 함수로 우선 버킷을 계산합니다.  
다만 계산된 버킷이 이미 분할된 영역에 속한다면, 더 높은 레벨의 해시 함수를 다시 적용해 실제 버킷을 찾습니다.

삽입 후 버킷이 가득 차거나 적재율(load factor)이 기준을 넘으면 `split pointer`가 가리키는 버킷을 분할합니다.  
이때 반드시 오버플로우가 발생한 버킷을 바로 분할하는 것은 아닙니다.

이 점이 선형 해싱의 특징입니다.  
분할은 정해진 순서대로 진행되며, 시간이 지나면서 전체 버킷이 균등하게 확장됩니다.

### 장점

- 디렉터리를 크게 유지하지 않아도 됩니다.
- 한 번에 전체 구조를 재해싱하지 않고 점진적으로 확장할 수 있습니다.
- 확장 비용이 여러 삽입 작업에 분산됩니다.

### 단점

- 검색 시 현재 레벨, 분할 포인터, 버킷 상태를 함께 고려해야 합니다.
- 분할 대상이 오버플로우가 발생한 버킷과 다를 수 있어 일시적으로 오버플로우가 남을 수 있습니다.
- 구현과 동작 이해가 정적 해싱보다 복잡합니다.

### 유리한 상황

- 데이터가 지속적으로 증가하는 환경
- 한 번에 큰 디렉터리 확장을 피하고 싶을 때
- 확장 비용을 점진적으로 분산시키고 싶을 때

## Static Hashing, Extendible Hashing, Linear Hashing 비교

| 항목 | Static Hashing | Extendible Hashing | Linear Hashing |
| --- | --- | --- | --- |
| 버킷 수 | 고정 | 필요 시 동적 증가 | 필요 시 점진적 증가 |
| 확장 방식 | 기본적으로 재구성 필요 | 디렉터리 확장 및 버킷 분할 | split pointer 기준 순차 분할 |
| 메타데이터 | 단순 | 디렉터리, Global Depth, Local Depth | 레벨, split pointer |
| 오버플로우 대응 | 오버플로우 버킷 연결 | 버킷 분할로 완화 | 점진적 분할로 완화 |
| 확장 비용 | 커질 수 있음 | 디렉터리 doubling 순간 비용 발생 | 삽입 작업에 분산 |
| 구현 난이도 | 낮음 | 높음 | 중간 이상 |
| 적합한 환경 | 데이터 크기가 안정적인 경우 | 안정적인 검색 성능이 중요한 경우 | 지속적 증가와 점진적 확장이 필요한 경우 |

## B+Tree와 해싱의 차이

해싱은 동등 조건 검색에 강하지만, 모든 검색에 적합한 구조는 아닙니다.  
B+Tree와 비교하면 차이가 더 분명해집니다.

| 항목 | B+Tree | Hashing |
| --- | --- | --- |
| 데이터 배치 기준 | 키 값의 정렬 순서 | 해시 함수 결과 |
| 동등 검색 | 효율적 | 매우 효율적 |
| 범위 검색 | 매우 유리 | 불리 |
| 정렬 결과 활용 | 가능 | 어려움 |
| 순차 접근 | 리프 노드 연결로 가능 | 일반적으로 부적합 |
| 대표 조건 | `=`, `BETWEEN`, `>`, `<`, `ORDER BY` | 주로 `=` |

예를 들어 `user_id = 1004`처럼 정확한 키를 찾는 조건에서는 해싱이 매우 빠를 수 있습니다.  
하지만 `user_id BETWEEN 1000 AND 2000`처럼 범위를 찾는 조건에서는 해시 값이 키 순서를 보존하지 않기 때문에 연속적으로 읽기 어렵습니다.

따라서 해싱은 **정확히 하나의 키 또는 특정 동등 조건을 빠르게 찾는 구조**로 이해하는 것이 좋습니다.

## 해싱에서 성능을 좌우하는 요소

해싱 구조의 성능은 단순히 해시 함수를 쓴다고 자동으로 좋아지지 않습니다.  
다음 요소가 함께 맞아야 합니다.

- 해시 함수가 데이터를 고르게 분산하는가
- 버킷 크기가 데이터 특성과 잘 맞는가
- 오버플로우 버킷이 과도하게 늘어나지 않는가
- 데이터 증가 시 확장 비용을 감당할 수 있는가
- 조회 패턴이 범위 검색보다 동등 검색 중심인가

특히 오버플로우 체인이 길어지면 해싱은 더 이상 `상수 시간`에 가까운 접근을 보장하지 못합니다.  
결국 많은 버킷을 따라가야 하므로 풀 스캔이나 비효율적인 인덱스 접근과 비슷한 문제가 생길 수 있습니다.

## 정리

- 해싱은 검색 키를 해시 함수에 넣어 저장 버킷을 직접 찾는 구조입니다.
- `Static Hashing`은 버킷 수가 고정되어 단순하지만, 데이터 증가 시 오버플로우 문제가 커질 수 있습니다.
- `Extendible Hashing`은 디렉터리와 깊이 정보를 이용해 필요한 버킷을 동적으로 분할합니다.
- `Linear Hashing`은 split pointer를 이용해 버킷을 순서대로 분할하며 확장 비용을 점진적으로 분산합니다.
- 해싱은 동등 조건 검색에 강하지만, 범위 검색과 정렬된 순차 접근에는 적합하지 않습니다.
- B+Tree와 해싱은 우열 관계라기보다, 조회 패턴에 따라 선택해야 하는 서로 다른 물리적 접근 구조입니다.

결국 해싱을 이해할 때 중요한 질문은 "해시가 빠른가"가 아니라, **데이터 증가와 조회 패턴을 감당할 수 있는 방식으로 버킷을 관리하고 있는가**입니다.
