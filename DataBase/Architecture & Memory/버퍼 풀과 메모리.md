# 버퍼 풀과 메모리 관리

## 개요

`Buffer Pool`은 데이터베이스가 디스크의 페이지를 메모리에 올려두고 관리하는 영역입니다.

기본적인 캐싱 개념과 교체 알고리즘 설명은 별도 문서에서 다루고 있으므로, 이 문서에서는 **버퍼 풀 안의 페이지가 어떤 상태로 관리되고, 변경된 페이지가 언제 디스크에 기록되며, 메모리 압박이 생기면 어떤 일이 발생하는지**에 집중합니다.

핵심은 단순히 "데이터를 메모리에 올린다"가 아니라, 메모리에 올라온 페이지를 아래 관점에서 계속 추적하는 것입니다.

- 이 버퍼가 비어 있는가
- 이 페이지가 현재 사용 중인가
- 이 페이지가 변경되었는가
- 이 페이지를 디스크에 내려써야 하는가
- 이 페이지를 다른 페이지로 재사용할 수 있는가

## 페이지와 버퍼 프레임

버퍼 풀을 이해할 때는 `Page`와 `Buffer Frame`을 구분하면 좋습니다.

| 구분 | 의미 |
| --- | --- |
| Page / Block | 디스크에 저장된 데이터베이스의 I/O 단위 |
| Buffer Frame | 버퍼 풀 안에서 페이지 하나를 담을 수 있는 메모리 슬롯 |

디스크에 있는 페이지가 메모리로 올라오면, 해당 페이지는 버퍼 풀의 특정 버퍼 프레임에 배치됩니다.

```text
디스크 페이지
→ 버퍼 풀의 빈 프레임에 적재
→ SQL 실행 과정에서 해당 프레임을 참조
→ 필요하면 같은 프레임이 다른 페이지로 재사용됨
```

즉, 페이지는 디스크의 논리적 데이터 단위이고, 버퍼 프레임은 그 페이지를 메모리에 담는 물리적 공간에 가깝습니다.

## 버퍼 풀에서 관리하는 페이지 상태

버퍼 풀은 단순한 메모리 배열이 아니라, 각 프레임과 페이지의 상태를 계속 추적하는 관리 구조입니다.

### 1. Free

`Free` 상태는 아직 어떤 페이지도 담고 있지 않거나, 즉시 재사용할 수 있는 빈 프레임을 의미합니다.

데이터베이스가 새 페이지를 메모리에 올려야 할 때는 먼저 사용 가능한 프레임을 찾습니다.  
비어 있는 프레임이 있으면 기존 페이지를 밀어내는 과정 없이 바로 사용할 수 있습니다.

### 2. Clean

`Clean Page`는 메모리에 올라와 있지만 디스크의 원본과 내용이 같은 페이지입니다.

이 페이지는 메모리에서 제거하더라도 데이터 손실이 없습니다.  
필요하면 나중에 디스크에서 다시 읽어올 수 있기 때문입니다.

### 3. Dirty

`Dirty Page`는 메모리에서는 변경되었지만 아직 디스크의 데이터 파일에는 반영되지 않은 페이지입니다.

이 페이지는 바로 버릴 수 없습니다.  
제거하기 전에 변경 내용을 디스크에 기록해야 합니다.

### 4. Pinned

`Pinned` 또는 `Fixed` 상태는 현재 어떤 세션이나 실행 엔진이 해당 페이지를 사용 중이라는 뜻입니다.

예를 들어 쿼리가 페이지를 읽고 있거나 변경 중이라면, 데이터베이스는 그 페이지를 임의로 제거하거나 다른 페이지로 덮어쓸 수 없습니다.  
사용이 끝나고 고정이 풀린 뒤에야 재사용 후보가 될 수 있습니다.

## 버퍼 풀 내부의 대표 관리 구조

구현은 데이터베이스 제품마다 다르지만, 버퍼 풀은 보통 아래와 같은 보조 구조를 함께 사용합니다.

### 1. Free List

`Free List`는 즉시 사용할 수 있는 빈 버퍼 프레임 목록입니다.

인스턴스가 시작된 직후에는 빈 프레임이 많지만, 시간이 지나면 대부분의 프레임이 한 번 이상 사용됩니다.  
이후에는 빈 프레임을 찾는 것보다 기존 프레임을 재사용 가능한 상태로 만드는 작업이 더 중요해집니다.

### 2. Flush List

`Flush List`는 디스크에 아직 반영되지 않은 더티 페이지를 추적하는 목록입니다.

데이터베이스는 이 목록을 이용해 어떤 페이지를 먼저 디스크에 기록할지 판단합니다.  
일반적으로 오래전에 변경된 페이지, 체크포인트 진행에 필요한 페이지, 메모리 확보에 필요한 페이지가 플러시 대상이 됩니다.

### 3. Page Hash

`Page Hash`는 특정 페이지가 현재 어느 버퍼 프레임에 올라와 있는지 빠르게 찾기 위한 구조입니다.

버퍼 풀에는 많은 페이지가 존재할 수 있으므로, 매번 전체 프레임을 순차적으로 탐색하면 비용이 큽니다.  
데이터베이스는 파일 번호, 페이지 번호 같은 식별자를 기준으로 해시 구조를 두고 페이지 위치를 빠르게 찾습니다.

### 4. Pin Count

`Pin Count`는 특정 페이지를 현재 몇 개의 작업이 사용 중인지 나타내는 값입니다.

값이 0보다 크면 해당 페이지는 아직 사용 중인 상태입니다.  
따라서 메모리 공간이 부족하더라도 이 페이지를 바로 재사용할 수 없습니다.

## 변경 작업과 Dirty Page

사용자가 `INSERT`, `UPDATE`, `DELETE`를 실행하면 데이터베이스는 보통 메모리에 올라온 페이지를 먼저 변경합니다.  
이때 페이지의 상태는 `Dirty`로 바뀝니다.

```text
변경 SQL 실행
→ 대상 페이지를 버퍼 풀에서 찾거나 읽어옴
→ 페이지를 사용하는 동안 Pin 상태로 보호
→ 메모리의 페이지 내용 변경
→ Dirty Page로 표시
→ 작업이 끝나면 Pin 해제
```

더티 페이지는 변경 내용을 담고 있으므로, 언젠가는 데이터 파일에 기록되어야 합니다.  
하지만 변경이 발생할 때마다 즉시 데이터 파일에 쓰는 것은 비효율적입니다.

같은 페이지가 짧은 시간 안에 여러 번 변경될 수 있고, 여러 페이지를 모아서 쓰면 I/O를 더 효율적으로 처리할 수 있기 때문입니다.

## Flush가 발생하는 시점

`Flush`는 더티 페이지를 디스크의 데이터 파일에 기록하는 작업입니다.

플러시는 보통 아래 상황에서 발생합니다.

### 1. 체크포인트 진행

체크포인트는 특정 시점까지의 변경 내용이 데이터 파일에 어느 정도 반영되었는지 정리하는 기준점입니다.

체크포인트가 진행되면 데이터베이스는 오래된 더티 페이지를 디스크에 기록해, 장애 복구 시 다시 적용해야 하는 로그 범위를 줄입니다.

### 2. 메모리 공간 부족

새로운 페이지를 올려야 하는데 재사용 가능한 프레임이 부족하면, 데이터베이스는 기존 프레임을 확보해야 합니다.

깨끗한 페이지는 바로 재사용할 수 있지만, 더티 페이지는 먼저 플러시해야 합니다.  
따라서 더티 페이지가 너무 많으면 메모리 확보 과정이 느려질 수 있습니다.

### 3. 백그라운드 플러시

대부분의 데이터베이스는 사용자 세션이 직접 오래 기다리지 않도록 백그라운드 작업을 통해 더티 페이지를 미리 디스크에 기록합니다.

이 작업이 충분히 따라가지 못하면, 나중에 사용자 쿼리가 메모리 공간을 확보하는 과정에서 플러시를 기다릴 수 있습니다.

## 로그와 복구의 관계

더티 페이지를 나중에 디스크에 기록한다면, 장애 발생 시 변경 내용이 사라질 위험이 있습니다.  
이를 막기 위해 데이터베이스는 `Redo Log` 또는 `WAL(Write-Ahead Logging)`을 사용합니다.

핵심 원칙은 **데이터 파일보다 변경 로그를 먼저 안정적으로 기록하는 것**입니다.

```text
변경 발생
→ 변경 내용을 로그에 기록
→ 버퍼 풀의 페이지 변경
→ 더티 페이지를 나중에 데이터 파일에 기록
→ 장애 발생 시 로그를 이용해 복구
```

즉, 버퍼 풀은 데이터 파일 쓰기를 지연시키지만, 로그를 통해 복구 가능성을 유지합니다.

## 메모리 압박이 생길 때의 흐름

버퍼 풀 공간이 부족해지면 데이터베이스는 재사용 가능한 프레임을 확보해야 합니다.

이때 페이지 상태에 따라 처리 방식이 달라집니다.

| 페이지 상태 | 처리 방식 |
| --- | --- |
| Free | 바로 사용 가능 |
| Clean | 필요하면 즉시 재사용 가능 |
| Dirty | 디스크에 플러시한 뒤 재사용 가능 |
| Pinned | 현재 사용 중이므로 재사용 불가 |

메모리 압박이 심한데 더티 페이지나 고정된 페이지가 많으면, 새 페이지를 올리는 작업이 지연될 수 있습니다.

특히 아래 상황에서는 병목이 커질 수 있습니다.

- 변경 작업이 많아 더티 페이지가 빠르게 증가하는 경우
- 디스크 쓰기 속도가 플러시 속도를 따라가지 못하는 경우
- 긴 쿼리가 많은 페이지를 오래 고정하는 경우
- 버퍼 풀 외의 메모리 부족으로 운영체제 스왑이 발생하는 경우

## Read Ahead와 Prefetch

데이터베이스는 접근 패턴을 보고 앞으로 필요할 가능성이 높은 페이지를 미리 읽을 수 있습니다.  
이를 `Read Ahead` 또는 `Prefetch`라고 부릅니다.

예를 들어 테이블 스캔이나 인덱스 범위 스캔처럼 연속된 페이지를 읽는 패턴이 감지되면, 다음 페이지들을 미리 버퍼 풀에 올릴 수 있습니다.

```text
현재 페이지 접근
→ 연속 접근 패턴 감지
→ 다음 페이지들을 미리 읽음
→ 실제 실행 흐름이 도달했을 때 대기 시간 감소
```

다만 예측이 빗나가면 당장 필요하지 않은 페이지가 메모리를 차지할 수 있습니다.  
따라서 미리 읽기는 버퍼 풀의 여유 공간과 현재 I/O 부하를 함께 고려해야 합니다.

## 버퍼 풀 크기와 전체 메모리 균형

버퍼 풀은 클수록 유리한 경우가 많지만, 무조건 크게 잡는 것이 정답은 아닙니다.

데이터베이스는 버퍼 풀 외에도 여러 메모리 영역을 사용합니다.

| 메모리 영역 | 주요 역할 |
| --- | --- |
| Buffer Pool | 테이블과 인덱스 페이지 보관 |
| Shared Pool / Plan Cache | SQL, 실행 계획, 메타데이터 보관 |
| Redo Log Buffer | 변경 로그를 디스크에 쓰기 전 임시 저장 |
| Sort / Hash Memory | 정렬, 해시 조인, 그룹핑 작업 수행 |
| Connection / Session Memory | 세션 상태, 커서, 임시 작업 정보 저장 |

버퍼 풀을 지나치게 크게 잡으면 정렬, 해시 조인, 세션 메모리, 운영체제 파일 시스템 캐시가 부족해질 수 있습니다.  
최악의 경우 운영체제 스왑이 발생하면서 전체 데이터베이스 성능이 크게 떨어집니다.

따라서 버퍼 풀 크기는 데이터 크기만 보고 정하는 것이 아니라, 쿼리 특성, 동시 접속 수, 정렬/해시 작업량, 로그 쓰기 부하, 운영체제 메모리 여유를 함께 보고 결정해야 합니다.

## 한눈에 정리

| 항목 | 의미 |
| --- | --- |
| Buffer Frame | 페이지를 담는 버퍼 풀 내부 메모리 슬롯 |
| Clean Page | 디스크의 원본과 내용이 같은 페이지 |
| Dirty Page | 메모리에서 변경되었지만 아직 데이터 파일에 기록되지 않은 페이지 |
| Pinned Page | 현재 작업이 사용 중이라 재사용할 수 없는 페이지 |
| Free List | 즉시 사용할 수 있는 프레임 목록 |
| Flush List | 디스크 기록이 필요한 더티 페이지 목록 |
| Page Hash | 페이지가 어느 프레임에 있는지 빠르게 찾기 위한 구조 |
| Flush | 더티 페이지를 데이터 파일에 기록하는 작업 |
| Read Ahead | 앞으로 필요할 가능성이 높은 페이지를 미리 읽는 방식 |

## 흐름으로 보면

```text
SQL 실행
→ 필요한 페이지를 버퍼 프레임에 배치
→ 작업 중인 페이지는 Pin 상태로 보호
→ 변경이 발생하면 Dirty Page로 표시
→ 로그를 먼저 기록해 복구 가능성 확보
→ 백그라운드 작업이나 체크포인트가 Dirty Page를 Flush
→ Clean 상태가 된 프레임은 필요 시 재사용
```

## 정리

- 버퍼 풀 관리는 페이지를 메모리에 올리는 일뿐 아니라, 페이지 상태를 추적하고 재사용 가능 여부를 판단하는 과정입니다.
- `Dirty Page`는 변경 내용을 담고 있으므로 제거 전에 반드시 플러시가 필요합니다.
- `Pinned Page`는 현재 사용 중인 페이지이기 때문에 메모리 압박 상황에서도 바로 재사용할 수 없습니다.
- 플러시가 늦어지면 새 페이지를 올리는 작업이 지연되고, 사용자 쿼리가 디스크 쓰기를 기다릴 수 있습니다.
- 버퍼 풀 크기는 다른 데이터베이스 메모리 영역과 운영체제 메모리까지 함께 고려해 결정해야 합니다.

결국 버퍼 풀과 메모리 관리는 **페이지 상태, 더티 페이지 플러시, 로그 기반 복구, 전체 메모리 균형을 함께 제어하는 데이터베이스의 핵심 운영 메커니즘**입니다.
