# CQRS 패턴

## 개요

`CQRS(Command Query Responsibility Segregation)`는 **상태를 변경하는 요청(Command)** 과 **상태를 조회하는 요청(Query)** 의 책임을 분리하는 아키텍처 패턴입니다.  
핵심은 "쓰기와 읽기는 성격이 다르므로, 같은 모델로 다루지 말자"는 데 있습니다.

전통적인 CRUD 구조에서는 하나의 도메인 모델이나 하나의 테이블 구조를 기준으로 생성, 수정, 삭제, 조회를 모두 처리하는 경우가 많습니다.  
하지만 실제 서비스에서는 쓰기와 읽기의 요구사항이 크게 다를 수 있습니다.

- 쓰기는 비즈니스 규칙 검증과 트랜잭션 일관성이 중요합니다.
- 읽기는 빠른 응답 속도와 화면 맞춤형 데이터 구성이 더 중요합니다.

CQRS는 이 차이를 인정하고, **쓰기 모델과 읽기 모델을 분리해서 각각에 맞게 최적화**하려는 접근입니다.

## CQRS가 필요한 이유

CRUD 방식은 단순한 시스템에서는 효율적이지만, 도메인이 복잡해질수록 한계가 드러납니다.

예를 들어 주문 시스템을 생각해보면 쓰기 쪽에서는 다음이 중요합니다.

- 주문 생성 시 재고 차감이 가능한가
- 결제 상태가 유효한가
- 주문 상태 전이가 올바른가

반면 조회 쪽에서는 다음이 더 중요합니다.

- 주문 목록을 페이지 단위로 빠르게 보여줄 수 있는가
- 주문, 고객, 결제, 배송 정보를 한 화면에 묶어 보여줄 수 있는가
- 통계나 집계 데이터를 쉽게 만들 수 있는가

즉, **쓰기 모델은 무결성과 규칙 중심**, **읽기 모델은 조회 편의성과 성능 중심**으로 요구사항이 갈라집니다.  
이 둘을 하나의 모델에 모두 담으려 하면 모델이 비대해지고, 결국 어느 한쪽도 충분히 잘 최적화하지 못하게 됩니다.

## 1. Command와 Query

CQRS를 이해하려면 먼저 `Command`와 `Query`를 명확히 구분해야 합니다.

### Command

`Command`는 시스템의 상태를 변경하는 요청입니다.

- 회원 가입
- 주문 생성
- 상품 정보 수정
- 결제 취소

Command는 보통 다음 특징을 가집니다.

- 비즈니스 규칙 검증이 필요합니다.
- 트랜잭션 경계가 중요합니다.
- 성공 또는 실패가 명확해야 합니다.
- 수행 결과로 상태가 바뀝니다.

즉, Command 모델은 "이 변경이 가능한가?"를 엄격하게 판단하는 역할을 맡습니다.

### Query

`Query`는 시스템의 상태를 읽어오는 요청입니다.

- 주문 상세 조회
- 사용자 프로필 조회
- 관리자 통계 화면 조회
- 검색 결과 목록 조회

Query는 다음 특징을 가집니다.

- 상태를 바꾸지 않습니다.
- 응답 형식이 화면이나 API 요구에 맞게 자유로울 수 있습니다.
- 조인, 집계, 캐시, 비정규화 구조가 자주 사용됩니다.

즉, Query 모델은 "어떻게 빨리, 보기 좋게 읽을 것인가?"에 집중합니다.

## 2. CQRS 구조

CQRS의 기본 구조는 다음과 같이 볼 수 있습니다.

1. 사용자가 상태 변경 요청을 보냅니다.
2. Command 모델이 입력을 검증하고 도메인 규칙을 적용합니다.
3. 쓰기 저장소에 트랜잭션을 반영합니다.
4. 필요하면 이벤트를 발행합니다.
5. 읽기 모델이 이벤트나 변경 결과를 반영해 조회용 데이터를 갱신합니다.
6. 사용자의 조회 요청은 읽기 모델이 처리합니다.

이 구조에서 중요한 점은 **쓰기 모델과 읽기 모델이 꼭 같은 저장 구조를 가질 필요가 없다는 것**입니다.

- 쓰기 모델은 정규화된 RDB 테이블일 수 있습니다.
- 읽기 모델은 조회 전용 테이블, 캐시, 검색 엔진 문서, 집계 테이블일 수 있습니다.

즉, CQRS는 단순히 클래스를 나누는 수준을 넘어서 **모델, 저장소, 확장 전략까지 분리할 수 있는 패턴**입니다.

### 읽기/쓰기 저장소는 반드시 분리해야 할까

반드시 그렇지는 않습니다.  
CQRS는 책임 분리가 핵심이지, 물리적으로 DB를 꼭 둘로 나누는 것이 본질은 아닙니다.

구현 수준은 다양할 수 있습니다.

- 같은 DB 안에서 Command 객체와 Query 객체만 분리
- 같은 DB지만 읽기 전용 테이블이나 View를 따로 구성
- 쓰기 DB와 읽기 DB를 물리적으로 분리
- 읽기 모델을 캐시나 검색 엔진으로 별도 운영

즉, CQRS는 "분리의 정도"를 시스템 복잡도에 맞게 조절할 수 있습니다.

## 3. CQRS와 Event Sourcing의 관계

`CQRS`와 `Event Sourcing`은 자주 함께 언급되지만, 같은 개념은 아닙니다.

- `CQRS`: 쓰기와 읽기 책임을 분리하는 패턴
- `Event Sourcing`: 상태 자체를 저장하기보다 상태 변경 이벤트를 저장하는 패턴

둘은 함께 쓰이면 잘 맞습니다.  
예를 들어 Command 쪽에서 상태 변경이 일어날 때 이벤트를 저장하고, 그 이벤트를 이용해 읽기 모델 Projection을 만들 수 있기 때문입니다.

하지만 CQRS를 쓴다고 해서 반드시 Event Sourcing을 도입해야 하는 것은 아닙니다.  
반대로 Event Sourcing 없이도 일반적인 RDB 테이블 기반으로 CQRS를 구현할 수 있습니다.

## 4. CQRS의 장점

### 읽기와 쓰기를 각각 최적화할 수 있다

쓰기 모델은 도메인 무결성과 트랜잭션 중심으로 설계하고, 읽기 모델은 화면 요구사항과 조회 성능 중심으로 설계할 수 있습니다.  
이 때문에 두 요구사항이 서로 덜 충돌하게 됩니다.

### 복잡한 도메인 로직을 더 명확하게 표현할 수 있다

Command 쪽에 규칙을 집중시키면 "상태를 어떻게 바꿀 수 있는가"가 모델 안에 명확하게 드러납니다.  
그 결과 비즈니스 규칙이 서비스 곳곳에 흩어지는 것을 줄일 수 있습니다.

### 조회 성능을 높이기 쉽다

조회 전용 모델은 비정규화, 캐시, 검색 인덱스, 집계 테이블 등을 자유롭게 활용할 수 있습니다.  
따라서 복잡한 화면도 단순한 조회 한 번으로 응답할 수 있게 만들 수 있습니다.

### 읽기와 쓰기 트래픽을 따로 확장할 수 있다

실서비스에서는 읽기 비중이 훨씬 큰 경우가 많습니다.  
CQRS를 적용하면 읽기 모델만 별도로 확장하거나, 읽기 저장소만 캐시/복제본으로 분산하는 전략을 취하기 쉬워집니다.

## 5. CQRS의 단점과 주의점

### 구조가 복잡해진다

쓰기 모델과 읽기 모델을 따로 두면 코드, 데이터 흐름, 운영 포인트가 모두 늘어납니다.  
단순 CRUD 시스템에 적용하면 얻는 이점보다 복잡성이 더 커질 수 있습니다.

### 최종 일관성 문제가 생길 수 있다

쓰기 결과가 즉시 읽기 모델에 반영되지 않으면, 방금 수정한 데이터가 조회 화면에 잠깐 보이지 않을 수 있습니다.  
이런 구조를 `Eventually Consistent`라고 합니다.

이 문제는 특히 이벤트 기반으로 읽기 모델을 갱신할 때 자주 나타납니다.  
따라서 사용자 경험과 비즈니스 요구사항이 이 지연을 허용하는지 먼저 판단해야 합니다.

### 디버깅과 운영이 어려워진다

같은 데이터를 쓰기 모델과 읽기 모델이 각각 다른 형태로 관리하면,

- 어느 시점에 동기화가 밀렸는지
- 어떤 이벤트가 반영되지 않았는지
- 읽기 데이터가 왜 stale 상태인지

를 추적해야 하므로 관측성과 운영 도구가 중요해집니다.

### 팀의 설계 역량이 필요하다

CQRS는 단순히 폴더를 나누는 패턴이 아닙니다.  
트랜잭션 경계, 이벤트 흐름, 읽기 모델 재구축, 장애 복구까지 함께 고려해야 하므로 팀이 분리의 목적을 정확히 이해하고 있어야 합니다.

## 6. 언제 적합한가

다음과 같은 경우 CQRS가 특히 잘 맞습니다.

- 읽기 트래픽이 쓰기보다 훨씬 많은 시스템
- 쓰기 규칙이 복잡하고 도메인 모델이 중요한 시스템
- 조회 화면마다 필요한 데이터 조합이 크게 다른 시스템
- 읽기 성능 최적화가 중요한 대규모 서비스
- 이벤트 기반 아키텍처와 잘 결합해야 하는 시스템

예를 들어 주문, 결제, 정산, 배송처럼 상태를 변경하는 규칙이 많고 조회 요구도 다양한 도메인에서는 CQRS가 효과적일 수 있습니다.

## 7. 언제 과할 수 있는가

다음과 같은 경우에는 CQRS가 과한 선택이 될 수 있습니다.

- 단순한 관리자 페이지 중심 CRUD 시스템
- 도메인 규칙이 거의 없고 테이블 조작이 곧 비즈니스인 경우
- 트래픽 규모가 작고 조회 성능 문제가 크지 않은 경우
- 작은 팀이 빠르게 개발해야 하는 초기 서비스

이런 경우에는 우선 전통적인 CRUD 구조로 시작하고, 실제 병목과 복잡성이 드러날 때 CQRS를 부분적으로 도입하는 편이 더 현실적입니다.

## 8. 오해하기 쉬운 부분

### CQRS는 무조건 마이크로서비스 아키텍처인가

아닙니다.  
단일 애플리케이션 내부에서도 충분히 CQRS를 적용할 수 있습니다.  
핵심은 서비스 분리가 아니라 **읽기/쓰기 책임 분리**입니다.

### CQRS는 무조건 DB를 두 개 써야 하는가

아닙니다.  
같은 DB를 쓰더라도 모델과 접근 경로를 분리하면 CQRS의 핵심을 적용한 것입니다.

### CQRS를 쓰면 항상 최종 일관성이 필요한가

항상 그런 것은 아닙니다.  
같은 트랜잭션 안에서 읽기 모델을 함께 갱신하면 강한 일관성을 유지할 수도 있습니다.  
다만 CQRS를 크게 확장할수록 최종 일관성을 받아들이는 구조가 많아집니다.

### CQRS는 조회 성능 패턴일 뿐인가

아닙니다.  
조회 성능 향상은 중요한 효과 중 하나이지만, 본질은 **도메인 변경 책임과 조회 책임을 분리해 모델을 단순화하는 것**입니다.

## 정리

- `CQRS`는 상태 변경 요청과 조회 요청의 책임을 분리하는 아키텍처 패턴입니다.
- 쓰기 모델은 비즈니스 규칙과 트랜잭션, 읽기 모델은 조회 성능과 응답 형태에 집중합니다.
- 읽기/쓰기 모델은 논리적으로만 분리할 수도 있고, 필요하면 저장소까지 물리적으로 분리할 수도 있습니다.
- `Event Sourcing`은 CQRS와 자주 함께 쓰이지만, CQRS의 필수 조건은 아닙니다.
- CQRS는 복잡한 도메인과 높은 조회 요구가 있는 시스템에서 강점을 가지지만, 단순 CRUD 시스템에는 과할 수 있습니다.
- 결국 CQRS는 "무조건 도입할 패턴"이 아니라, **읽기와 쓰기의 성격 차이가 충분히 클 때 선택하는 설계 전략**이라고 보는 것이 적절합니다.
