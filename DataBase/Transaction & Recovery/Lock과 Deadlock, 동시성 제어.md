# Lock과 Deadlock, 동시성 제어

## 개요

데이터베이스는 여러 세션이 동시에 같은 데이터를 읽고 수정하는 환경에서 동작합니다.  
이때 아무 제어 없이 병렬 실행만 허용하면 데이터가 꼬이거나, 일부 변경이 덮어써지거나, 중간 상태를 읽는 문제가 생길 수 있습니다.

이 문제를 막기 위해 DBMS는 `동시성 제어(Concurrency Control)` 메커니즘을 사용합니다.

- `Lock`은 동시에 접근하는 작업 간 충돌을 직접 제어합니다.
- `Deadlock`은 서로가 서로의 자원을 기다리며 멈춰 버리는 상태입니다.
- `MVCC`는 읽기 일관성을 높여 읽기와 쓰기의 충돌을 줄이는 방식입니다.

즉, 동시성 제어는 단순히 "잠근다"는 개념이 아니라, `정합성`, `성능`, `동시 처리량` 사이에서 균형을 잡는 기술입니다.

## 동시성 제어란 무엇인가

동시성 제어는 여러 트랜잭션이 동시에 실행될 때도 결과가 논리적으로 올바르게 유지되도록 보장하는 메커니즘입니다.

핵심 목표는 다음과 같습니다.

- 서로 충돌하는 변경을 안전하게 조정한다
- 읽기 작업이 잘못된 중간 상태를 보지 않게 한다
- 가능한 한 많은 작업을 동시에 처리한다

동시성 제어가 없다면 다음과 같은 문제가 생길 수 있습니다.

- 두 트랜잭션이 같은 값을 수정해 한쪽 결과가 덮어써지는 `Lost Update`
- 커밋되지 않은 중간 상태를 읽는 문제
- 같은 트랜잭션 안에서 조회 결과가 계속 달라지는 문제

즉, DBMS는 "동시에 처리"와 "올바르게 처리"를 함께 만족시켜야 합니다.

## 1. Lock이란 무엇인가

`Lock`은 특정 데이터에 대한 접근 권한을 제한해 충돌을 방지하는 장치입니다.  
어떤 트랜잭션이 데이터를 읽거나 수정할 때 DBMS는 필요한 범위에 잠금을 걸어 다른 트랜잭션의 접근을 제어합니다.

가장 단순하게 보면 Lock은 다음 질문에 답합니다.

- 지금 이 데이터를 다른 트랜잭션도 읽어도 되는가
- 지금 이 데이터를 다른 트랜잭션이 수정해도 되는가
- 이 작업은 기다려야 하는가, 바로 진행해도 되는가

### Lock이 필요한 이유

예를 들어 같은 계좌 잔액을 두 세션이 동시에 수정한다고 가정해 보겠습니다.

- 세션 A가 잔액 `100`을 읽고 `-30`을 계산합니다.
- 세션 B도 같은 시점에 잔액 `100`을 읽고 `-50`을 계산합니다.
- 둘이 차례로 반영되면 최종 결과가 `20`이 아니라 `50` 또는 `70`이 될 수 있습니다.

이런 충돌을 막기 위해 DBMS는 수정 중인 데이터에 대해 다른 수정 작업을 제한합니다.

## 2. 대표적인 Lock 종류

DBMS마다 세부 구현은 다르지만, 개념적으로는 다음 두 가지가 가장 중요합니다.

### Shared Lock

`Shared Lock`은 읽기를 위한 잠금입니다.  
여러 트랜잭션이 동시에 같은 데이터를 읽는 것은 보통 허용되므로, 공유 잠금은 서로 공존할 수 있습니다.

즉, `읽기-읽기`는 대체로 함께 허용됩니다.

### Exclusive Lock

`Exclusive Lock`은 쓰기를 위한 잠금입니다.  
어떤 트랜잭션이 데이터를 수정하는 동안에는 다른 트랜잭션이 같은 데이터를 수정하거나, 경우에 따라 읽는 것까지 제한될 수 있습니다.

즉, `쓰기-쓰기` 충돌은 강하게 제어됩니다.

### 잠금 대상 범위

잠금은 항상 "행 하나"에만 걸리는 것은 아닙니다.  
DBMS는 상황에 따라 여러 수준에서 잠금을 사용할 수 있습니다.

- `Row Lock`: 특정 행 단위 제어
- `Page/Block Lock`: 페이지 또는 블록 단위 제어
- `Table Lock`: 테이블 전체 단위 제어

잠금 범위가 커질수록 정합성 제어는 단순해지지만, 동시성은 떨어지기 쉽습니다.

## 3. Lock이 실제로 동작하는 방식

트랜잭션이 데이터를 수정하려고 하면 DBMS는 먼저 해당 데이터에 필요한 잠금을 확보하려고 시도합니다.

### 잠금을 바로 얻는 경우

충돌하는 잠금이 없다면 트랜잭션은 즉시 진행됩니다.

### 잠금을 기다리는 경우

다른 트랜잭션이 이미 충돌하는 잠금을 보유 중이라면 현재 트랜잭션은 대기 상태로 들어갑니다.

이때 발생하는 현상이 `Blocking`입니다.

- 세션 A가 어떤 행을 수정 중이다
- 세션 B도 같은 행을 수정하려 한다
- 세션 B는 세션 A의 커밋 또는 롤백까지 기다린다

즉, 모든 대기가 Deadlock은 아닙니다.  
대부분은 정상적인 `Lock Wait`입니다.

## 4. Deadlock이란 무엇인가

`Deadlock`은 둘 이상의 트랜잭션이 서로가 가진 잠금이 풀리기만 기다리며, 영원히 진행할 수 없는 상태입니다.

가장 대표적인 예시는 다음과 같습니다.

### 예시

- 세션 A는 `행 1`을 잠근 뒤 `행 2`를 수정하려고 합니다.
- 세션 B는 `행 2`를 잠근 뒤 `행 1`을 수정하려고 합니다.
- 세션 A는 세션 B가 가진 잠금을 기다립니다.
- 세션 B는 세션 A가 가진 잠금을 기다립니다.

이제 둘 다 상대가 끝나기를 기다리지만, 누구도 먼저 끝날 수 없습니다.  
이 상태가 `Deadlock`입니다.

## 5. Deadlock과 일반 대기의 차이

둘은 모두 "기다린다"는 점에서는 비슷하지만 의미는 다릅니다.

| 구분 | 일반 Lock Wait | Deadlock |
| --- | --- | --- |
| 상태 | 잠시 대기 후 풀릴 수 있음 | 서로가 서로를 기다려 영원히 진행 불가 |
| 원인 | 선행 트랜잭션의 작업 중 | 순환 대기 구조 발생 |
| 해결 방식 | 선행 트랜잭션 종료를 기다림 | DBMS가 한쪽을 강제 종료 |

즉, `대기(wait)`는 정상 상황일 수 있지만, `Deadlock`은 DBMS가 반드시 개입해야 하는 오류 상황입니다.

## 6. DBMS는 Deadlock을 어떻게 처리할까

대부분의 DBMS는 잠금 대기 관계를 추적하다가 순환 구조가 발견되면 Deadlock으로 판단합니다.

이후 보통 다음과 같이 처리합니다.

- 관련 트랜잭션 중 하나를 `victim`으로 선택
- 해당 트랜잭션을 강제로 롤백
- 나머지 트랜잭션은 계속 진행

즉, Deadlock은 "영원히 기다리게 두는 것"이 아니라, 한쪽을 희생시켜 전체 시스템을 풀어내는 방식으로 해결합니다.

## 7. 동시성 제어 방식은 Lock만 있는 것이 아니다

동시성 제어를 전부 잠금으로만 처리하면 정합성은 좋아질 수 있지만, 대기와 경합이 크게 늘어날 수 있습니다.  
그래서 DBMS나 애플리케이션은 여러 방식을 조합합니다.

### 비관적 동시성 제어

충돌이 자주 발생한다고 보고, 먼저 잠금을 잡아 충돌 자체를 막는 방식입니다.

- 장점: 충돌 제어가 직관적입니다.
- 단점: 대기 시간이 길어질 수 있습니다.

### 낙관적 동시성 제어

충돌이 드물다고 보고 일단 작업을 진행한 뒤, 커밋 시점에 충돌 여부를 검사하는 방식입니다.

- 장점: 읽기 중심 환경에서 효율적일 수 있습니다.
- 단점: 충돌 시 재시도가 필요합니다.

### MVCC 기반 제어

읽기와 쓰기가 직접 충돌하지 않도록 과거 버전을 활용하는 방식입니다.  
이 방식은 특히 조회가 많은 환경에서 효과적입니다.

즉, 현대 DBMS의 동시성 제어는 `Lock`과 `MVCC`가 함께 작동하는 경우가 많습니다.

## 8. Lock과 MVCC의 관계

`MVCC`가 있다고 해서 Lock이 없어지는 것은 아닙니다.  
둘은 대체 관계라기보다 역할 분담 관계에 가깝습니다.

### MVCC가 잘하는 일

- 읽기 일관성 제공
- 읽기와 쓰기 간 충돌 완화

### Lock이 여전히 필요한 일

- 같은 데이터를 동시에 수정하는 `write-write` 충돌 제어
- 무결성 보장을 위한 직렬화 수준 제어
- 특정 범위에 대한 변경 금지

즉, `읽기`는 MVCC가 많이 도와주지만, `쓰기 충돌`은 여전히 Lock이 핵심입니다.

## 9. Deadlock이 잘 생기는 상황

다음 패턴에서는 Deadlock 가능성이 높아집니다.

### 1. 자원 접근 순서가 제각각일 때

어떤 트랜잭션은 `A -> B` 순서로 잠그고, 다른 트랜잭션은 `B -> A` 순서로 잠그면 순환 대기가 생기기 쉽습니다.

### 2. 트랜잭션이 너무 길 때

트랜잭션이 오래 열려 있으면 잠금을 오래 보유하게 되고, 그만큼 충돌 가능성이 커집니다.

### 3. 한 번에 너무 많은 행을 수정할 때

대량 `UPDATE`, `DELETE`는 잠금 범위를 넓히고 대기 체인을 길게 만들 수 있습니다.

### 4. 인덱스가 부적절할 때

원래는 몇 개 행만 잡아야 할 작업이 넓은 범위를 스캔하면서 예상보다 많은 잠금을 만들 수 있습니다.

## 10. 실무에서 동시성 문제를 줄이는 방법

동시성 제어는 DBMS가 해 주는 일만이 아니라, SQL과 애플리케이션 설계의 영향도 크게 받습니다.

### 1. 트랜잭션을 짧게 유지한다

잠금을 오래 잡고 있지 않도록 조회, 외부 API 호출, 사용자 입력 대기 등을 트랜잭션 안에 오래 두지 않는 것이 중요합니다.

### 2. 자원 접근 순서를 통일한다

여러 테이블이나 행을 함께 갱신해야 한다면 항상 같은 순서로 접근하는 것이 Deadlock 예방에 효과적입니다.

### 3. 필요한 범위만 잠그게 한다

적절한 인덱스를 사용하면 불필요한 스캔과 과도한 잠금을 줄일 수 있습니다.

### 4. 대량 작업은 잘게 나눈다

한 번에 전체를 잠그기보다 배치 단위로 나누면 경합을 줄일 수 있습니다.

### 5. 재시도 로직을 고려한다

Deadlock은 완전히 없애기 어려운 경우가 있으므로, 애플리케이션에서 일시적 실패에 대한 재시도 전략을 두는 것이 현실적입니다.

## 한눈에 비교

| 항목 | Lock | Deadlock | MVCC |
| --- | --- | --- | --- |
| 의미 | 접근 충돌을 제어하는 장치 | 잠금 간 순환 대기 상태 | 과거 버전을 이용한 읽기 일관성 방식 |
| 주 목적 | 충돌 방지 | 시스템이 풀어야 하는 오류 상황 | 읽기와 쓰기 충돌 완화 |
| 핵심 대상 | 읽기/쓰기 권한 | 대기 관계 | 조회 시점의 버전 |
| 없으면 생기는 문제 | 수정 충돌, 정합성 훼손 | 작업 영구 정지 | 조회 대기 증가, 일관된 읽기 어려움 |

## 정리

- 동시성 제어는 여러 트랜잭션이 동시에 실행되어도 결과의 정합성을 유지하게 하는 메커니즘입니다.
- `Lock`은 충돌하는 접근을 직접 제어하는 가장 기본적인 수단입니다.
- `Deadlock`은 서로가 서로를 기다리는 순환 대기 상태이며, 일반적인 대기와는 다릅니다.
- `MVCC`는 읽기 일관성을 제공해 읽기와 쓰기 충돌을 줄이지만, 쓰기 충돌까지 모두 해결하지는 못합니다.
- 실무에서는 짧은 트랜잭션, 일관된 접근 순서, 적절한 인덱스, 재시도 전략이 동시성 문제를 줄이는 핵심입니다.
