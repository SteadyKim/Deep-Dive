# 프로세스 동기화

## 개요

여러 프로세스나 쓰레드가 동시에 실행될 때, 서로 독립적으로만 동작하는 것은 아닙니다.  
같은 데이터나 자원을 함께 사용하는 순간, **누가 먼저 접근하고 언제 수정하는지**를 제어해야 합니다.

이처럼 여러 실행 흐름이 공유 자원에 접근할 때 **실행 순서와 접근 타이밍을 올바르게 맞추는 것**이 `동기화(Synchronization)`입니다.  
동기화가 제대로 되지 않으면 데이터가 꼬이거나, 일부 작업이 영원히 기다리거나, 시스템 전체가 멈추는 문제가 생길 수 있습니다.

## 프로세스 동기화란 무엇인가

프로세스 동기화는 여러 실행 주체가 공유 자원에 접근할 때, **정합성과 일관성을 유지하도록 접근을 제어하는 것**입니다.  
여기서 실행 주체는 엄밀히는 프로세스일 수도 있고, 같은 프로세스 내부의 쓰레드일 수도 있습니다.

예를 들어 은행 계좌 잔액이 `100`일 때 두 작업이 동시에 각각 `30`, `50`을 출금한다고 가정해 보겠습니다.

- 작업 A는 `100`을 읽고 `70`으로 계산합니다.
- 작업 B도 `100`을 읽고 `50`으로 계산합니다.
- A가 먼저 `70`을 기록하고, B가 나중에 `50`을 기록합니다.

최종 결과는 `20`이어야 하지만 실제 값은 `50`이 됩니다.  
이런 문제는 여러 실행 흐름이 공유 데이터에 대한 접근 순서를 제대로 조정하지 못했기 때문에 발생합니다.

즉, 동기화의 핵심은 단순히 "동시에 실행하지 않게 막는 것"이 아니라, **공유 자원에 대한 접근을 의도한 규칙대로 직렬화하거나 조정하는 것**입니다.

## 왜 동기화가 필요한가

동기화가 필요한 이유는 여러 작업이 같은 자원을 함께 쓰기 때문입니다.

- 메모리 안의 공유 변수
- 파일
- 데이터베이스 연결
- 큐, 버퍼, 캐시
- 프린터, 디스크 같은 장치

이 자원들은 동시에 접근할 수는 있지만, **동시에 수정해도 항상 안전한 것은 아닙니다**.  
특히 읽기와 쓰기가 섞이거나, 여러 단계의 작업이 하나의 논리적 연산을 이루는 경우에는 접근 순서가 매우 중요합니다.

이때 동기화가 없으면 대표적으로 다음 문제가 생깁니다.

- `Race Condition`: 실행 순서에 따라 결과가 달라집니다.
- `Lost Update`: 먼저 한 갱신이 나중의 갱신에 덮어써집니다.
- `Deadlock`: 서로 자원을 기다리며 영원히 진행하지 못합니다.
- `Starvation`: 어떤 작업이 계속 기회를 얻지 못합니다.

## 1. 임계 구역

### 임계 구역이란 무엇인가

`임계 구역(Critical Section)`은 여러 실행 흐름이 **공유 자원에 접근하는 코드 구간**을 의미합니다.  
이 구간은 동시에 둘 이상이 들어가면 문제가 생길 수 있기 때문에 특별한 보호가 필요합니다.

예를 들어 다음과 같은 코드는 겉보기보다 위험합니다.

```text
count = count + 1
```

이 한 줄은 실제로는 보통 다음처럼 여러 단계로 나뉩니다.

1. 현재 `count` 값을 읽는다.
2. `1`을 더한다.
3. 다시 저장한다.

두 쓰레드가 이 과정을 동시에 수행하면 둘 다 같은 원래 값을 읽을 수 있기 때문에, 증가가 한 번만 반영되는 문제가 생길 수 있습니다.

즉, 임계 구역은 단순히 코드 길이의 문제가 아니라 **중간에 끼어들면 안 되는 작업 묶음**입니다.

### 임계 구역 문제의 조건

운영체제에서 임계 구역 문제를 제대로 해결했다고 보려면 보통 다음 조건을 만족해야 합니다.

- `Mutual Exclusion`: 한 번에 하나의 실행 흐름만 임계 구역에 들어가야 합니다.
- `Progress`: 아무도 임계 구역을 사용하지 않는다면, 들어가려는 작업 중 하나는 합리적인 시간 안에 선택되어야 합니다.
- `Bounded Waiting`: 어떤 작업도 무한정 기다리지 않아야 합니다.

즉, 단순히 막기만 해서는 안 되고, **안전하면서도 결국은 진행 가능해야** 합니다.

## 2. 뮤텍스

### 뮤텍스란 무엇인가

`뮤텍스(Mutex)`는 `Mutual Exclusion`의 줄임말로, 한 번에 하나의 실행 흐름만 공유 자원에 접근하게 만드는 가장 기본적인 동기화 도구입니다.

동작은 단순합니다.

1. 임계 구역에 들어가기 전에 `lock`을 획득합니다.
2. 이미 다른 실행 흐름이 lock을 가지고 있으면 기다립니다.
3. 작업이 끝나면 `unlock`으로 lock을 해제합니다.

즉, 뮤텍스는 "이 자원은 지금 누가 사용 중인가"를 관리하는 열쇠라고 볼 수 있습니다.

### 뮤텍스의 특징

- 소유 개념이 있습니다. 보통 lock을 획득한 주체가 직접 해제해야 합니다.
- 한 번에 하나만 들어가게 하므로 상호 배제에 적합합니다.
- 공유 데이터 보호처럼 범위가 명확한 임계 구역에 자주 사용됩니다.

예를 들어 계좌 잔액 갱신, 연결 리스트 수정, 전역 캐시 갱신처럼 **동시에 건드리면 안 되는 코드 블록**을 감쌀 때 자연스럽습니다.

### 뮤텍스의 주의점

뮤텍스를 쓴다고 모든 문제가 끝나는 것은 아닙니다.

- lock을 너무 오래 잡으면 성능이 나빠집니다.
- lock 획득 순서가 꼬이면 `Deadlock`이 생길 수 있습니다.
- 임계 구역이 너무 크면 병렬성이 크게 떨어집니다.

그래서 실무에서는 "필요한 최소 범위만 잠근다"는 원칙이 중요합니다.

## 3. 세마포어

### 세마포어란 무엇인가

`세마포어(Semaphore)`는 공유 자원에 접근할 수 있는 **허용 개수**를 정수 값으로 관리하는 동기화 도구입니다.

보통 두 연산으로 설명합니다.

- `wait(P)`: 세마포어 값을 감소시키고, 사용할 수 없으면 대기합니다.
- `signal(V)`: 세마포어 값을 증가시키고, 기다리던 작업이 있으면 깨웁니다.

즉, 세마포어는 "지금 몇 개까지 들어갈 수 있는가"를 표현하는 카운터 기반 제어 장치입니다.

### 이진 세마포어와 카운팅 세마포어

#### 이진 세마포어(Binary Semaphore)

값이 `0` 또는 `1`만 가능한 세마포어입니다.  
한 번에 하나만 들어가게 만들 수 있어서 겉으로는 뮤텍스와 비슷해 보입니다.

#### 카운팅 세마포어(Counting Semaphore)

값이 `2`, `3`, `N`처럼 여러 개를 가질 수 있는 세마포어입니다.  
즉, 동시에 접근 가능한 자원 수가 여러 개일 때 적합합니다.

예를 들어 DB 커넥션 풀에 연결이 `10`개 있다면, 세마포어 값을 `10`으로 두고 동시에 최대 `10`개의 작업만 사용하게 만들 수 있습니다.

### 세마포어와 뮤텍스의 차이

둘 다 동기화 도구이지만 목적과 의미가 완전히 같지는 않습니다.

| 구분 | 뮤텍스 | 세마포어 |
| --- | --- | --- |
| 핵심 목적 | 상호 배제 | 접근 가능 수 제어 |
| 값 | 잠김 / 해제 | 정수 카운트 |
| 소유 개념 | 보통 있음 | 보통 없음 |
| 적합한 상황 | 임계 구역 보호 | 자원 개수 제한, 실행 순서 조정 |

즉, 뮤텍스는 "한 번에 하나만", 세마포어는 "한 번에 몇 개까지"에 더 가깝습니다.

### 세마포어의 주의점

세마포어는 유연하지만 그만큼 실수하기 쉽습니다.

- `wait`와 `signal` 짝이 맞지 않으면 버그가 생깁니다.
- 누가 해제해야 하는지 명확하지 않아 코드 추적이 어려울 수 있습니다.
- 잘못 쓰면 상호 배제와 순서 제어가 뒤섞여 가독성이 나빠질 수 있습니다.

그래서 세마포어는 강력하지만, 단순한 상호 배제 용도라면 뮤텍스가 더 명확한 경우가 많습니다.

## 4. 모니터

### 모니터란 무엇인가

`모니터(Monitor)`는 공유 자원과 그 자원을 다루는 연산을 하나의 추상화 안에 묶고, **한 번에 하나의 실행 흐름만 내부 코드에 들어오도록 보장하는 고수준 동기화 기법**입니다.

쉽게 말하면, 뮤텍스나 세마포어를 개발자가 매번 직접 조합하는 대신 **언어나 런타임 차원에서 더 안전하게 감싼 구조**라고 볼 수 있습니다.

일반적으로 모니터는 다음 요소를 포함합니다.

- 공유 데이터
- 그 데이터를 다루는 메서드
- 내부 상호 배제
- 필요한 경우 `Condition Variable`

즉, "공유 자원"과 "동기화 규칙"을 분리하지 않고 하나의 관리 단위로 묶는 것이 핵심입니다.

### Condition Variable

모니터에서는 단순히 lock만 거는 것으로 끝나지 않고, 특정 조건이 만족될 때까지 기다렸다가 다시 깨우는 메커니즘이 함께 쓰입니다.  
이때 사용하는 것이 `Condition Variable`입니다.

대표적으로는 다음 패턴이 나옵니다.

- 버퍼가 비어 있으면 소비자는 기다립니다.
- 버퍼에 데이터가 들어오면 생산자가 소비자를 깨웁니다.

즉, 모니터는 단순한 상호 배제뿐 아니라 **조건이 만족될 때까지의 대기와 재개 흐름**까지 더 구조적으로 표현할 수 있습니다.

### 모니터의 장점

- 동기화 코드가 공유 자원과 함께 묶여 가독성이 좋습니다.
- lock 획득과 해제를 실수할 가능성이 줄어듭니다.
- 세마포어보다 의도가 더 잘 드러나는 경우가 많습니다.

### 모니터의 한계

- 언어나 런타임 지원 방식에 따라 동작 모델이 다를 수 있습니다.
- 내부 동작을 정확히 이해하지 않으면 `signal`, `wait`, 조건 검사 순서에서 실수가 생길 수 있습니다.

즉, 모니터는 더 고수준의 추상화이지만, 결국 내부에는 상호 배제와 조건 대기라는 동기화 문제가 그대로 존재합니다.

## 5. 언제 무엇을 쓰는가

실무에서는 동기화 도구를 이름으로 외우기보다, **문제 형태에 맞춰 고르는 것**이 중요합니다.

### 단순한 공유 변수 보호

공유 변수나 자료구조 일부를 보호하는 목적이라면 보통 `뮤텍스`가 가장 직관적입니다.  
의도가 명확하고, 누가 lock을 잡고 푸는지도 비교적 분명합니다.

### 자원 개수 제한

동시에 사용할 수 있는 자원이 여러 개라면 `세마포어`가 자연스럽습니다.  
예를 들어 커넥션 풀, 작업 슬롯, 생산자-소비자 버퍼의 빈 칸 개수 관리 같은 경우입니다.

### 구조적으로 안전한 동기화

공유 상태와 동기화 로직을 함께 묶고 싶다면 `모니터`가 더 적합합니다.  
특히 객체지향 언어나 런타임이 이를 잘 지원하면 유지보수성이 좋아집니다.

## 정리

- `프로세스 동기화`는 여러 실행 흐름이 공유 자원에 접근할 때 정합성과 일관성을 유지하도록 접근 순서를 제어하는 것입니다.
- `임계 구역`은 동시에 접근하면 문제가 생길 수 있는 공유 자원 접근 코드 구간입니다.
- 임계 구역 문제는 `Mutual Exclusion`, `Progress`, `Bounded Waiting` 조건을 만족하도록 해결해야 합니다.
- `뮤텍스`는 한 번에 하나만 임계 구역에 들어가게 만드는 상호 배제 도구입니다.
- `세마포어`는 정수 카운트를 기반으로 여러 자원의 접근 가능 개수를 제어할 수 있는 도구입니다.
- `모니터`는 공유 자원과 동기화 규칙을 하나의 추상화로 묶어 더 구조적으로 관리하는 고수준 기법입니다.

결국 동기화의 본질은 "같은 자원을 여러 실행 흐름이 함께 사용할 때, 어떤 규칙으로 접근을 조정할 것인가"에 있습니다.  
그리고 `임계 구역`, `뮤텍스`, `세마포어`, `모니터`는 그 문제를 서로 다른 수준에서 해결하기 위한 대표적인 도구들입니다.
