# 가상 메모리

## 개요

프로그램이 실행되려면 코드와 데이터가 메모리에 올라와 있어야 합니다.  
그런데 현실에서는 실행하고 싶은 프로그램의 크기 합이 물리 메모리를 초과하거나, 여러 프로그램이 동시에 메모리를 차지하려 할 때 충돌이 생깁니다.

운영체제는 이 문제를 `가상 메모리(Virtual Memory)` 기법으로 해결합니다.  
가상 메모리는 프로세스에게 실제 물리 메모리보다 훨씬 큰 메모리 공간이 있는 것처럼 보이게 하는 추상화 기법입니다.

이 기법 덕분에 프로세스는 물리 메모리의 한계를 신경 쓰지 않고 자신만의 주소 공간을 사용할 수 있고,  
운영체제는 여러 프로세스를 안전하게 격리하면서 동시에 실행할 수 있게 됩니다.

## 가상 메모리란 무엇인가

가상 메모리는 프로세스가 사용하는 `가상 주소(Virtual Address)`와 실제 하드웨어인 `물리 주소(Physical Address)`를 분리하는 개념입니다.

프로세스는 자신이 `0번지부터 시작하는 연속적인 큰 메모리 공간`을 가진 것처럼 동작합니다.  
하지만 실제로는 그 주소들이 물리 메모리의 어딘가에 분산되어 있거나, 아직 메모리에 올라오지 않고 디스크에 있을 수 있습니다.

이 변환을 담당하는 하드웨어가 `MMU(Memory Management Unit)`이고,  
운영체제가 관리하는 변환 정보가 `페이지 테이블(Page Table)`입니다.

## 1. 페이징(Paging)

### 페이징이란 무엇인가

가상 메모리를 구현하는 대표적인 방법이 `페이징(Paging)`입니다.  
페이징은 가상 주소 공간과 물리 메모리를 모두 **고정 크기의 블록으로 분할**하는 방식입니다.

- 가상 주소 공간을 나눈 단위를 `페이지(Page)`라고 합니다.
- 물리 메모리를 나눈 단위를 `프레임(Frame)`이라고 합니다.
- 페이지와 프레임의 크기는 동일하며, 보통 4KB 단위입니다.

### 페이지 테이블

운영체제는 각 프로세스마다 `페이지 테이블`을 유지합니다.  
페이지 테이블은 가상 페이지 번호를 물리 프레임 번호로 대응시키는 매핑 정보입니다.

```
가상 주소 = [페이지 번호 | 페이지 내 오프셋]
                ↓ (페이지 테이블 조회)
물리 주소 = [프레임 번호 | 페이지 내 오프셋]
```

CPU가 가상 주소로 메모리를 접근할 때, MMU는 페이지 테이블을 참조해 물리 주소로 변환한 뒤 실제 메모리에 접근합니다.

### TLB(Translation Lookaside Buffer)

페이지 테이블은 메모리에 저장되어 있기 때문에, 매번 조회하면 메모리 접근이 두 번 발생합니다.  
이 오버헤드를 줄이기 위해 하드웨어 캐시인 `TLB`가 사용됩니다.

TLB는 최근에 사용된 페이지-프레임 매핑을 캐싱합니다.

- TLB에 매핑이 있으면(`TLB Hit`): 빠르게 주소 변환
- TLB에 없으면(`TLB Miss`): 페이지 테이블을 조회하고 TLB를 갱신

실제 프로그램은 지역성(Locality)에 의해 같은 페이지를 반복해서 접근하는 경향이 있기 때문에, TLB 히트율은 일반적으로 매우 높습니다.

## 2. 요구 페이징(Demand Paging)

### 왜 요구 페이징이 필요한가

프로그램을 실행할 때 전체 코드와 데이터를 한꺼번에 메모리에 올리면 메모리 낭비가 심합니다.  
실제로는 프로그램의 모든 부분이 항상 필요하지 않고, 자주 쓰이는 코드 경로와 데이터는 일부에 집중됩니다.

`요구 페이징(Demand Paging)`은 페이지가 **실제로 필요해질 때만** 메모리에 올리는 방식입니다.  
프로그램 시작 시에는 아무 페이지도 메모리에 없을 수 있고, 접근이 발생할 때마다 필요한 페이지를 적재합니다.

### 페이지 폴트(Page Fault)

프로세스가 접근하려는 가상 페이지가 현재 물리 메모리에 없을 때 `페이지 폴트(Page Fault)`가 발생합니다.

페이지 폴트가 발생하면 운영체제가 개입하여 다음 절차를 수행합니다.

1. CPU가 페이지 폴트 예외를 발생시킵니다.
2. 운영체제가 해당 가상 주소가 유효한지 확인합니다.
3. 디스크(스왑 영역 또는 파일)에서 해당 페이지를 찾습니다.
4. 비어 있는 물리 프레임을 확보합니다. 빈 프레임이 없으면 교체 대상을 선정합니다.
5. 디스크에서 페이지를 읽어 프레임에 올립니다.
6. 페이지 테이블을 갱신합니다.
7. 페이지 폴트를 유발한 명령어를 재실행합니다.

페이지 폴트는 디스크 I/O를 수반하므로 비용이 매우 큽니다.  
따라서 얼마나 페이지 폴트를 줄이느냐가 가상 메모리 성능의 핵심입니다.

## 3. 페이지 교체 알고리즘

물리 메모리가 꽉 찼을 때 어떤 페이지를 내보낼지 결정하는 것이 `페이지 교체 알고리즘`입니다.  
어떤 페이지를 교체하느냐에 따라 페이지 폴트 횟수가 달라지므로, 교체 정책 선택이 성능에 직접 영향을 줍니다.

### OPT(Optimal Page Replacement)

앞으로 **가장 오랫동안 사용되지 않을 페이지**를 교체하는 이론적으로 최적인 알고리즘입니다.

- 페이지 폴트를 최소화합니다.
- 미래 참조 순서를 미리 알아야 하기 때문에 실제 구현은 불가능합니다.
- 다른 알고리즘의 성능을 평가하는 기준으로 활용됩니다.

### FIFO(First-In First-Out)

가장 **먼저 메모리에 올라온 페이지**를 먼저 교체하는 방식입니다.

- 구현이 단순합니다.
- 오래된 페이지가 아직 자주 쓰일 수 있는 경우 불필요한 교체가 발생합니다.
- 프레임 수를 늘렸는데 오히려 페이지 폴트가 증가하는 `Belady의 역설`이 발생할 수 있습니다.

### LRU(Least Recently Used)

**가장 오랫동안 사용되지 않은 페이지**를 교체하는 방식입니다.

- 최근에 사용된 페이지는 앞으로도 사용될 가능성이 높다는 `시간 지역성(Temporal Locality)` 원리에 기반합니다.
- OPT에 근접한 성능을 보여 실무에서 가장 널리 쓰이는 기준입니다.
- 매 접근마다 타임스탬프를 기록하거나 연결 리스트를 갱신해야 해서 구현 비용이 있습니다.
- 하드웨어 지원이 없으면 완전한 구현이 어렵기 때문에, 실제 OS에서는 LRU를 근사한 `Clock 알고리즘` 같은 방식이 주로 사용됩니다.

### Clock 알고리즘(LRU 근사)

페이지마다 `참조 비트(Reference Bit)`를 두고, 시계 바늘처럼 순환하며 교체 대상을 찾는 방식입니다.

- 시계 바늘이 가리키는 페이지의 참조 비트가 1이면 0으로 바꾸고 넘어갑니다.
- 참조 비트가 0인 페이지를 만나면 그 페이지를 교체합니다.

완전한 LRU보다 정확도는 낮지만, 하드웨어 비용이 적고 구현이 단순해서 Linux 같은 실제 운영체제에서 변형된 형태로 사용됩니다.

## 4. 스래싱(Thrashing)

### 스래싱이란 무엇인가

`스래싱(Thrashing)`은 프로세스가 실행보다 **페이지 교체에 더 많은 시간을 소비하는 상태**입니다.

메모리에 올라와 있는 프로세스 수가 너무 많아지면, 각 프로세스에게 할당되는 물리 프레임 수가 부족해집니다.  
그러면 프로세스들이 계속 페이지 폴트를 일으키고, 운영체제는 디스크 I/O 처리에 바빠지며, 정작 CPU는 놀게 됩니다.

CPU 이용률이 떨어지면 운영체제는 더 많은 프로세스를 올려서 CPU를 바쁘게 하려 하고,  
그 결과 메모리 경쟁이 더 심해져 스래싱이 가속됩니다.

### 스래싱을 막는 방법

#### 워킹 셋(Working Set) 모델

프로세스가 특정 시간 내에 실제로 참조하는 페이지 집합을 `워킹 셋`이라고 합니다.  
운영체제는 각 프로세스의 워킹 셋 크기를 추적하고, 워킹 셋 전체를 메모리에 유지할 수 있을 때만 프로세스를 실행합니다.

즉, 메모리가 부족하면 일부 프로세스를 일시 중단(swap out)하여 실행 중인 프로세스들이 각자의 워킹 셋을 유지할 수 있게 합니다.

#### 페이지 폴트 빈도(Page Fault Rate) 제어

프로세스별 페이지 폴트 발생 빈도를 모니터링하는 방식입니다.

- 폴트 빈도가 너무 높으면: 해당 프로세스에 더 많은 프레임을 할당합니다.
- 폴트 빈도가 너무 낮으면: 해당 프로세스의 프레임을 줄입니다.

이 방식은 각 프로세스의 상태를 보고 동적으로 자원을 조정하므로 스래싱을 효과적으로 억제할 수 있습니다.

## 5. 스왑(Swap)

물리 메모리가 부족하면 운영체제는 사용하지 않는 페이지를 디스크의 `스왑 공간(Swap Space)`으로 내보냅니다.  
나중에 해당 페이지가 다시 필요해지면 디스크에서 읽어 메모리에 올립니다.

스왑은 메모리 부족 상황을 완화해 주지만, 디스크 I/O 속도가 메모리 속도보다 수십만 배 느리기 때문에  
스왑이 자주 발생하면 전체 시스템 성능이 크게 저하됩니다.

SSD를 스왑 장치로 쓰면 HDD보다는 빠르지만, 스왑 자체를 최소화하도록 메모리를 충분히 확보하는 것이 근본적인 해결책입니다.

## 6. 가상 메모리가 제공하는 이점

가상 메모리는 단순히 메모리 용량 문제를 넘어 다음과 같은 이점을 제공합니다.

| 이점 | 설명 |
| --- | --- |
| 프로세스 격리 | 각 프로세스는 독립된 가상 주소 공간을 가지므로 서로의 메모리를 침범할 수 없습니다. |
| 메모리 효율 | 실제로 필요한 페이지만 물리 메모리에 올려 메모리를 효율적으로 사용할 수 있습니다. |
| 대용량 프로그램 실행 | 물리 메모리보다 큰 프로그램도 필요한 부분만 올리면서 실행할 수 있습니다. |
| 메모리 공유 | 여러 프로세스가 같은 라이브러리 코드를 물리 메모리에 한 번만 올려 공유할 수 있습니다. |
| Copy-on-Write | `fork()` 시 페이지를 즉시 복사하지 않고, 실제 쓰기가 일어날 때 복사함으로써 비용을 줄입니다. |

## 정리

- `가상 메모리`는 프로세스에게 물리 메모리보다 큰 독립적인 주소 공간을 제공하는 추상화 기법입니다.
- `페이징`은 메모리를 고정 크기 페이지로 나눠 관리하며, `페이지 테이블`이 가상 주소를 물리 주소로 변환합니다.
- `TLB`는 페이지 테이블 조회 비용을 줄이는 하드웨어 캐시입니다.
- `요구 페이징`은 페이지를 실제로 접근할 때만 메모리에 올리며, 접근 시 페이지가 없으면 `페이지 폴트`가 발생합니다.
- 페이지 교체 알고리즘은 `OPT`, `FIFO`, `LRU`, `Clock` 등이 있으며, 실제 OS에서는 LRU를 근사한 방식이 주로 사용됩니다.
- `스래싱`은 메모리 과부하로 페이지 교체만 반복되는 상태이며, 워킹 셋 모델이나 폴트 빈도 제어로 완화할 수 있습니다.

결국 가상 메모리의 핵심은 **물리 메모리의 한계를 추상화로 숨기고, 프로세스 간 격리와 효율적인 메모리 사용을 동시에 달성하는 것**입니다.  
이 기법이 없으면 현대 운영체제가 여러 프로그램을 안정적으로 동시에 실행하는 것 자체가 어렵습니다.
