# 세그멘테이션과 단편화

## 개요

프로세스에게 메모리를 나눠 주는 방식은 크게 두 흐름으로 나뉩니다.  
하나는 메모리를 **고정 크기 블록으로 자르는** 페이징이고, 다른 하나는 **논리적 의미 단위로 자르는** 세그멘테이션입니다.

`가상 메모리` 문서가 페이징을 중심으로 다뤘다면, 이 문서는 그 반대편에 있는 세그멘테이션과,  
메모리를 어떤 단위로 나누든 필연적으로 따라오는 `단편화(Fragmentation)` 문제를 다룹니다.

단편화는 "메모리는 충분히 남아 있는데 정작 쓸 수 없는" 상황을 만드는 근본 원인이며,  
어떤 메모리 관리 기법을 선택하느냐에 따라 어떤 종류의 단편화가 생기는지가 갈립니다.

## 1. 연속 할당과 단편화의 시작

### 연속 메모리 할당

초기의 단순한 방식은 프로세스마다 물리 메모리의 **연속된 한 덩어리**를 통째로 할당하는 것입니다.  
프로세스가 올라오고 종료되기를 반복하면 메모리 곳곳에 빈 공간(hole)이 생깁니다.

이때 빈 공간 중 어디에 새 프로세스를 넣을지 결정하는 방식이 있습니다.

| 방식 | 설명 | 특징 |
| --- | --- | --- |
| First Fit | 요청 크기보다 큰 첫 번째 빈 공간에 할당 | 탐색이 빠름 |
| Best Fit | 요청 크기와 가장 근접한 빈 공간에 할당 | 작은 자투리가 많이 남음 |
| Worst Fit | 가장 큰 빈 공간에 할당 | 남는 조각을 크게 유지하려는 시도 |

Best Fit은 직관적으로 좋아 보이지만, 딱 맞는 공간을 찾다 보니 오히려 **너무 작아서 아무도 못 쓰는 자투리**를 양산하는 경향이 있습니다.

### 외부 단편화(External Fragmentation)

`외부 단편화`는 **전체 빈 메모리 총량은 충분한데, 연속되지 않아서** 요청을 못 들어주는 상황입니다.

```
[프로세스A][빈 20KB][프로세스B][빈 30KB][프로세스C][빈 10KB]

→ 빈 공간 합은 60KB지만, 50KB짜리 프로세스는 올릴 수 없다
  (연속된 50KB 공간이 없기 때문)
```

연속 할당 방식의 근본적인 한계이며, 이를 해결하려는 시도에서 페이징과 세그멘테이션이 출발합니다.

### 내부 단편화(Internal Fragmentation)

`내부 단편화`는 **할당해 준 공간이 실제로 필요한 양보다 커서** 그 내부가 남는 상황입니다.

- 페이징처럼 고정 크기 블록으로 나눠 줄 때 주로 발생합니다.
- 예: 페이지 크기가 4KB인데 실제로 필요한 데이터가 4.1KB라면 페이지 2개(8KB)를 할당받고, 뒤쪽 약 3.9KB가 그대로 낭비됩니다.

| 구분 | 발생 원인 | 주로 발생하는 기법 |
| --- | --- | --- |
| 외부 단편화 | 빈 공간이 흩어져 연속 공간 부족 | 세그멘테이션, 연속 할당 |
| 내부 단편화 | 할당 단위가 실제 필요량보다 큼 | 페이징 |

## 2. 세그멘테이션(Segmentation)

### 세그멘테이션이란 무엇인가

`세그멘테이션`은 메모리를 **프로그램의 논리적 의미 단위(세그먼트)**로 나누는 방식입니다.  
페이징이 크기만 보고 기계적으로 자른다면, 세그멘테이션은 프로그래머가 인식하는 단위를 그대로 반영합니다.

- 코드(Text) 세그먼트
- 데이터(Data) 세그먼트
- 힙(Heap) 세그먼트
- 스택(Stack) 세그먼트

각 세그먼트는 **서로 다른 크기**를 가질 수 있습니다.

### 세그먼트 테이블

세그먼트마다 크기가 다르기 때문에, 주소 변환에는 시작 위치와 길이가 모두 필요합니다.  
운영체제는 이를 `세그먼트 테이블(Segment Table)`로 관리합니다.

```
논리 주소 = [세그먼트 번호(s) | 오프셋(d)]
                 ↓ (세그먼트 테이블 조회)
세그먼트 테이블[s] = { base(시작 물리 주소), limit(길이) }

if (d < limit)  물리 주소 = base + d
else            트랩 발생 (세그먼트 경계 침범)
```

`limit` 검사는 단순한 성능 장치가 아니라 **보호(protection)** 기능입니다.  
세그먼트 경계를 넘는 접근을 하드웨어가 즉시 잡아내므로, 코드 세그먼트에 쓰기를 시도하거나 남의 세그먼트를 침범하는 접근을 차단할 수 있습니다.

### 세그멘테이션의 장점

- **논리적 단위 관리**: 코드/데이터/스택이 분리되어 있어 보호와 공유가 자연스럽습니다.
- **공유의 용이함**: 공유 라이브러리 코드를 하나의 세그먼트로 만들어 여러 프로세스가 참조할 수 있습니다.
- **의미 기반 보호**: 세그먼트 단위로 읽기/쓰기/실행 권한을 부여할 수 있습니다.

### 세그멘테이션의 단점

세그먼트는 크기가 제각각이라, 메모리에 올렸다 내렸다를 반복하면 **외부 단편화**가 발생합니다.  
이는 앞서 본 연속 할당의 문제와 동일한 성격이며, 세그멘테이션의 가장 큰 약점입니다.

### 왜 세그멘테이션에는 생기고 페이징에는 없는가

같은 상황(100KB 메모리, A:30KB·B:20KB·C:40KB를 올린 뒤 A와 B가 종료, 이후 55KB 요청)을 두 방식으로 비교해 보면 차이가 분명해집니다.

```
세그멘테이션:
  [빈 30KB][빈 20KB][C:40KB][빈 10KB]
  빈 공간 총합 60KB ≥ 55KB 인데도,
  연속된 최대 공간은 50KB → 55KB 못 넣음 → 외부 단편화

페이징 (프레임 10KB로 미리 분할):
  [빈][빈][빈][빈][빈][C][C][C][C][빈]
  55KB=6페이지 요청 → 흩어진 빈 프레임 6칸에 나눠 담음 → 성공
```

두 방식이 갈리는 이유는 두 가지입니다.

| 원인 | 세그멘테이션 | 페이징 |
| --- | --- | --- |
| 조각 크기 | 제각각이라 구멍과 크기가 안 맞음 | 프레임 크기가 모두 같아 어떤 페이지든 들어맞음 |
| 배치 제약 | 연속된 한 덩어리로만 할당 가능 | 흩어진 프레임에 분산 배치 가능 |

즉 페이징은 **"크기 불일치"와 "연속 제약"을 동시에 없애** 외부 단편화를 원천적으로 제거합니다.  
대신 요청 크기가 페이지 단위로 딱 떨어지지 않을 때 마지막 페이지에서 **내부 단편화**(최대 1페이지 미만)를 감수합니다.

## 3. 페이징 vs 세그멘테이션

| 항목 | 페이징 | 세그멘테이션 |
| --- | --- | --- |
| 분할 기준 | 고정 크기(물리적) | 논리적 의미 단위(가변 크기) |
| 크기 | 모든 페이지 동일 | 세그먼트마다 다름 |
| 단편화 | 내부 단편화 | 외부 단편화 |
| 주소 구성 | 페이지 번호 + 오프셋 | 세그먼트 번호 + 오프셋 |
| 보호/공유 | 페이지 단위 (다소 부자연스러움) | 의미 단위 (자연스러움) |
| 관리 테이블 | 페이지 테이블 | 세그먼트 테이블(base + limit) |

핵심 트레이드오프는 이렇습니다.

- 페이징은 **외부 단편화를 없애는 대신 내부 단편화와 논리적 부자연스러움**을 감수합니다.
- 세그멘테이션은 **논리적으로 자연스러운 대신 외부 단편화**를 감수합니다.

## 4. 세그멘테이션-페이징 혼합 기법

두 방식의 장점만 취하기 위해 실제 시스템(대표적으로 x86)은 둘을 결합합니다.

핵심 아이디어는 **"세그먼트로 논리적으로 나누되, 각 세그먼트 내부는 다시 페이지로 나눈다"**는 것입니다.

```
논리 주소 = [세그먼트 번호 | 페이지 번호 | 오프셋]
             ↓ 세그먼트 테이블 → 해당 세그먼트의 페이지 테이블
             ↓ 페이지 테이블 → 프레임 번호
물리 주소 = [프레임 번호 | 오프셋]
```

- 세그먼트 단위로 **보호와 공유**의 이점을 유지합니다.
- 각 세그먼트를 페이지로 관리하므로 **외부 단편화가 사라집니다**.
- 대신 주소 변환 단계가 늘어나 구조가 복잡해집니다.

> 참고: 현대 x86-64와 리눅스는 세그멘테이션을 사실상 무력화(모든 세그먼트의 base를 0으로)하고 페이징 중심으로 동작합니다.  
> 세그먼트 레지스터는 남아 있지만 메모리 분할보다는 특수 용도(스레드 로컬 저장소 등)로만 제한적으로 쓰입니다.

## 5. 외부 단편화를 줄이는 방법

세그멘테이션이나 연속 할당에서 외부 단편화를 완화하는 대표적 방법이 있습니다.

### 압축(Compaction)

흩어진 프로세스들을 메모리 한쪽으로 몰아 빈 공간을 하나로 합치는 방식입니다.

- 빈 공간을 연속된 큰 덩어리로 만들 수 있습니다.
- 하지만 실행 중인 프로세스를 물리적으로 이동시켜야 하므로 비용이 크고, 이동 중에는 시스템을 멈춰야 할 수 있습니다.

### 페이징 도입

가장 근본적인 해결책은 애초에 **고정 크기 페이징**을 사용해 외부 단편화 자체를 없애는 것입니다.  
현대 운영체제가 페이징을 기본으로 채택한 이유가 바로 여기에 있습니다.

## 정리

- `외부 단편화`는 빈 공간이 흩어져 연속 공간이 부족한 문제이고, `내부 단편화`는 할당 단위가 필요량보다 커서 내부가 남는 문제입니다.
- `세그멘테이션`은 메모리를 논리적 의미 단위(코드/데이터/힙/스택)로 나누며, `세그먼트 테이블`의 base와 limit으로 주소 변환과 보호를 수행합니다.
- 세그멘테이션은 보호·공유에 유리하지만 크기가 가변적이라 **외부 단편화**를 겪습니다.
- `페이징`은 내부 단편화를, `세그멘테이션`은 외부 단편화를 갖는다는 것이 두 기법의 핵심 대비입니다.
- 실제 시스템은 둘을 결합한 **세그멘테이션-페이징 혼합 기법**으로 각자의 장점을 취하며, 현대 x86-64는 페이징 중심으로 동작합니다.

결국 메모리 관리의 본질은 **어떤 단위로 나눌 것인가**의 선택이며, 그 선택이 곧 어떤 단편화를 감수할지를 결정합니다.  
페이징이 표준이 된 이유도 "외부 단편화를 없애는 것이 실무에서 더 중요했기 때문"이라는 트레이드오프의 결과입니다.
