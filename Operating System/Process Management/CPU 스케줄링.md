# CPU 스케줄링

## 개요

CPU는 한순간에 제한된 수의 작업만 실행할 수 있기 때문에, 운영체제는 여러 프로세스와 쓰레드 중에서 **지금 누구에게 CPU를 줄지** 결정해야 합니다.  
이 결정을 담당하는 것이 `CPU 스케줄링`입니다.

CPU 스케줄링은 단순히 실행 순서를 정하는 문제가 아니라, **응답 시간**, **처리량**, **공정성**, **기아 현상 방지** 같은 시스템 특성을 좌우하는 핵심 메커니즘입니다.  
어떤 스케줄링 정책을 선택하느냐에 따라 사용자 체감 성능과 시스템 전체 효율이 크게 달라질 수 있습니다.

## CPU 스케줄링이란 무엇인가

CPU 스케줄링은 준비 상태(Ready State)에 있는 여러 작업 중에서, 어떤 작업을 다음에 실행할지 선택하는 과정입니다.  
운영체제는 스케줄러를 통해 이 결정을 수행하고, 선택된 작업에 CPU를 할당합니다.

이 과정은 보통 다음 흐름으로 이해할 수 있습니다.

1. 여러 프로세스나 쓰레드가 `Ready Queue`에서 대기합니다.
2. 스케줄러가 정책에 따라 다음 실행 대상을 고릅니다.
3. 디스패처가 실제로 CPU를 넘기고 실행을 시작합니다.
4. 실행 중인 작업이 종료되거나, I/O를 기다리거나, 할당 시간을 모두 쓰면 다시 스케줄링이 일어납니다.

즉, CPU 스케줄링은 "누가 먼저 실행되는가"만이 아니라, **얼마나 오래 실행되는가**, **언제 뺏을 수 있는가**, **어떤 기준으로 우선순위를 둘 것인가**까지 포함하는 개념입니다.

## CPU 스케줄링의 목표

운영체제는 보통 다음 목표 사이에서 균형을 잡으려 합니다.

- `CPU Utilization`: CPU가 놀지 않고 최대한 바쁘게 일하게 합니다.
- `Throughput`: 단위 시간당 더 많은 작업을 처리하게 합니다.
- `Turnaround Time`: 작업이 시작부터 종료까지 걸리는 시간을 줄입니다.
- `Waiting Time`: Ready Queue에서 기다리는 시간을 줄입니다.
- `Response Time`: 사용자가 요청한 뒤 첫 응답을 받기까지 시간을 줄입니다.
- `Fairness`: 특정 작업만 지나치게 우대하거나 배제하지 않도록 합니다.

문제는 이 목표들이 항상 동시에 최적화되지는 않는다는 점입니다.  
예를 들어 짧은 작업에 유리한 정책은 평균 응답 시간을 줄일 수 있지만, 긴 작업은 계속 뒤로 밀려 기아 현상이 생길 수 있습니다.

## 선점형과 비선점형

CPU 스케줄링은 크게 `비선점형(Non-Preemptive)`과 `선점형(Preemptive)`으로 나눌 수 있습니다.

### 비선점형 스케줄링

비선점형은 한 작업이 CPU를 잡으면, 스스로 종료하거나 I/O 대기 상태로 빠질 때까지 CPU를 계속 사용합니다.

- 장점: 구현이 단순하고 문맥 교환 비용이 적습니다.
- 단점: 긴 작업이 CPU를 오래 점유하면 뒤에 있는 짧은 작업들이 오래 기다릴 수 있습니다.

### 선점형 스케줄링

선점형은 운영체제가 실행 중인 작업의 CPU를 강제로 회수하고, 다른 작업에 넘길 수 있습니다.

- 장점: 응답성이 좋아지고, 인터랙티브한 작업을 더 빠르게 처리할 수 있습니다.
- 단점: 문맥 교환이 자주 발생해 오버헤드가 커질 수 있습니다.

현대 운영체제는 보통 응답성과 공정성을 위해 선점형 스케줄링을 기본으로 사용합니다.

## 1. 대표적인 CPU 스케줄링 알고리즘

### FCFS(First Come, First Served)

가장 먼저 도착한 작업부터 순서대로 실행하는 방식입니다.

- 장점: 단순하고 구현이 쉽습니다.
- 단점: 앞에 긴 작업이 오면 뒤의 짧은 작업들이 모두 기다리는 `Convoy Effect`가 발생할 수 있습니다.

예를 들어 실행 시간이 긴 배치 작업 하나 앞에 들어오면, 짧은 요청 여러 개가 줄줄이 지연될 수 있습니다.  
그래서 평균 대기 시간이 나빠질 가능성이 큽니다.

### SJF(Shortest Job First)

실행 시간이 가장 짧은 작업을 먼저 실행하는 방식입니다.  
이론적으로는 평균 대기 시간을 최소화하는 데 유리합니다.

- 장점: 평균 대기 시간 측면에서 효율적입니다.
- 단점: 다음 작업의 실행 시간을 정확히 알아야 하며, 긴 작업은 계속 뒤로 밀릴 수 있습니다.

실제 시스템에서는 미래 실행 시간을 정확히 알 수 없기 때문에, 완전한 형태로 쓰기보다는 과거 패턴을 기반으로 예측하는 방식으로 응용됩니다.

### SRTF(Shortest Remaining Time First)

`SJF`의 선점형 버전입니다.  
새로 들어온 작업의 남은 실행 시간이 현재 작업보다 더 짧으면 CPU를 빼앗아 실행합니다.

- 장점: 짧은 작업에 대한 응답성이 매우 좋습니다.
- 단점: 문맥 교환이 많아질 수 있고, 긴 작업의 기아 가능성이 있습니다.

### Round Robin

각 작업에 동일한 `Time Quantum`을 주고, 할당 시간이 끝나면 다음 작업으로 넘기는 방식입니다.

- 장점: 공정성이 좋고, 인터랙티브한 시스템에 적합합니다.
- 단점: `Time Quantum`을 너무 짧게 잡으면 문맥 교환 비용이 커지고, 너무 길게 잡으면 `FCFS`처럼 동작합니다.

즉, `Round Robin`의 핵심은 정책 자체보다도 **적절한 Time Quantum 선택**에 있습니다.

### Priority Scheduling

우선순위가 높은 작업을 먼저 실행하는 방식입니다.  
우선순위는 정적일 수도 있고, 실행 중 동적으로 바뀔 수도 있습니다.

- 장점: 중요한 작업을 먼저 처리할 수 있습니다.
- 단점: 우선순위가 낮은 작업이 계속 밀리는 `Starvation`이 발생할 수 있습니다.

이 문제를 완화하기 위해 오래 기다린 작업의 우선순위를 점차 높이는 `Aging` 기법을 함께 사용하기도 합니다.

### Multi-Level Queue

작업을 성격에 따라 여러 큐로 나누고, 각 큐마다 다른 스케줄링 정책을 적용하는 방식입니다.

예를 들어 다음처럼 나눌 수 있습니다.

- 시스템 작업 큐
- 인터랙티브 작업 큐
- 배치 작업 큐

각 큐는 `Round Robin`, `FCFS` 같은 다른 정책을 가질 수 있고, 큐 사이에도 우선순위를 둘 수 있습니다.  
대신 한 번 큐가 나뉘면 이동이 제한적이라 유연성이 떨어질 수 있습니다.

### MLFQ(Multi-Level Feedback Queue)

`Multi-Level Queue`를 더 유연하게 만든 방식입니다.  
작업의 실행 패턴에 따라 큐를 이동시키면서 우선순위를 조정합니다.

일반적으로는 다음과 같이 동작합니다.

- 처음 들어온 작업은 높은 우선순위 큐에서 시작합니다.
- CPU를 오래 쓰면 낮은 우선순위 큐로 내려갑니다.
- 짧게 자주 끝나는 인터랙티브 작업은 높은 우선순위를 유지합니다.

이 방식은 응답성과 처리량 사이의 균형을 잘 맞출 수 있어 실무적인 가치가 높습니다.  
다만 규칙이 복잡하고, 잘못 튜닝하면 특정 유형의 작업이 불리해질 수 있습니다.

## 2. 문맥 교환과 스케줄링 비용

CPU 스케줄링이 자주 일어나면 시스템이 더 공정하고 민감하게 반응할 수 있지만, 그만큼 `Context Switch` 비용도 늘어납니다.

문맥 교환이 일어나면 운영체제는 현재 작업의 레지스터 상태, 프로그램 카운터, 스택 정보 등을 저장하고 다음 작업의 상태를 복원해야 합니다.  
이 과정은 실제 사용자 작업을 수행하는 시간이 아니라, 스케줄링을 위한 관리 비용입니다.

즉, 스케줄링은 무조건 자주 한다고 좋은 것이 아닙니다.

- 너무 드물면 응답성이 나빠집니다.
- 너무 잦으면 오버헤드가 커집니다.

결국 스케줄링 정책은 공정성과 성능, 오버헤드 사이에서 균형을 잡는 문제입니다.

## 3. 실무 관점에서 중요한 포인트

실무에서 CPU 스케줄링을 공부할 때는 알고리즘 이름만 외우는 것보다, **어떤 상황에서 어떤 문제가 발생하는지**를 함께 이해하는 것이 중요합니다.

### 인터랙티브 시스템

사용자 입력에 빨리 반응해야 하는 데스크톱 환경이나 웹 서버는 `Response Time`이 중요합니다.  
이 경우 선점형 스케줄링과 짧은 작업 우대 정책이 유리합니다.

### 배치 시스템

대량 작업을 한꺼번에 처리하는 시스템은 개별 응답 시간보다 `Throughput`과 전체 완료 시간이 더 중요할 수 있습니다.  
이 경우 너무 잦은 선점보다 안정적인 처리량이 우선될 수 있습니다.

### 기아 현상과 공정성

우선순위 기반 정책이나 짧은 작업 우선 정책은 성능상 이점이 있지만, 특정 작업이 계속 밀릴 수 있습니다.  
그래서 현실 시스템은 순수한 알고리즘 하나만 쓰기보다 `Aging`, 동적 우선순위 조정, 피드백 큐 같은 보완 장치를 함께 둡니다.

### 멀티코어 환경

현대 시스템은 CPU가 하나가 아니라 여러 코어를 가집니다.  
그래서 실제 운영체제는 단순히 "다음 작업 하나"를 고르는 수준을 넘어서, **어떤 코어에 배치할지**, **캐시 지역성을 어떻게 유지할지**, **부하를 어떻게 분산할지**까지 고려합니다.

즉, 교과서의 기본 스케줄링 알고리즘은 출발점이고, 실제 운영체제는 그 위에 훨씬 더 많은 정책을 덧붙여 사용합니다.

## 4. 면접에서 자주 나오는 포인트

- `선점형`과 `비선점형`의 차이를 설명할 수 있어야 합니다.
- `Round Robin`에서 `Time Quantum`이 너무 크거나 너무 작을 때 어떤 문제가 생기는지 설명할 수 있어야 합니다.
- `SJF`가 평균 대기 시간에 유리한 이유와, 왜 실제 구현이 어려운지 설명할 수 있어야 합니다.
- `Priority Scheduling`의 `Starvation` 문제와 이를 완화하는 `Aging`을 연결해서 말할 수 있어야 합니다.
- `MLFQ`가 왜 현대 운영체제에서 자주 언급되는지, 인터랙티브 작업과 CPU-Bound 작업을 어떻게 다르게 다루는지 설명할 수 있으면 좋습니다.

## 정리

- `CPU 스케줄링`은 Ready Queue의 여러 작업 중 어떤 작업에 CPU를 할당할지 결정하는 과정입니다.
- 핵심 목표는 `CPU Utilization`, `Throughput`, `Turnaround Time`, `Waiting Time`, `Response Time`, `Fairness` 사이에서 균형을 잡는 것입니다.
- 스케줄링은 `선점형`과 `비선점형`으로 나뉘며, 현대 운영체제는 주로 응답성을 위해 선점형 방식을 사용합니다.
- 대표 알고리즘으로는 `FCFS`, `SJF`, `SRTF`, `Round Robin`, `Priority Scheduling`, `MLQ`, `MLFQ`가 있습니다.
- 실제 시스템에서는 알고리즘 자체보다도 기아 현상 방지, 문맥 교환 비용, 멀티코어 부하 분산 같은 현실적인 요소가 함께 중요합니다.
