# ACID

## 개요

ACID는 데이터베이스 트랜잭션이 갖춰야 할 핵심 성질을 설명하는 개념입니다.  
트랜잭션은 여러 개의 데이터 변경 작업을 하나의 논리적 작업 단위로 묶어 처리하며, ACID는 이 과정에서 데이터의 신뢰성과 안정성을 보장합니다.

ACID는 다음 네 가지 속성으로 구성됩니다.

- `Atomicity`: 원자성
- `Consistency`: 일관성
- `Isolation`: 격리성
- `Durability`: 지속성

## 1. Atomicity

원자성은 트랜잭션 내부의 여러 작업이 전부 성공하거나 전부 실패해야 한다는 성질입니다.  
즉, 일부만 반영된 중간 상태가 남아서는 안 됩니다.

예를 들어 계좌 이체는 다음 두 작업으로 이루어질 수 있습니다.

- A 계좌에서 10만 원 차감
- B 계좌에 10만 원 증가

이때 첫 번째 작업만 반영되고 두 번째 작업이 실패하면 데이터는 잘못된 상태가 됩니다.  
원자성은 이런 부분 반영 상태를 허용하지 않습니다.

### 구현 메커니즘: UNDO Log

데이터베이스는 트랜잭션이 데이터를 변경하기 전에 변경 이전 값을 `UNDO` 영역에 기록합니다.  
이후 작업 도중 오류가 발생하거나 사용자가 `ROLLBACK`을 수행하면, 시스템은 이 정보를 이용해 데이터를 트랜잭션 시작 이전 상태로 되돌립니다.

즉, UNDO의 가장 직접적인 역할은 실패한 트랜잭션을 되돌려 원자성을 보장하는 것입니다.  
다만 UNDO는 원자성 보장에만 쓰이는 것이 아니라, 일부 DBMS에서는 이후 설명할 `MVCC`의 과거 버전 조회에도 함께 활용됩니다.

정리하면 원자성은 다음 흐름으로 이해할 수 있습니다.

- 변경 전 데이터를 UNDO에 기록
- 트랜잭션 수행
- 실패 시 UNDO를 이용해 복구
- 성공 시 COMMIT

## 2. Consistency

일관성은 트랜잭션 수행 전후에 데이터베이스가 항상 유효한 상태를 유지해야 한다는 성질입니다.  
즉, 트랜잭션이 끝난 뒤에도 데이터는 무결성 제약 조건과 업무 규칙을 만족해야 합니다.

예를 들어 다음과 같은 규칙이 있다고 가정할 수 있습니다.

- 기본키는 중복될 수 없음
- 외래키는 존재하는 부모 데이터를 참조해야 함
- 잔액은 음수가 될 수 없음

트랜잭션은 이런 규칙을 깨지 않는 범위에서만 성공적으로 완료되어야 합니다.

### 구현 메커니즘: 제약 조건과 애플리케이션 규칙

일관성은 단일 로그나 하나의 내부 구조만으로 보장되는 속성이 아닙니다.  
주로 다음 요소들이 함께 작동해 보장됩니다.

- `PRIMARY KEY`, `FOREIGN KEY`, `CHECK`, `UNIQUE` 같은 제약 조건
- 트리거, 저장 프로시저, 애플리케이션 비즈니스 로직
- 트랜잭션 성공 또는 실패를 판단하는 DB 엔진의 검증 과정

제약 조건을 위반하는 변경이 시도되면 해당 작업은 실패하며, 필요하면 트랜잭션은 롤백됩니다.  
결국 일관성은 "트랜잭션 전후의 상태가 정의된 규칙을 만족하는가"에 대한 속성입니다.

## 3. Isolation

격리성은 동시에 실행되는 여러 트랜잭션이 서로의 중간 상태에 부적절하게 영향을 주지 않도록 보장하는 성질입니다.  
즉, 한 트랜잭션이 아직 확정하지 않은 변경 내용을 다른 트랜잭션이 함부로 읽거나 덮어써서는 안 됩니다.

동시성 제어가 없으면 다음과 같은 문제가 발생할 수 있습니다.

- Dirty Read
- Non-Repeatable Read
- Phantom Read

### 구현 메커니즘: Lock과 MVCC

전통적인 방식은 `Lock`을 사용해 동시 접근을 제어하는 것입니다.  
이 방식은 충돌을 명확히 통제할 수 있지만, 동시성이 높아질수록 대기와 경합이 커질 수 있습니다.

이를 보완하기 위해 많은 RDBMS는 `MVCC(Multi-Version Concurrency Control)`를 사용합니다.  
MVCC는 데이터의 여러 버전을 관리하여, 읽기 작업이 쓰기 작업과 직접 충돌하지 않도록 만듭니다.

일반적인 흐름은 다음과 같습니다.

- 트랜잭션이 데이터를 변경하면 이전 버전 정보가 유지됨
- 읽기 트랜잭션은 자신이 허용받은 시점의 커밋된 버전을 조회
- 쓰기 트랜잭션은 새로운 버전을 생성하거나 변경을 예약

이 구조 덕분에 읽기와 쓰기가 서로를 과도하게 막지 않으면서도 일관된 조회 결과를 제공할 수 있습니다.

구현 방식은 DBMS마다 다르지만, 오라클이나 InnoDB 같은 시스템에서는 과거 버전을 제공할 때 `UNDO` 정보나 버전 체인을 활용합니다.  
즉, UNDO는 원자성의 복구 수단이면서 동시에 MVCC를 지원하는 내부 메커니즘이 될 수 있습니다.

### 트랜잭션 격리 수준

격리성은 보통 `Isolation Level`로 조절합니다.  
격리 수준이 높을수록 이상 현상은 줄어들지만, 동시성 비용은 커질 수 있습니다.

#### Read Uncommitted

커밋되지 않은 데이터까지 읽을 수 있는 수준입니다.  
`Dirty Read`가 발생할 수 있습니다.

#### Read Committed

커밋된 데이터만 읽을 수 있는 수준입니다.  
대부분의 Dirty Read는 방지되지만, `Non-Repeatable Read`와 `Phantom Read`는 발생할 수 있습니다.

#### Repeatable Read

트랜잭션 안에서 같은 조건으로 조회한 기존 행은 동일한 결과를 보장받습니다.  
일반적으로 `Non-Repeatable Read`는 방지되지만, 구현 방식에 따라 `Phantom Read`는 남을 수 있습니다.

#### Serializable

가장 높은 격리 수준으로, 트랜잭션들을 직렬 실행한 것과 동일한 결과를 보장합니다.  
대신 동시성 저하와 잠금 비용이 가장 클 수 있습니다.

## 4. Durability

지속성은 트랜잭션이 `COMMIT`된 뒤에는 시스템 장애가 발생하더라도 그 결과가 보존되어야 한다는 성질입니다.  
즉, 커밋 완료 응답을 받은 변경 사항은 전원 장애나 프로세스 장애 이후에도 사라지면 안 됩니다.

### 구현 메커니즘: REDO Log와 WAL

데이터베이스는 변경된 데이터를 항상 즉시 데이터 파일에 반영하지는 않습니다.  
대신 메모리의 버퍼 캐시에 우선 반영하고, 변경 내역은 별도의 로그에 기록합니다.

이때 핵심이 되는 방식이 `WAL(Write-Ahead Logging)`입니다.

- 실제 데이터 파일보다 로그를 먼저 기록
- 커밋 시점에는 변경 사실이 로그에 안전하게 반영되어 있어야 함
- 이후 장애가 발생하면 로그를 기반으로 복구 수행

지속성 보장을 위해 주로 사용하는 로그가 `REDO Log`입니다.  
시스템 장애가 발생하면 데이터베이스는 재시작 과정에서 REDO Log를 재생해 데이터 파일에 반영되지 못한 변경 사항을 복구합니다.

즉, REDO Log는 커밋된 변경을 안전하게 남겨 지속성을 보장하는 기반이면서, 크래시 이후 그 변경을 다시 반영하는 `복구(Recovery)` 메커니즘의 핵심 재료이기도 합니다.

이 과정을 흔히 `Roll-forward`, `Redo Recovery`, 또는 `Crash Recovery`라고 부릅니다.

## ACID와 로그의 관계

ACID의 네 가지 속성은 각각 독립적이지만, 실제 데이터베이스 내부에서는 서로 연결되어 동작합니다.

- `Atomicity`: UNDO를 이용해 실패한 작업을 되돌림
- `Consistency`: 제약 조건과 업무 규칙을 만족하는 상태만 허용
- `Isolation`: Lock과 MVCC로 동시 실행 충돌을 제어
- `Durability`: REDO Log와 WAL로 커밋 결과를 보존

다만 이를 너무 단순하게 1:1 대응으로 이해하면 실제 동작을 놓치기 쉽습니다.

- `UNDO`는 원자성을 위한 롤백에 사용되며, 동시에 MVCC의 과거 버전 조회에도 활용될 수 있습니다.
- `REDO Log`는 지속성을 보장하는 로그이며, 장애 이후 복구 과정에서도 사용됩니다.

즉, 트랜잭션 처리는 단순히 `COMMIT`과 `ROLLBACK` 명령만의 문제가 아니라, 로그 구조, 동시성 제어, 제약 조건 검사, 복구 메커니즘이 함께 작동하는 종합적인 시스템입니다.

## 정리

- ACID는 트랜잭션의 신뢰성을 보장하는 네 가지 핵심 성질입니다.
- 원자성은 전부 성공 또는 전부 실패를 의미하며, 주로 UNDO를 통해 복구합니다.
- 일관성은 트랜잭션 전후에 데이터가 무결성 규칙을 만족해야 한다는 의미입니다.
- 격리성은 동시 실행되는 트랜잭션 간 간섭을 통제하며, Lock과 MVCC가 핵심 역할을 합니다.
- MVCC는 DBMS에 따라 UNDO 또는 버전 체인을 활용해 과거 버전을 제공합니다.
- 지속성은 커밋된 결과가 장애 이후에도 유지되어야 한다는 의미이며, REDO Log와 WAL이 이를 뒷받침합니다.
- REDO Log는 지속성 보장의 기반일 뿐 아니라, 크래시 발생 후 복구에도 사용됩니다.
