# Overflow Chain과 Skew 문제

## 개요

해싱 기반 저장 구조는 검색 키를 해시 함수에 넣어 대상 버킷(bucket)을 바로 찾는 방식입니다.  
이론적으로는 동등 조건 검색에서 매우 빠르게 동작할 수 있지만, 실제 성능은 데이터가 버킷에 얼마나 고르게 분산되는지에 크게 좌우됩니다.

해싱 구조에서 성능을 흔드는 대표적인 문제는 다음 2가지입니다.

- `Overflow Chain`: 버킷이 가득 차 추가 버킷이 연결되는 현상
- `Skew`: 데이터나 요청이 특정 버킷에 치우치는 현상

이 둘은 따로 발생하기도 하지만, 실무적으로는 skew가 overflow chain을 길게 만들고, 길어진 overflow chain이 조회 성능을 떨어뜨리는 흐름으로 자주 연결됩니다.

## 해싱 구조에서 버킷이 중요한 이유

해싱은 키 값을 정렬해서 찾는 방식이 아닙니다.  
해시 함수의 결과를 이용해 "이 키는 어느 버킷에 있어야 하는가"를 계산하고, 해당 버킷으로 직접 이동합니다.

```text
bucket = hash(key) mod N
```

이 구조가 빠르려면 전제가 필요합니다.

- 각 버킷에 데이터가 고르게 들어가야 합니다.
- 한 버킷 안에 들어가는 레코드 수가 적절히 유지되어야 합니다.
- 특정 버킷만 지나치게 자주 접근되지 않아야 합니다.
- 버킷이 가득 찼을 때 생기는 추가 탐색 비용이 작아야 합니다.

즉, 해싱의 성능은 해시 함수를 한 번 계산하는 비용보다, **계산된 버킷에 도착한 뒤 얼마나 적은 I/O로 원하는 데이터를 찾는가**에 더 크게 영향을 받습니다.

## Overflow Chain

`Overflow Chain`은 기본 버킷이 가득 찼을 때 추가 버킷을 연결해 데이터를 저장하는 구조입니다.

처음에는 해시 함수로 계산한 기본 버킷 안에서 원하는 레코드를 찾을 수 있습니다.  
하지만 해당 버킷에 더 이상 공간이 없으면 데이터베이스는 오버플로우 버킷을 추가로 연결할 수 있습니다.

```text
기본 버킷 -> Overflow Bucket 1 -> Overflow Bucket 2 -> ...
```

이렇게 연결된 오버플로우 버킷들의 목록이 길어지면 조회 비용이 증가합니다.

### 왜 성능이 나빠지는가

해싱의 장점은 대상 버킷을 바로 계산할 수 있다는 점입니다.  
하지만 overflow chain이 길어지면 "대상 버킷을 찾는 것"만으로는 조회가 끝나지 않습니다.

데이터베이스는 다음 순서로 탐색해야 합니다.

1. 해시 함수로 기본 버킷을 계산합니다.
2. 기본 버킷을 읽습니다.
3. 원하는 레코드가 없으면 연결된 오버플로우 버킷을 읽습니다.
4. 필요한 경우 다음 오버플로우 버킷을 계속 따라갑니다.

이 과정에서는 추가 I/O가 발생합니다.  
특히 오버플로우 버킷이 물리적으로 연속된 위치에 있지 않다면 랜덤 I/O가 늘어날 수 있습니다.

결국 overflow chain이 길어진 해싱 구조는 더 이상 "버킷 한 번 접근으로 끝나는 구조"가 아닙니다.  
해시 함수를 통해 시작 위치는 빨리 찾지만, 실제 레코드를 찾기 위해 연결된 버킷을 순차 탐색해야 합니다.

## Skew

`Skew`는 데이터나 요청이 여러 버킷에 고르게 분산되지 않고 특정 버킷에 몰리는 현상입니다.

해싱은 해시 함수가 키 값을 균등하게 퍼뜨린다는 전제 위에서 성능을 기대합니다.  
하지만 실제 데이터 분포나 접근 패턴이 이 전제와 맞지 않으면 일부 버킷만 빠르게 커지거나 과도하게 자주 접근될 수 있습니다.

Skew는 크게 두 가지 관점에서 볼 수 있습니다.

- `Data Skew`: 특정 버킷에 데이터가 과도하게 많이 저장되는 현상
- `Access Skew`: 특정 버킷에 조회나 수정 요청이 과도하게 집중되는 현상

두 skew는 서로 다른 문제입니다.  
데이터가 균등하게 분산되어 있어도 특정 키에 요청이 집중되면 access skew가 발생할 수 있고, 요청은 균등해 보여도 데이터 자체가 특정 버킷에 몰려 있으면 data skew가 발생할 수 있습니다.

## Skew가 발생하는 원인

### 해시 함수의 분산 품질이 낮은 경우

해시 함수가 키 값을 충분히 고르게 섞지 못하면 특정 버킷에 데이터가 몰릴 수 있습니다.

예를 들어 키 값의 마지막 자리만 사용하는 방식처럼 단순한 해시 함수를 사용하면, 데이터 패턴에 따라 일부 버킷에 편중이 생길 수 있습니다.  
이 경우 전체 데이터 건수는 많지 않아도 특정 버킷만 먼저 가득 찹니다.

### 키 값 자체가 치우친 경우

해시 함수가 괜찮더라도 입력 키 분포가 특정 패턴으로 강하게 치우쳐 있으면 문제가 생길 수 있습니다.

예를 들어 테넌트 기반 서비스에서 일부 대형 고객이 대부분의 데이터를 생성한다면, 단순히 `tenant_id`만 해시 키로 사용하는 구조는 위험할 수 있습니다.  
대형 고객의 데이터와 요청이 특정 버킷 또는 특정 파티션에 집중될 수 있기 때문입니다.

### 시간 순 증가 키를 잘못 사용하는 경우

시간 순으로 증가하는 값을 해시 키나 분산 기준으로 사용할 때도 주의가 필요합니다.  
해시 함수가 증가 패턴을 충분히 흩뜨리지 못하면 최근 데이터가 특정 영역에 집중될 수 있습니다.

이 문제는 샤딩이나 파티셔닝에서도 비슷하게 나타납니다.  
새 데이터가 항상 마지막 범위로 들어가면 특정 파티션이나 샤드가 핫스팟이 되는 것처럼, 해싱에서도 특정 버킷이 과도하게 바빠질 수 있습니다.

## Overflow Chain과 Skew의 연결

`Skew`는 원인에 가깝고, `Overflow Chain`은 그 결과로 나타나는 경우가 많습니다.

흐름은 다음과 같습니다.

1. 해시 함수 또는 키 분포 문제로 특정 버킷에 데이터가 몰립니다.
2. 해당 버킷이 다른 버킷보다 먼저 가득 찹니다.
3. 새 데이터를 저장하기 위해 오버플로우 버킷이 연결됩니다.
4. 같은 버킷으로 계속 데이터가 들어오면 overflow chain이 길어집니다.
5. 조회 시 기본 버킷만 읽고 끝나지 않아 I/O가 증가합니다.

따라서 해싱 구조를 점검할 때는 평균 적재율만 보면 부족합니다.  
전체 평균으로는 여유가 있어 보여도, 특정 버킷의 체인이 길면 실제 조회 성능은 크게 나빠질 수 있습니다.

## 동적 해싱이 문제를 완전히 해결하지는 않습니다

`Extendible Hashing`이나 `Linear Hashing`은 버킷을 동적으로 늘려 overflow 문제를 완화합니다.  
하지만 동적 해싱을 사용한다고 해서 skew 문제가 자동으로 사라지는 것은 아닙니다.

### Extendible Hashing의 경우

확장 가능한 해싱은 가득 찬 버킷을 분할하고, 필요하면 디렉터리를 확장합니다.  
이 방식은 특정 버킷의 overflow chain을 줄이는 데 유리합니다.

하지만 특정 키 값이나 특정 고객군에 요청이 계속 몰린다면, 버킷을 분할해도 접근 집중 자체는 남을 수 있습니다.  
즉, 데이터 저장 공간 문제는 완화되더라도 access skew는 별도로 관리해야 합니다.

### Linear Hashing의 경우

선형 해싱은 `split pointer`가 가리키는 버킷을 순서대로 분할합니다.  
확장 비용을 점진적으로 분산할 수 있지만, 오버플로우가 발생한 버킷을 즉시 분할하지 않을 수도 있습니다.

그래서 특정 버킷에 skew가 심하면 한동안 overflow chain이 남을 수 있습니다.  
시간이 지나며 구조가 확장되더라도, 분할 순서와 실제 부하 집중 지점이 어긋나면 성능 편차가 발생할 수 있습니다.

## 문제를 완화하는 방법

Overflow chain과 skew를 줄이려면 다음 요소를 함께 봐야 합니다.

- 해시 함수가 키 값을 충분히 고르게 분산하는지 확인합니다.
- 해시 키가 실제 데이터 분포와 조회 패턴에 적합한지 검토합니다.
- 버킷별 레코드 수와 overflow chain 길이를 모니터링합니다.
- 평균 적재율뿐 아니라 최대 적재 버킷과 핫 버킷을 확인합니다.
- 데이터 증가가 빠른 경우 정적 해싱보다 동적 해싱 구조를 고려합니다.
- 특정 테넌트나 특정 키에 요청이 몰리면 키 설계나 분산 기준을 재검토합니다.

핵심은 전체 데이터 양이 아니라, **가장 바쁜 버킷이 어느 정도의 부하를 받고 있는가**입니다.  
해싱 구조는 평균적으로는 좋아 보여도, 일부 버킷이 병목이 되면 전체 응답 시간이 흔들릴 수 있습니다.

## 정리

- `Overflow Chain`은 기본 버킷이 가득 차 추가 버킷이 연결되는 구조입니다.
- Overflow chain이 길어지면 해시 함수로 버킷을 바로 찾아도 추가 버킷을 따라가야 하므로 I/O가 증가합니다.
- `Skew`는 데이터나 요청이 특정 버킷에 치우치는 현상입니다.
- Skew는 특정 버킷을 먼저 가득 차게 만들고, 결과적으로 overflow chain을 길게 만들 수 있습니다.
- 동적 해싱은 overflow를 완화하지만, 데이터 분포와 접근 집중 문제를 완전히 없애지는 못합니다.
- 해싱 성능을 안정적으로 유지하려면 평균 적재율이 아니라 버킷별 분포, 체인 길이, 핫스팟을 함께 봐야 합니다.

결국 해싱 구조의 성능 문제는 "해시 함수가 느린가"보다, **해시 결과가 실제 저장 공간과 요청 부하를 얼마나 고르게 나누고 있는가**에서 결정됩니다.
