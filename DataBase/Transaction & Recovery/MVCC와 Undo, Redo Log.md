# MVCC와 Undo, Redo Log

## 개요

`MVCC`, `Undo`, `Redo Log`는 모두 트랜잭션 처리와 깊게 연결되어 있지만 역할은 서로 다릅니다.

- `MVCC`는 동시성 환경에서 읽기 일관성을 제공하는 메커니즘입니다.
- `Undo`는 변경 이전 데이터를 보관해 롤백과 과거 버전 조회를 가능하게 합니다.
- `Redo Log`는 변경 이력을 기록해 장애 이후에도 커밋된 결과를 복구할 수 있게 합니다.

이 셋을 한 문장으로 정리하면 다음과 같습니다.

- `MVCC`: 읽는 쪽을 위한 일관성
- `Undo`: 되돌리기와 과거 버전 재구성
- `Redo Log`: 커밋 결과 보존과 장애 복구

## 먼저 구분해야 할 개념

실무에서 가장 많이 헷갈리는 지점은 `Undo`와 `Redo`를 둘 다 "로그"로만 이해하는 경우입니다.  
하지만 둘은 기록 목적이 다릅니다.

| 구분 | 핵심 목적 | 저장 관점 | 주 사용 시점 |
| --- | --- | --- | --- |
| `MVCC` | 읽기 일관성 | 버전 관점 | 조회 시 |
| `Undo` | 롤백, 과거 버전 복원 | 변경 이전 값 | 롤백, 일관된 읽기 |
| `Redo Log` | 장애 복구, 지속성 보장 | 변경 사실 | 커밋, 크래시 복구 |

즉, `Undo`는 "이전 상태로 되돌릴 수 있게" 만들고, `Redo Log`는 "변경 내용을 다시 적용할 수 있게" 만듭니다.

## 1. MVCC란 무엇인가

`MVCC(Multi-Version Concurrency Control)`는 하나의 데이터에 대해 여러 시점의 버전을 논리적으로 관리하여, 읽기 작업과 쓰기 작업이 서로 과하게 막히지 않도록 하는 방식입니다.

트랜잭션이 동시에 실행될 때 가장 단순한 방법은 잠금만으로 충돌을 제어하는 것입니다.  
하지만 이 방식은 읽기와 쓰기가 서로 오래 대기하게 만들 수 있습니다.

`MVCC`는 이 문제를 완화시킬 수 있습니다.

- 쓰는 트랜잭션은 새로운 버전을 만들거나 현재 버전을 갱신합니다.
- 읽는 트랜잭션은 자기 기준 시점에 커밋되어 있던 버전을 읽습니다.
- 그래서 읽기와 쓰기가 항상 직접 충돌하지는 않습니다.

### MVCC가 필요한 이유

예를 들어 어떤 세션이 `UPDATE`를 수행하는 동안 다른 세션이 같은 데이터를 조회한다고 가정해 보겠습니다.

- 잠금 기반만 사용하면 조회가 대기할 가능성이 큽니다.
- `MVCC`를 사용하면 조회는 변경 전의 일관된 버전을 읽을 수 있습니다.

즉, 조회는 "현재 막 수정 중인 값"이 아니라 "내가 읽어도 되는 시점의 값"을 봅니다.

### MVCC의 핵심 아이디어

핵심은 `현재 블록`만 보는 것이 아니라, 필요하면 `과거 버전`을 재구성해서 읽는다는 점입니다.  
이때 과거 버전을 재구성하기 위해 많이 쓰이는 것이 `Undo`입니다.

## 2. Undo란 무엇인가

`Undo`는 데이터 변경 이전 값을 보관하는 영역 또는 정보입니다.  
트랜잭션이 데이터를 수정할 때 DBMS는 원본 값을 `Undo`에 기록해 둡니다.

이 정보는 크게 두 가지 목적에 사용됩니다.

### 1. 롤백을 위한 복구

트랜잭션 도중 오류가 나거나 사용자가 `ROLLBACK`을 수행하면 DBMS는 `Undo`를 이용해 데이터를 변경 전 상태로 되돌립니다.

예를 들어 어떤 행의 값이 `100`에서 `150`으로 바뀌었다면, `Undo`에는 이전 값 `100`을 복원할 수 있는 정보가 남습니다.

### 2. 일관된 읽기를 위한 과거 버전 제공

`MVCC` 환경에서 조회 트랜잭션은 자기 기준 시점 이후에 바뀐 데이터를 그대로 읽으면 안 됩니다.  
이때 DBMS는 현재 블록에 있는 최신 값만 보지 않고, 필요하면 `Undo`를 따라가며 과거 버전을 재구성합니다.

즉, `Undo`는 단순한 롤백 도구가 아니라 `MVCC`를 성립시키는 핵심 재료이기도 합니다.

## 3. Redo Log란 무엇인가

`Redo Log`는 데이터 변경 사실을 기록하는 로그입니다.  
주 목적은 `Durability`, 즉 커밋된 변경이 장애 이후에도 사라지지 않도록 보장하는 것입니다.

DBMS는 보통 변경 내용을 먼저 메모리 버퍼에 반영하고, 데이터 파일은 나중에 디스크에 기록합니다.  
이 과정에서 장애가 발생하면 메모리에만 있던 변경 내용이 유실될 수 있습니다.

이 문제를 막기 위해 `Redo Log`가 사용됩니다.

- 어떤 블록이 어떻게 바뀌었는지 로그로 남깁니다.
- 커밋 시점에는 필요한 `Redo`가 안전하게 기록됩니다.
- 장애가 나면 이 로그를 바탕으로 변경을 다시 적용합니다.

### 왜 Redo가 먼저 중요한가

이 원리는 `WAL(Write-Ahead Logging)`로 설명할 수 있습니다.

- 실제 데이터 파일보다 로그를 먼저 안전하게 기록합니다.
- 그래야 장애가 나도 "무엇을 복구해야 하는지"를 알 수 있습니다.

즉, `Redo Log`는 "나중에 다시 적용할 수 있는 근거"입니다.

## 트랜잭션 흐름으로 보면

`UPDATE`가 한 번 일어날 때 내부에서는 대략 다음 순서가 만들어집니다.

### 1. 변경 전 값은 Undo에 남긴다

기존 값을 되돌릴 수 있도록 `Undo` 정보가 생성됩니다.

### 2. 변경 사실은 Redo Log 대상으로 기록된다

데이터 블록 변경 내용뿐 아니라, `Undo` 블록에 대한 변경도 복구 가능해야 하므로 일반적으로 `Redo` 기록 대상이 됩니다.

### 3. 조회는 필요하면 Undo를 따라가 과거 버전을 본다

다른 세션이 조회할 때 자기 기준 시점과 맞지 않는 최신 값이 보이면, `Undo`를 이용해 읽을 수 있는 버전을 재구성합니다.

### 4. 커밋하면 Redo 기준으로 지속성이 보장된다

커밋 자체는 보통 `Redo Log`가 안전하게 기록되었는지와 강하게 연결됩니다.  
즉, 커밋 응답을 받았다는 것은 장애가 나도 복구 가능한 상태라는 뜻입니다.

### 5. 장애가 나면 Redo로 재적용하고, 필요하면 Undo로 정리한다

크래시 복구 시에는 일반적으로 다음 관점이 함께 작동합니다.

- 커밋되었지만 데이터 파일에 아직 반영되지 않은 변경은 `Redo`로 다시 적용
- 커밋되지 않은 변경은 `Undo` 관점에서 정리

그래서 복구는 `Redo`만의 문제가 아니라 `Undo`와 함께 이해해야 정확합니다.

## 조회 시점과 커밋 시점의 차이

이 주제는 시점을 나눠서 이해하면 훨씬 명확해집니다.

### 조회 시점에 중요한 것

- 내가 읽는 기준 시점은 언제인가
- 현재 값이 아니라 과거 버전을 읽어야 하는가
- 과거 버전이 필요하면 무엇으로 복원하는가

이 질문의 답은 주로 `MVCC`와 `Undo`입니다.

### 커밋 시점에 중요한 것

- 커밋된 변경이 장애 이후에도 살아남는가
- 메모리의 변경이 아직 데이터 파일에 없더라도 복구 가능한가

이 질문의 답은 주로 `Redo Log`입니다.

## 한눈에 비교

| 항목 | MVCC | Undo | Redo Log |
| --- | --- | --- | --- |
| 목적 | 읽기 일관성 | 롤백, 과거 버전 복원 | 지속성, 장애 복구 |
| 초점 | 조회 | 변경 이전 상태 | 변경 사실 |
| 주 사용 상황 | 동시 조회 | ROLLBACK, consistent read | COMMIT, crash recovery |
| 없으면 생기는 문제 | 읽기-쓰기 충돌 증가 | 롤백 불가, 과거 버전 조회 곤란 | 커밋 손실, 복구 불가 |

## 자주 헷갈리는 포인트

### Undo는 Durability를 위한 것이 아니다

`Undo`는 변경을 되돌리거나 과거 버전을 읽게 해 주는 쪽에 가깝습니다.  
커밋된 결과를 장애 이후에도 보존하는 핵심은 `Redo Log`입니다.

### Redo는 롤백용 로그가 아니다

`Redo Log`는 "변경을 다시 적용"하기 위한 로그입니다.  
반대로 `Undo`는 "변경을 되돌리기" 위한 정보입니다.

### MVCC는 별도의 로그 이름이 아니다

`MVCC`는 동시성 제어 방식입니다.  
즉, `Undo`나 버전 체인 같은 내부 구조를 활용해 구현되는 메커니즘이지, `Redo Log`처럼 독립된 로그 파일 이름이 아닙니다.

### 구현 방식은 DBMS마다 다를 수 있다

`MVCC`의 기준 시점, 버전 관리 방식, `Undo` 저장 구조는 Oracle, PostgreSQL, InnoDB 계열에서 조금씩 다릅니다.  
하지만 큰 그림은 공통적입니다.

- 읽기 일관성을 제공해야 한다
- 롤백을 위한 이전 값이 필요하다
- 장애 이후 복구를 위한 변경 기록이 필요하다

## 정리

- `MVCC`는 읽기 일관성을 위한 동시성 제어 방식입니다.
- `Undo`는 변경 이전 값을 저장해 롤백과 과거 버전 조회를 가능하게 합니다.
- `Redo Log`는 변경 사실을 기록해 커밋 결과의 지속성과 장애 복구를 보장합니다.
- 조회 관점에서는 `MVCC + Undo`가 중요하고, 커밋과 복구 관점에서는 `Redo Log`가 핵심입니다.
- 실제 트랜잭션 처리에서는 이 세 요소가 함께 작동해야 동시성, 원자성, 지속성을 동시에 만족할 수 있습니다.
