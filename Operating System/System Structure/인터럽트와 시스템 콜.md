# 인터럽트와 시스템 콜

## 개요

응용 프로그램은 화면에 글자를 출력하거나 파일을 읽는 것처럼 하드웨어를 다루는 작업을 스스로 할 수 없습니다.  
이런 작업은 운영체제(커널)를 거쳐야만 안전하게 수행할 수 있습니다.

이때 **하드웨어가 CPU에게 사건을 알리는 방식**이 `인터럽트(Interrupt)`이고,  
**응용 프로그램이 커널에게 서비스를 요청하는 방식**이 `시스템 콜(System Call)`입니다.

두 개념은 모두 "지금 실행 중인 흐름을 멈추고 커널로 제어를 넘긴다"는 공통점을 가지며,  
그 바탕에는 `사용자 모드`와 `커널 모드`를 구분하는 `이중 모드(Dual Mode)`가 있습니다.  
이 구조를 이해하면 운영체제가 어떻게 하드웨어를 보호하고, 여러 프로그램을 안전하게 실행하는지 명확하게 볼 수 있습니다.

## 1. 사용자 모드와 커널 모드

### 왜 모드를 나누는가

만약 모든 프로그램이 하드웨어에 직접 접근할 수 있다면, 하나의 잘못된 프로그램이 다른 프로그램의 메모리를 덮어쓰거나 디스크를 손상시킬 수 있습니다.  
운영체제는 이를 막기 위해 CPU 실행 상태를 두 가지 모드로 나눕니다.

- `사용자 모드(User Mode)`: 일반 응용 프로그램이 실행되는 모드입니다. 제한된 명령어만 사용할 수 있고, 하드웨어에 직접 접근할 수 없습니다.
- `커널 모드(Kernel Mode)`: 운영체제 코드가 실행되는 모드입니다. 모든 명령어와 하드웨어 자원에 접근할 수 있습니다.

CPU 내부의 `모드 비트(Mode Bit)` 하나로 현재 어떤 모드인지 구분합니다.

- 모드 비트가 `1`이면 사용자 모드
- 모드 비트가 `0`이면 커널 모드

### 특권 명령어

하드웨어 제어처럼 위험한 명령어는 `특권 명령어(Privileged Instruction)`로 지정되어 커널 모드에서만 실행됩니다.

- 입출력 장치 접근
- 인터럽트 활성화/비활성화
- 타이머 설정
- 페이지 테이블 등록 등 메모리 관리 명령어

사용자 모드에서 특권 명령어를 실행하려 하면 CPU가 예외를 발생시켜 커널로 제어를 넘깁니다.  
즉, 응용 프로그램은 하드웨어를 직접 만질 수 없고 **반드시 커널에게 대신 요청**해야 합니다. 그 요청 통로가 바로 시스템 콜입니다.

## 2. 인터럽트

### 인터럽트란 무엇인가

`인터럽트`는 CPU가 현재 작업을 진행하는 도중에, 처리해야 할 사건이 발생했음을 알리는 신호입니다.  
CPU는 인터럽트를 감지하면 하던 일을 잠시 멈추고, 그 사건을 처리하는 코드를 실행한 뒤 원래 작업으로 돌아옵니다.

인터럽트가 없다면 CPU는 어떤 사건이 발생했는지 알기 위해 계속 확인(폴링)해야 하므로 CPU 자원이 크게 낭비됩니다.

### 인터럽트의 종류

인터럽트는 발생 원인에 따라 크게 두 가지로 나뉩니다.

| 구분 | 발생 주체 | 예시 |
| --- | --- | --- |
| 하드웨어 인터럽트 | 외부 장치 | 키보드 입력, 디스크 I/O 완료, 타이머 만료 |
| 소프트웨어 인터럽트 | 실행 중인 프로그램 | 시스템 콜, 0으로 나누기, 잘못된 메모리 접근 |

소프트웨어 인터럽트 중에서, 프로그램 실행 오류(예외)나 시스템 콜처럼 **CPU 내부에서 동기적으로 발생**하는 것을 별도로 `트랩(Trap)` 또는 `예외(Exception)`라고 부르기도 합니다.

- `트랩`: 시스템 콜처럼 프로그램이 **의도적으로** 발생시키는 것
- `예외`: 0으로 나누기, 페이지 폴트처럼 **의도치 않게** 발생하는 오류

### 인터럽트 처리 과정

인터럽트가 발생하면 CPU와 운영체제는 다음 순서로 처리합니다.

1. 현재 실행 중인 명령어를 마무리합니다.
2. 현재 작업의 상태(PC, 레지스터 등)를 저장합니다.
3. `인터럽트 벡터 테이블(Interrupt Vector Table)`을 참조해 해당 인터럽트의 처리 루틴 주소를 찾습니다.
4. `인터럽트 서비스 루틴(ISR, Interrupt Service Routine)`을 실행해 사건을 처리합니다.
5. 저장해 둔 상태를 복원하고, 원래 작업을 이어서 실행합니다.

여기서 상태를 저장하고 복원하는 과정이 `문맥 교환(Context Switch)`과 밀접하게 연결됩니다.

### 인터럽트가 중요한 이유

- **CPU 효율**: CPU는 장치가 준비될 때까지 기다릴 필요 없이 다른 작업을 하다가, 인터럽트가 오면 그때 처리합니다.
- **선점형 스케줄링의 기반**: 타이머 인터럽트가 주기적으로 발생하기 때문에 운영체제가 CPU를 회수해 다른 프로세스에 넘길 수 있습니다.
- **비동기 이벤트 처리**: 언제 발생할지 모르는 외부 사건(입력, 네트워크 등)에 즉각 반응할 수 있습니다.

## 3. 시스템 콜

### 시스템 콜이란 무엇인가

`시스템 콜`은 사용자 모드의 응용 프로그램이 커널의 기능을 사용하기 위해 커널에 요청을 보내는 인터페이스입니다.

파일을 열거나 새로운 프로세스를 만드는 등, 하드웨어나 커널 자원이 필요한 작업은 응용 프로그램이 직접 할 수 없습니다.  
대신 시스템 콜을 호출하면 CPU가 커널 모드로 전환되고, 커널이 대신 그 작업을 수행한 뒤 결과를 돌려줍니다.

### 시스템 콜의 동작 흐름

시스템 콜은 소프트웨어 인터럽트(트랩)를 이용해 사용자 모드에서 커널 모드로 넘어갑니다.

1. 응용 프로그램이 라이브러리 함수(예: `read()`)를 호출합니다.
2. 요청 종류를 식별하는 `시스템 콜 번호`와 인자를 레지스터에 세팅합니다.
3. 트랩 명령어를 실행해 CPU를 커널 모드로 전환합니다. (모드 비트 `1` → `0`)
4. 커널은 시스템 콜 번호를 보고 `시스템 콜 테이블`에서 해당 처리 루틴을 찾아 실행합니다.
5. 작업이 끝나면 결과를 반환하고, CPU를 다시 사용자 모드로 되돌립니다. (모드 비트 `0` → `1`)

```
사용자 모드                    커널 모드
  read() 호출
      │  트랩 발생 (모드 전환)
      └───────────────►  시스템 콜 처리 루틴 실행
                              │  실제 디스크 I/O 수행
      ◄───────────────┘  결과 반환 (모드 복귀)
  이어서 실행
```

### 시스템 콜의 분류

시스템 콜은 제공하는 기능에 따라 대략 다음과 같이 나뉩니다.

| 분류 | 예시 |
| --- | --- |
| 프로세스 제어 | `fork()`, `exec()`, `exit()`, `wait()` |
| 파일 관리 | `open()`, `read()`, `write()`, `close()` |
| 장치 관리 | `ioctl()`, 장치 요청/해제 |
| 정보 유지 | `getpid()`, 시간 조회, 시스템 정보 조회 |
| 통신 | `pipe()`, `socket()`, 공유 메모리 요청 |

응용 프로그램이 직접 시스템 콜 번호를 다루면 이식성이 떨어지기 때문에, 보통 `표준 라이브러리(예: libc)`가 시스템 콜을 감싼 함수를 제공하고 개발자는 그 함수를 호출합니다.

## 4. 인터럽트와 시스템 콜의 관계

시스템 콜은 결국 **소프트웨어 인터럽트를 이용해 커널로 진입하는 특수한 경우**입니다.  
둘 다 "실행 흐름을 멈추고 커널 모드로 전환한다"는 메커니즘을 공유하지만, 발생 주체와 목적이 다릅니다.

| 구분 | 인터럽트(하드웨어) | 시스템 콜(트랩) |
| --- | --- | --- |
| 발생 주체 | 외부 장치 | 실행 중인 프로그램 |
| 발생 시점 | 비동기적 (언제든 발생) | 동기적 (특정 명령어 실행 시) |
| 목적 | 외부 사건 알림 | 커널 서비스 요청 |
| 예시 | 키보드 입력, 타이머 만료 | `open()`, `fork()` |

## 5. 폴링과 인터럽트

CPU가 장치의 상태를 확인하는 방식에는 두 가지가 있습니다.

- `폴링(Polling)`: CPU가 장치 상태를 **주기적으로 반복 확인**하는 방식입니다. 구현은 단순하지만, 사건이 없을 때도 계속 확인하므로 CPU를 낭비합니다.
- `인터럽트(Interrupt)`: 장치가 준비되면 **CPU에게 신호를 보내는** 방식입니다. CPU는 그동안 다른 일을 할 수 있어 효율적입니다.

일반적으로는 인터럽트가 효율적이지만, 사건이 매우 빈번하게 발생하는 고속 장치에서는 인터럽트 처리 오버헤드가 커져 오히려 폴링이 유리할 수 있습니다.  
그래서 리눅스의 네트워크 처리(NAPI)처럼, 평소에는 인터럽트를 쓰다가 트래픽이 몰리면 폴링으로 전환하는 **혼합 방식**이 실무에서 쓰이기도 합니다.

## 정리

- 운영체제는 하드웨어를 보호하기 위해 `사용자 모드`와 `커널 모드`를 나누며, 위험한 `특권 명령어`는 커널 모드에서만 실행됩니다.
- `인터럽트`는 하드웨어나 프로그램이 CPU에게 사건을 알리는 신호이며, CPU는 하던 일을 멈추고 `인터럽트 서비스 루틴`을 실행한 뒤 원래 작업으로 돌아옵니다.
- 인터럽트는 발생 주체에 따라 `하드웨어 인터럽트`와 `소프트웨어 인터럽트(트랩/예외)`로 나뉩니다.
- `시스템 콜`은 응용 프로그램이 커널 기능을 요청하는 인터페이스이며, 내부적으로 트랩을 이용해 커널 모드로 전환합니다.
- 시스템 콜은 인터럽트 메커니즘을 공유하지만, **동기적으로 프로그램이 직접 발생시킨다**는 점에서 하드웨어 인터럽트와 다릅니다.
- 장치 확인 방식에는 `폴링`과 `인터럽트`가 있고, 상황에 따라 둘을 혼합해 사용하기도 합니다.

결국 인터럽트와 시스템 콜의 핵심은 **사용자 프로그램과 하드웨어 사이에 커널이라는 안전한 중개자를 두고, 제어권을 안전하게 넘기고 되돌려받는 메커니즘**이라는 점입니다.  
이 구조가 있기에 운영체제는 하드웨어를 보호하면서도 여러 프로그램에게 필요한 서비스를 안정적으로 제공할 수 있습니다.
