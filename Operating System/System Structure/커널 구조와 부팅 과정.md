# 커널 구조와 부팅 과정

## 개요

`인터럽트`와 `시스템 콜`이 사용자 프로그램이 커널로 들어가는 문이라면, 이 문서는 그 문 너머에 있는 **커널 자체가 어떻게 생겼고, 언제 어떻게 메모리에 올라오는가**를 다룹니다.

전원을 켠 직후의 컴퓨터에는 운영체제가 없습니다. 메모리는 비어 있고, 디스크에 있는 커널은 아직 아무도 읽어주지 않았습니다.  
"운영체제를 실행하려면 운영체제가 필요하다"며 시작하는 것이 `부팅`이고, 그렇게 올라온 커널을 어떤 방식으로 조립할지에 대한 설계 선택이 `커널 구조`입니다.

이 두 가지를 이해하면 왜 리눅스 커널 패닉은 시스템 전체를 멈추는데 macOS의 일부 드라이버는 죽어도 재시작되는지, 왜 컨테이너가 가벼운 것인지 같은 질문에 답할 수 있습니다.

## 1. 커널이란 무엇인가

`커널`은 운영체제의 핵심부로, **부팅 시 메모리에 올라와 종료될 때까지 상주하며 커널 모드에서 실행되는 코드**입니다.

운영체제라는 말은 보통 커널보다 넓은 범위를 가리킵니다.

| 구분 | 설명 | 예시 |
| --- | --- | --- |
| 커널 | 항상 메모리에 상주하는 핵심 코드 | 스케줄러, 메모리 관리자, 파일 시스템, 드라이버 |
| 시스템 프로그램 | 커널 위에서 도는 사용자 모드 프로그램 | 셸, 서비스 데몬, `ls` 같은 유틸리티 |
| 사용자 프로그램 | 일반 응용 | 브라우저, 에디터 |

여기서 중요한 판단 기준이 하나 생깁니다. **어떤 기능을 커널 안에 넣을 것인가?**  
커널 안에 넣으면 빠르지만, 그 코드의 버그가 시스템 전체를 무너뜨립니다. 커널 밖으로 빼면 안전하지만, 매번 모드 전환과 통신 비용을 냅니다.  
이 트레이드오프가 아래 커널 구조들을 갈라놓습니다.

## 2. 커널 구조

### 2.1 단일형 커널

스케줄링, 메모리 관리, 파일 시스템, 장치 드라이버, 네트워크 스택까지 **모든 핵심 기능을 하나의 커널 주소 공간에 넣는** 구조입니다.  
리눅스, 유닉스 계열이 대표적입니다.

```
[ 사용자 모드 ]  응용 프로그램 · 셸 · 라이브러리
--------------------------- 시스템 콜 경계
[ 커널 모드 ]    스케줄러 | 메모리 관리 | 파일 시스템 | 드라이버 | 네트워크
                        └── 전부 같은 주소 공간, 함수 호출로 직접 통신 ──┘
```

- **장점**: 커널 내부 모듈끼리는 그냥 함수 호출로 통신합니다. 모드 전환도, 메시지 복사도 없어 성능이 좋습니다.
- **단점**: 드라이버 하나의 NULL 포인터 참조가 커널 전체를 죽입니다(`커널 패닉`). 코드베이스가 거대해져 유지보수가 어렵고, 작은 수정에도 커널 전체를 다시 빌드해야 합니다.

마지막 단점을 완화하기 위해 리눅스는 `적재 가능 커널 모듈`을 지원합니다.  
드라이버 같은 기능을 실행 중에 `insmod` / `rmmod`로 붙였다 뗄 수 있어, 재부팅 없이 확장할 수 있습니다.  
다만 모듈도 결국 **커널 주소 공간 안에서 실행**되므로, 격리 측면의 위험은 그대로입니다. 유연성만 얻은 것이지 안전성을 얻은 것은 아닙니다.

### 2.2 마이크로 커널

커널에는 **정말 최소한의 기능만** 남기고, 나머지는 사용자 모드의 독립적인 서버 프로세스로 밀어내는 구조입니다.

커널에 남기는 것은 대략 다음과 같습니다.

- 프로세스/쓰레드 스케줄링
- 기본적인 메모리 관리
- 프로세스 간 통신(IPC)

파일 시스템, 드라이버, 네트워크 스택은 전부 사용자 모드 서버가 됩니다.

```
[ 사용자 모드 ]  응용  ↔  파일 서버  ↔  드라이버 서버  ↔  네트워크 서버
                   └────────── 메시지(IPC) ──────────┘
--------------------------- 
[ 커널 모드 ]    스케줄링 · 메모리 · IPC (그게 전부)
```

- **장점**: 드라이버 서버가 죽어도 커널은 멀쩡합니다. 해당 서버만 재시작하면 됩니다. 커널 코드가 작아 검증하기 쉬워 항공·자동차 같은 고신뢰 영역에서 선호됩니다.
- **단점**: 응용이 파일을 읽으려면 커널을 거쳐 파일 서버로 메시지를 보내고, 다시 돌아와야 합니다. 예전에는 함수 호출 한 번이면 됐을 일이 **여러 번의 모드 전환과 메시지 복사**로 바뀌면서 성능이 떨어집니다.

여기서 IPC 성능이 곧 마이크로 커널의 성능이 됩니다.

### 2.3 하이브리드 커널

현실의 운영체제 대부분은 순수한 한쪽이 아닙니다.  
Windows NT 계열과 macOS는 마이크로 커널 설계에서 출발했지만, 성능이 중요한 부분(그래픽, 파일 시스템 일부)을 다시 커널 모드로 끌어들인 `하이브리드 커널`입니다.

즉 "성능이 중요한 코드는 안으로, 잘 죽거나 자주 바뀌는 코드는 밖으로"라는 **실용적 타협**입니다.

### 2.4 구조 비교

| 구분 | 단일형 커널 | 마이크로 커널 |
| --- | --- | --- |
| 커널 크기 | 크다 | 작다 |
| 내부 통신 | 함수 호출 | IPC 메시지 |
| 성능 | 빠름 | 상대적으로 느림 |
| 안정성 | 모듈 하나가 전체를 죽일 수 있음 | 서버 하나가 죽어도 격리됨 |
| 확장 | 커널 모듈 적재 | 서버 프로세스 추가 |
| 예시 | Linux, Unix | QNX, MINIX, L4 |

## 3. 부팅 과정

전원을 켠 순간 CPU는 아무것도 모릅니다. 커널은 디스크에 있고, 디스크를 읽으려면 드라이버가 필요하고, 드라이버는 커널 안에 있습니다.  
이 순환을 **아주 작은 코드부터 시작해 점점 큰 코드를 끌어올리는 방식**으로 푸는 것이 부팅이며, "자기 신발끈을 잡아당겨 스스로를 들어올린다"는 뜻에서 `부트스트랩`이라 부릅니다.

### 3.1 전체 흐름

```
전원 ON
  └─ 1. 펌웨어(BIOS/UEFI) : ROM에서 실행, 하드웨어 점검(POST), 부팅 장치 탐색
       └─ 2. 부트로더(GRUB 등)  : 커널 이미지를 디스크에서 메모리로 적재
            └─ 3. 커널 초기화     : 메모리 관리·스케줄러·드라이버 초기화, 루트 파일 시스템 마운트
                 └─ 4. init 프로세스 : 최초의 사용자 프로세스(PID 1) 생성, 서비스 기동
                      └─ 5. 로그인 / 셸
```

### 3.2 단계별로 보기

**1) 펌웨어 (BIOS / UEFI)**

CPU는 전원이 들어오면 미리 정해진 주소의 명령어부터 실행합니다. 그 주소에는 메인보드의 ROM에 구워진 펌웨어가 있습니다.  
디스크가 아니라 ROM에 있기 때문에, 운영체제 없이도 실행될 수 있습니다. 이것이 순환을 깨는 출발점입니다.

- `POST(Power-On Self-Test)`: CPU, 메모리, 기본 장치가 정상인지 점검합니다.
- 부팅 가능한 장치를 순서대로 찾아 그 안의 부트로더를 메모리로 읽어 실행합니다.

**2) 부트로더**

부트로더의 유일한 임무는 **커널을 메모리에 올리고 제어권을 넘기는 것**입니다. GRUB, Windows Boot Manager 등이 여기 해당합니다.

- 커널 이미지를 디스크에서 읽어 메모리에 적재합니다.
- 부팅 옵션(커널 파라미터, 여러 OS 중 선택 등)을 처리합니다.
- 커널의 시작 지점으로 점프합니다.

**3) 커널 초기화**

이제 커널이 CPU를 잡았습니다. 여기서 우리가 다른 문서에서 배운 자료구조들이 하나씩 만들어집니다.

- 메모리 관리 초기화: 페이지 테이블을 세팅하고 가상 메모리를 활성화합니다.
- 스케줄러와 인터럽트 벡터 테이블을 초기화합니다.
- 필수 장치 드라이버를 올리고, `루트 파일 시스템`을 마운트합니다.

**4) init 프로세스 (PID 1)**

커널은 마지막으로 **최초의 사용자 모드 프로세스**를 만듭니다. 리눅스에서는 `systemd`(과거에는 `init`)이며 PID는 항상 `1`입니다.

이 프로세스가 특별한 이유는 두 가지입니다.

- 이후의 모든 프로세스는 `fork()`로 만들어지므로, PID 1은 **모든 프로세스의 조상**이 됩니다.
- 부모가 먼저 죽어 고아가 된 프로세스는 PID 1이 입양해 정리합니다. 즉 좀비 프로세스가 무한정 쌓이지 않게 하는 최종 안전망입니다.

init이 네트워크, 로그, 디스플레이 매니저 같은 서비스를 순서대로 띄우면 부팅이 끝나고 로그인 화면이 나타납니다.

## 4. 실무 예시

### 커널 패닉 vs 프로세스 크래시

응용 프로그램이 죽으면 그 프로세스만 종료되고 커널이 자원을 회수합니다. 하지만 커널 코드(드라이버 포함)가 죽으면 **자원을 회수해 줄 상위 주체가 없습니다**.  
그래서 커널은 복구를 시도하지 않고 즉시 멈춥니다(`커널 패닉`, Windows의 `블루 스크린`).  
서버에서 특정 하드웨어 드라이버를 올린 직후 시스템이 통째로 재부팅된다면, 그 코드가 커널 주소 공간에서 돌고 있다는 사실을 떠올려야 합니다.

### 컨테이너가 가벼운 이유

컨테이너는 가상 머신과 달리 **자기 커널을 부팅하지 않습니다**. 호스트의 커널을 그대로 공유하고, 프로세스 격리 기능(namespace, cgroup)만 빌려 씁니다.  
위의 부팅 과정 1~3단계를 통째로 건너뛰기 때문에 초 단위가 아니라 밀리초 단위로 뜨는 것입니다. 대신 **호스트 커널과 다른 커널을 쓸 수 없다**는 제약이 따라옵니다.

### 커널 모듈은 편하지만 공짜가 아니다

`LKM`으로 재부팅 없이 드라이버를 붙이는 건 편하지만, 검증되지 않은 서드파티 모듈을 프로덕션 커널에 적재하는 것은 **시스템 전체에 대한 쓰기 권한을 주는 것과 같습니다**.  
최근 리눅스가 `eBPF`처럼 **검증기를 통과한 코드만 커널에서 안전하게 실행**시키는 방향으로 가는 이유가 여기 있습니다.

## 정리

- `커널`은 부팅 시 메모리에 올라와 상주하며 커널 모드에서 실행되는 운영체제의 핵심부입니다.
- 커널 설계의 핵심 질문은 **"어떤 기능을 커널 안에 넣을 것인가"**이며, 이는 성능과 안정성의 트레이드오프입니다.
- `단일형 커널`은 모든 기능을 한 주소 공간에 넣어 함수 호출로 통신하므로 빠르지만, 모듈 하나의 버그가 전체를 죽입니다.
- `마이크로 커널`은 기능을 사용자 모드 서버로 분리해 격리성이 뛰어나지만, IPC 비용 때문에 느립니다. 현실의 OS 대부분은 둘을 절충한 `하이브리드 커널`입니다.
- `부팅`은 "OS를 실행하려면 OS가 필요하다"는 순환을, ROM의 작은 펌웨어에서 시작해 점점 큰 코드를 끌어올려 해결하는 과정입니다.
- 부팅 순서는 `펌웨어(BIOS/UEFI)` → `부트로더` → `커널 초기화` → `init 프로세스(PID 1)`이며, PID 1은 모든 프로세스의 조상이자 고아 프로세스의 최종 수거자입니다.

커널 구조와 부팅을 함께 보면 결국 하나의 질문으로 수렴합니다. **어디까지를 신뢰할 것인가.**  
커널 안에 넣은 코드는 전부 "시스템 전체를 믿고 맡긴 코드"이고, 부팅은 그 신뢰의 사슬을 ROM의 첫 명령어부터 한 단계씩 쌓아 올리는 과정입니다.
