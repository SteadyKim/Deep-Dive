# Checkpoint와 Crash Recovery

## 개요

데이터베이스는 변경 내용을 항상 즉시 데이터 파일에 직접 기록하지 않습니다.  
보통 먼저 메모리 버퍼에 반영하고, 변경 사실은 로그에 기록한 뒤, 실제 데이터 파일 기록은 나중에 수행합니다.

이 구조 덕분에 성능은 좋아지지만, 시스템이 갑자기 종료되면 "메모리에는 있었지만 파일에는 아직 없는 변경"이 남을 수 있습니다.  
이 문제를 다루는 핵심 개념이 `Checkpoint`와 `Crash Recovery`입니다.

- `Checkpoint`는 복구 기준점을 관리하고 복구 범위를 줄이는 장치입니다.
- `Crash Recovery`는 비정상 종료 후 로그를 이용해 데이터베이스를 일관된 상태로 되돌리는 과정입니다.

즉, `Checkpoint`는 "어디서부터 복구를 시작할지"와 관련이 있고, `Crash Recovery`는 "장애 후 실제로 어떻게 복구할지"와 관련이 있습니다.

## 먼저 알아둘 개념

이 주제를 이해하려면 다음 세 가지를 먼저 구분해야 합니다.

### 1. Buffer Cache

DBMS는 변경된 블록을 먼저 메모리의 버퍼 캐시에 반영합니다.  
이 상태에서는 사용자가 데이터를 수정했더라도, 그 결과가 아직 데이터 파일까지 내려가지 않았을 수 있습니다.

### 2. Dirty Page 또는 Dirty Block

메모리에서는 변경되었지만 아직 데이터 파일에는 기록되지 않은 페이지나 블록을 `Dirty Page` 또는 `Dirty Block`이라고 합니다.

즉, "메모리의 최신 상태"와 "디스크의 데이터 파일 상태"가 잠시 어긋나 있을 수 있습니다.

### 3. Redo Log 또는 WAL

변경된 블록 전체를 매번 즉시 데이터 파일에 쓰는 대신, DBMS는 먼저 "어떤 변경이 일어났는지"를 로그로 남깁니다.  
이 로그가 장애 이후 복구의 근거가 됩니다.

즉, 실제 데이터 파일은 늦게 써도 되지만, `복구 가능한 로그`는 먼저 안전하게 남아 있어야 합니다.

## 1. 왜 Checkpoint가 필요한가

만약 Checkpoint가 전혀 없다면 장애가 발생했을 때 DBMS는 매우 오래된 시점부터 로그를 훑어야 할 수 있습니다.  
이렇게 되면 복구 시간이 길어지고, 재시작 비용이 커집니다.

Checkpoint는 이 문제를 줄이기 위해 사용됩니다.

- 특정 시점까지의 디스크 반영 상태를 관리한다
- 복구 시작 기준점을 로그에 남긴다
- 장애 후 어디서부터 Redo를 적용할지 범위를 줄여 준다

즉, Checkpoint의 가장 중요한 역할은 "복구 시간을 단축하는 것"입니다.

## 2. Checkpoint란 무엇인가

`Checkpoint`는 데이터베이스가 "이 시점까지는 복구를 이렇게 보면 된다"는 기준 정보를 남기는 작업 또는 이벤트입니다.

많이 단순화해서 설명하면 다음과 같이 이해할 수 있습니다.

- 일부 Dirty Page를 디스크로 내려보낸다
- 해당 시점의 복구 기준 정보를 로그에 기록한다
- 나중에 장애가 나면 이 기준점 이후를 중심으로 복구한다

중요한 점은 Checkpoint가 항상 "모든 Dirty Page를 완전히 다 디스크에 기록한다"는 뜻은 아니라는 것입니다.  
정확한 구현은 DBMS마다 다르고, 많은 시스템은 `fuzzy checkpoint`처럼 일부만 반영해도 복구 가능한 형태로 관리합니다.

즉, Checkpoint는 "모든 쓰기 완료 이벤트"라기보다 "복구 기준점 확립 이벤트"에 더 가깝습니다.

## 3. Checkpoint가 동작할 때 내부에서 일어나는 일

DBMS마다 세부 구조는 다르지만, 개념적으로는 다음 흐름으로 볼 수 있습니다.

### 1. 현재까지의 로그 진행 상태를 기록한다

복구 시 참고할 수 있도록 특정 로그 위치나 시점을 남깁니다.

### 2. Dirty Page 일부 또는 다수를 디스크에 기록한다

버퍼 캐시에만 있던 변경 내용 중 일부를 실제 데이터 파일로 내립니다.

### 3. 복구 시 사용할 기준 정보를 남긴다

어떤 페이지가 반영되었고, 어디서부터 다시 보면 되는지에 대한 기준이 로그나 제어 정보에 반영됩니다.

즉, Checkpoint는 단순 쓰기 작업이 아니라 `메모리 상태`, `데이터 파일 상태`, `로그 기준점`을 함께 맞추는 작업입니다.

## 4. Crash Recovery란 무엇인가

`Crash Recovery`는 데이터베이스가 비정상 종료된 뒤 다시 시작될 때, 로그를 이용해 데이터베이스를 일관된 상태로 복구하는 과정입니다.

여기서 말하는 비정상 종료는 보통 다음과 같은 상황입니다.

- 서버 전원 장애
- OS 크래시
- DB 프로세스 강제 종료
- 인스턴스 비정상 중단

이런 경우 메모리 내용은 사라지지만, 로그 파일과 데이터 파일은 디스크에 남아 있습니다.  
DBMS는 이 둘의 차이를 메우는 방식으로 복구를 수행합니다.

## 5. Crash Recovery가 필요한 이유

다음 상황을 생각해 보면 이유가 명확합니다.

- 어떤 트랜잭션이 `COMMIT`을 완료했다
- 관련 변경은 `Redo Log`에 기록되었다
- 하지만 데이터 파일에는 아직 일부 블록만 반영되었다
- 그 직후 서버가 갑자기 종료되었다

이 경우 데이터 파일만 보면 커밋된 변경이 일부 빠져 있을 수 있습니다.  
하지만 로그에는 변경 사실이 남아 있으므로 DBMS는 재시작 시 이를 다시 적용해 정합성을 회복할 수 있습니다.

즉, Crash Recovery는 "커밋된 변경은 살리고, 완료되지 않은 변경은 정리"하는 과정입니다.

## 6. Crash Recovery는 어떻게 진행될까

구현은 DBMS마다 다르지만, 개념적으로는 보통 다음 순서로 이해할 수 있습니다.

### 1. 복구 시작점을 찾는다

DBMS는 Checkpoint 정보와 로그를 바탕으로 어디서부터 복구를 시작해야 할지 결정합니다.

Checkpoint가 없다면 훨씬 더 많은 로그를 뒤져야 할 수 있습니다.

### 2. Redo를 적용한다

커밋되었지만 데이터 파일에 반영되지 않았을 수 있는 변경을 다시 적용합니다.

즉, 로그를 읽어 "디스크에 빠진 최신 변경"을 보강합니다.

### 3. 필요하면 Undo를 적용한다

장애 시점에 아직 완료되지 않았던 트랜잭션의 흔적은 정리해야 합니다.  
이 단계에서는 미완료 변경을 되돌려 일관된 상태를 맞춥니다.

즉, `Redo`는 살아남아야 할 변경을 다시 반영하고, `Undo`는 남아 있으면 안 되는 미완료 변경을 정리합니다.

## 7. Redo와 Undo의 역할을 다시 보면

`Crash Recovery`에서는 `Redo`와 `Undo`가 함께 이해되어야 합니다.

### Redo의 역할

- 커밋된 변경을 다시 반영한다
- 데이터 파일에 아직 없던 변경을 복구한다
- 지속성을 실제 상태로 복원한다

### Undo의 역할

- 비정상 종료 시점에 미완료였던 트랜잭션을 정리한다
- 부분 반영 상태를 없앤다
- 데이터베이스를 논리적으로 일관된 상태로 되돌린다

즉, 복구는 단순히 "로그를 다시 읽는다"가 아니라, `반영할 것`과 `되돌릴 것`을 구분하는 과정입니다.

## 8. Checkpoint와 Crash Recovery의 관계

둘은 따로 존재하는 개념이 아니라, 하나의 흐름으로 이어집니다.

### Checkpoint가 하는 일

- 복구 기준점을 남긴다
- 복구 범위를 줄인다
- 재시작 시간을 단축한다

### Crash Recovery가 하는 일

- Checkpoint 이후 필요한 로그를 읽는다
- 반영되지 않은 커밋 내용을 Redo 한다
- 미완료 작업을 Undo 하여 정리한다

즉, Checkpoint는 복구를 더 빠르게 만들고, Crash Recovery는 실제로 복구를 수행합니다.

## 9. 자주 헷갈리는 포인트

### Checkpoint가 곧 Commit은 아니다

어떤 트랜잭션의 커밋 여부는 보통 로그 기록과 연결되어 판단됩니다.  
Checkpoint는 개별 트랜잭션의 성공 여부를 결정하는 이벤트가 아니라, 복구 효율을 높이는 시스템 이벤트에 가깝습니다.

즉, `COMMIT`과 `Checkpoint`는 목적이 다릅니다.

### Checkpoint가 모든 변경을 즉시 디스크에 다 쓰는 것은 아니다

많은 시스템은 완전한 강제 쓰기 대신 복구 가능한 형태로 기준점만 관리합니다.  
따라서 Checkpoint 이후에도 여전히 Dirty Page가 남아 있을 수 있습니다.

### Crash Recovery는 백업 복구와 다르다

`Crash Recovery`는 보통 인스턴스 장애나 비정상 종료 뒤에 로그를 이용해 최근 상태를 복구하는 과정입니다.  
반면 저장 장치 손상이나 파일 유실처럼 데이터 파일 자체가 사라진 경우에는 백업 복구나 미디어 복구가 필요할 수 있습니다.

즉, `Crash Recovery`는 "파일은 남아 있지만 메모리 상태가 사라진 상황"에 대한 복구에 가깝습니다.

## 10. Checkpoint가 너무 잦거나 너무 드물면

Checkpoint도 무조건 자주 하면 좋은 것은 아닙니다.

### 너무 잦은 경우

- 디스크 쓰기 부담이 커질 수 있습니다
- 백그라운드 I/O 부하가 높아질 수 있습니다
- 정상 처리 성능에 영향을 줄 수 있습니다

### 너무 드문 경우

- Dirty Page가 많이 쌓일 수 있습니다
- 장애 시 복구해야 할 로그 범위가 길어질 수 있습니다
- 재시작 시간이 길어질 수 있습니다

즉, Checkpoint는 성능과 복구 시간 사이의 균형 문제이기도 합니다.

## 트랜잭션 흐름으로 보면

하나의 변경 작업이 일어날 때 전체 흐름은 다음처럼 볼 수 있습니다.

### 1. 사용자가 데이터를 변경한다

변경은 먼저 메모리 버퍼에 반영됩니다.

### 2. 변경 사실이 Redo Log에 기록된다

복구 가능성을 보장하기 위해 로그가 먼저 안전하게 남습니다.

### 3. 커밋이 완료된다

사용자는 변경이 성공했다고 인식하지만, 실제 데이터 파일에는 아직 전부 반영되지 않았을 수 있습니다.

### 4. Checkpoint가 주기적으로 복구 기준점을 정리한다

Dirty Page 일부가 데이터 파일에 반영되고, 복구 기준 정보가 기록됩니다.

### 5. 장애가 발생하면 Crash Recovery가 수행된다

재시작 시 Checkpoint 이후의 필요한 로그를 읽어 Redo와 Undo를 수행합니다.

즉, 정상 운영 중의 지연 쓰기와 장애 후의 자동 복구는 하나의 구조로 이어져 있습니다.

## 한눈에 비교

| 항목 | Checkpoint | Crash Recovery |
| --- | --- | --- |
| 의미 | 복구 기준점 관리 이벤트 | 비정상 종료 후 자동 복구 과정 |
| 주 목적 | 복구 시간 단축 | 데이터 일관성 회복 |
| 핵심 수단 | Dirty Page 반영, 기준점 기록 | Redo, Undo, 로그 재생 |
| 언제 중요해지는가 | 정상 운영 중 | 재시작 시 |
| 없으면 생기는 문제 | 복구 범위 확대, 재시작 지연 | 장애 후 데이터 불일치 지속 |

## 정리

- `Checkpoint`는 복구 기준점을 남기고 복구 범위를 줄여 재시작 시간을 단축하는 메커니즘입니다.
- `Crash Recovery`는 비정상 종료 후 로그를 이용해 데이터베이스를 일관된 상태로 되돌리는 과정입니다.
- 데이터는 항상 즉시 파일에 기록되지 않기 때문에, 커밋 후에도 일부 변경은 메모리에만 있을 수 있습니다.
- 이때 `Redo`는 반영되어야 할 커밋 내용을 다시 적용하고, `Undo`는 미완료 트랜잭션을 정리합니다.
- `Checkpoint`와 `Crash Recovery`는 별개 개념이 아니라, 성능과 복구 가능성을 함께 만족시키기 위한 하나의 구조입니다.
