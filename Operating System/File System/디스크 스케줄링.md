# 디스크 스케줄링

## 개요

파일 시스템이 "어떤 블록에 데이터를 둘 것인가"를 결정한다면, 그 아래 계층에는 또 하나의 문제가 남아 있습니다.  
여러 프로세스가 동시에 디스크 I/O를 요청할 때, **그 요청들을 어떤 순서로 처리할 것인가**입니다.

HDD는 물리적으로 회전하는 플래터 위에서 헤드를 움직여 데이터를 읽습니다.  
헤드를 움직이는 시간(탐색 시간)이 전체 I/O 시간의 대부분을 차지하기 때문에, **요청 처리 순서를 바꾸는 것만으로도 성능이 크게 달라집니다.**

이 순서를 결정하는 정책이 `디스크 스케줄링`입니다.  
CPU 스케줄링이 "CPU를 누구에게 줄 것인가"를 다룬다면, 디스크 스케줄링은 "디스크 헤드를 어디로 먼저 보낼 것인가"를 다룹니다.

## 1. 디스크 접근 시간의 구성

HDD에서 하나의 요청을 처리하는 시간은 세 부분으로 나뉩니다.

| 구성 요소 | 설명 | 대략적인 크기 |
| --- | --- | --- |
| `탐색 시간(Seek Time)` | 헤드를 목표 트랙(실린더)까지 이동시키는 시간 | 수 ms (가장 큼) |
| `회전 지연(Rotational Latency)` | 목표 섹터가 헤드 아래로 회전해 올 때까지 기다리는 시간 | 수 ms |
| `전송 시간(Transfer Time)` | 실제 데이터를 읽고 쓰는 시간 | 1ms 미만 |

핵심은 **탐색 시간이 지배적**이라는 점입니다.  
따라서 디스크 스케줄링 알고리즘의 목표는 대부분 **헤드의 총 이동 거리를 최소화**하는 것입니다.

## 2. 디스크 스케줄링 알고리즘

아래 예시는 모두 다음 상황을 기준으로 설명합니다.

```
트랙 범위: 0 ~ 199
현재 헤드 위치: 53
대기 큐: 98, 183, 37, 122, 14, 124, 65, 67
```

### FCFS (First-Come First-Served)

요청이 **도착한 순서대로** 처리하는 방식입니다.

```
53 → 98 → 183 → 37 → 122 → 14 → 124 → 65 → 67   (총 이동: 640 트랙)
```

- 장점: 구현이 단순하고, 모든 요청이 언젠가는 반드시 처리되므로 공정합니다.
- 단점: 요청 위치를 전혀 고려하지 않아 헤드가 디스크 양 끝을 오가며 낭비가 큽니다.

### SSTF (Shortest Seek Time First)

현재 헤드 위치에서 **가장 가까운 요청부터** 처리하는 방식입니다.

```
53 → 65 → 67 → 37 → 14 → 98 → 122 → 124 → 183   (총 이동: 236 트랙)
```

- 장점: 평균 탐색 시간이 FCFS보다 크게 줄어듭니다.
- 단점: 헤드 근처에 요청이 계속 도착하면 멀리 있는 요청이 무한정 밀리는 `기아(Starvation)` 현상이 발생할 수 있습니다.

CPU 스케줄링의 SJF가 짧은 작업을 우대하다 긴 작업을 굶기는 것과 같은 구조의 문제입니다.

### SCAN (엘리베이터 알고리즘)

헤드가 **한쪽 방향으로 끝까지 이동하며** 경로상의 요청을 모두 처리하고, 끝에 도달하면 방향을 바꿔 되돌아오는 방식입니다.  
엘리베이터가 위로 가면서 손님을 태우고, 꼭대기에서 방향을 바꾸는 것과 같아 `엘리베이터 알고리즘`이라고도 부릅니다.

```
(헤드가 0 방향으로 이동 중이라고 가정)
53 → 37 → 14 → 0 → 65 → 67 → 98 → 122 → 124 → 183   (총 이동: 236 트랙)
```

- 장점: 기아 현상이 없고, 헤드 이동이 규칙적이라 성능이 안정적입니다.
- 단점: 방금 헤드가 지나간 직후의 위치에 도착한 요청은 헤드가 반대편 끝까지 갔다가 돌아올 때까지 기다려야 합니다. 즉, 위치에 따라 대기 시간 편차가 있습니다.

### C-SCAN (Circular SCAN)

SCAN의 변형으로, 헤드가 한쪽 끝에 도달하면 **요청을 처리하지 않고 반대쪽 끝으로 즉시 복귀**한 뒤 다시 같은 방향으로 스캔합니다.

```
(헤드가 199 방향으로 이동 중이라고 가정)
53 → 65 → 67 → 98 → 122 → 124 → 183 → 199 → (복귀) 0 → 14 → 37
```

- 장점: 항상 같은 방향으로만 처리하므로, 트랙 위치에 관계없이 **대기 시간이 균등**해집니다.
- 단점: 복귀 이동 자체는 아무 요청도 처리하지 않는 낭비 구간입니다.

### LOOK / C-LOOK

SCAN과 C-SCAN은 요청이 없어도 디스크 끝까지 이동합니다.  
`LOOK`과 `C-LOOK`은 **가장 멀리 있는 요청까지만 이동**하고 방향을 바꾸는 현실적인 개선안입니다.

```
(C-LOOK, 헤드가 199 방향으로 이동 중)
53 → 65 → 67 → 98 → 122 → 124 → 183 → (복귀) 14 → 37
```

실제 운영체제에서 "SCAN을 쓴다"고 하면 대부분 이 LOOK 계열 구현을 의미합니다.

### 알고리즘 비교

| 알고리즘 | 총 이동 거리 | 기아 가능성 | 대기 시간 균등성 | 특징 |
| --- | --- | --- | --- | --- |
| FCFS | 큼 | 없음 | 낮음 | 단순, 공정 |
| SSTF | 작음 | 있음 | 낮음 | 평균 성능 우수 |
| SCAN | 작음 | 없음 | 중간 | 안정적, 엘리베이터 방식 |
| C-SCAN | 작음 | 없음 | 높음 | 균등한 응답 시간 |
| C-LOOK | 가장 작음 | 없음 | 높음 | 실용적 구현 |

## 3. 실제 운영체제의 I/O 스케줄러

교과서의 알고리즘은 헤드 이동 거리만 보지만, 실제 운영체제는 **프로세스 간 공정성, 요청 병합, 읽기/쓰기 우선순위**까지 함께 고려합니다.  
Linux의 대표적인 I/O 스케줄러는 다음과 같습니다.

- `mq-deadline`: 각 요청에 마감 시간(Deadline)을 부여해, 이동 거리 최적화를 하면서도 오래 기다린 요청을 우선 처리해 기아를 방지합니다. 특히 읽기 요청에 더 짧은 마감 시간을 줍니다. 프로세스는 읽기가 끝나야 다음 작업을 진행하는 경우가 많아, 읽기 지연이 쓰기 지연보다 체감 성능에 크게 영향을 주기 때문입니다.
- `BFQ(Budget Fair Queueing)`: 프로세스마다 I/O 예산을 배분해 공정성을 보장합니다. 데스크톱처럼 반응성이 중요한 환경에 적합합니다.
- `none`: 스케줄링을 거의 하지 않고 요청을 그대로 전달합니다. NVMe SSD처럼 장치가 충분히 빠른 경우에 사용합니다.

또한 실제 스케줄러는 인접한 블록에 대한 요청들을 **하나의 큰 요청으로 병합(Merge)**해 I/O 횟수 자체를 줄입니다.

## 4. SSD에서는 어떻게 달라지는가

디스크 스케줄링 알고리즘의 전제는 "헤드 이동이 비싸다"는 것입니다.  
그런데 `SSD`는 기계적으로 움직이는 부품이 없어 **탐색 시간과 회전 지연이 존재하지 않습니다.**

따라서 SSD에서는 상황이 달라집니다.

- 어느 위치를 먼저 읽든 접근 시간이 거의 동일하므로, **헤드 이동 최소화 목적의 스케줄링은 의미가 없습니다.**
- 오히려 복잡한 스케줄링 연산 자체가 오버헤드가 되어, NVMe SSD에서는 `none` 스케줄러가 흔히 사용됩니다.
- 대신 SSD 내부 컨트롤러가 `웨어 레벨링(Wear Leveling)`, `가비지 컬렉션` 같은 자체 최적화를 수행하므로, 최적화의 주체가 OS에서 장치 쪽으로 이동했다고 볼 수 있습니다.

다만 SSD에서도 요청 병합이나 프로세스 간 공정성 보장은 여전히 유효하기 때문에, I/O 스케줄러가 완전히 사라진 것은 아닙니다.

## 정리

- `디스크 스케줄링`은 여러 디스크 I/O 요청의 처리 순서를 결정하는 정책이며, HDD에서는 `탐색 시간` 최소화가 핵심 목표입니다.
- `FCFS`는 공정하지만 비효율적이고, `SSTF`는 평균 성능이 좋지만 기아 현상이 발생할 수 있습니다.
- `SCAN`은 엘리베이터처럼 한 방향으로 스캔해 기아 없이 안정적인 성능을 내고, `C-SCAN`은 한 방향으로만 처리해 대기 시간을 균등하게 만듭니다.
- `LOOK`/`C-LOOK`은 요청이 있는 곳까지만 이동하는 실용적 개선안으로, 실제 구현은 대부분 이 방식입니다.
- 실제 Linux는 `mq-deadline`, `BFQ` 같은 스케줄러로 이동 거리 외에 기아 방지, 공정성, 요청 병합까지 처리합니다.
- `SSD`는 탐색 시간이 없어 이동 거리 기반 스케줄링이 무의미해졌고, 최적화의 중심이 장치 내부 컨트롤러로 이동했습니다.

결국 디스크 스케줄링의 핵심은 **저장 장치의 물리적 특성에 맞춰 요청 순서를 재배열함으로써, 같은 하드웨어에서 더 많은 I/O를 처리하는 것**입니다.  
장치가 HDD에서 SSD로 바뀌며 구체적인 알고리즘은 달라졌지만, "장치 특성을 이해하고 그에 맞게 요청을 다룬다"는 원칙은 그대로 유지되고 있습니다.
