# Lost Update

## 개요

`Lost Update`는 둘 이상의 트랜잭션이 같은 데이터를 기준으로 각각 계산한 뒤, 나중에 커밋한 변경이 먼저 커밋한 변경을 덮어써 버리는 현상입니다.  
핵심은 단순한 동시 조회가 아니라 `같은 원본 값`을 기반으로 한 `write-write 충돌`이라는 점입니다.

이 현상은 재고 차감, 계좌 잔액, 포인트, 좋아요 수, 조회수처럼 "현재 값에서 얼마를 더하거나 빼는" 업무에서 특히 치명적입니다.  
겉으로는 두 요청 모두 성공한 것처럼 보이지만, 실제로는 한쪽 변경이 사라져 데이터 정합성이 깨집니다.

## Lost Update란 무엇인가

예를 들어 계좌 잔액이 `100`이고, 두 세션이 동시에 출금을 수행한다고 가정해 보겠습니다.

- 세션 A는 잔액 `100`을 읽고 `30`을 출금해 `70`을 계산합니다.
- 세션 B도 잔액 `100`을 읽고 `50`을 출금해 `50`을 계산합니다.
- 세션 A가 먼저 `70`으로 반영하고 커밋합니다.
- 세션 B가 나중에 `50`으로 반영하고 커밋합니다.

최종 결과는 `20`이어야 하지만 실제 값은 `50`이 됩니다.  
세션 A의 변경 결과가 세션 B의 마지막 쓰기에 의해 사라졌기 때문에 이를 `Lost Update`라고 부릅니다.

## 1. 어떻게 발생하는가

`Lost Update`는 보통 다음 순서로 생깁니다.

1. 두 트랜잭션이 같은 행의 현재 값을 읽는다.
2. 각 트랜잭션이 애플리케이션 메모리 안에서 새 값을 계산한다.
3. 먼저 끝난 트랜잭션이 값을 기록한다.
4. 나중에 끝난 트랜잭션이 오래된 읽기 결과를 기준으로 다시 기록한다.
5. 먼저 반영된 변경이 최종 상태에서 사라진다.

한눈에 보면 다음과 같습니다.

| 시점 | 세션 A | 세션 B | 실제 DB 값 |
| --- | --- | --- | --- |
| 1 | 잔액 `100` 조회 |  | `100` |
| 2 |  | 잔액 `100` 조회 | `100` |
| 3 | `70` 계산 |  | `100` |
| 4 |  | `50` 계산 | `100` |
| 5 | `70`으로 갱신 후 커밋 |  | `70` |
| 6 |  | `50`으로 갱신 후 커밋 | `50` |

문제의 본질은 "같은 값을 두 번 읽었다"가 아니라, `오래된 읽기 결과를 기준으로 나중에 전체 값을 다시 써 버린다`는 데 있습니다.

## 2. 왜 기본 Row Lock만으로 충분하지 않을 수 있을까

많이 헷갈리는 지점은 DBMS가 같은 행에 대한 동시 `UPDATE`를 직렬화하는데도 왜 `Lost Update`가 생기느냐는 것입니다.

이유는 DBMS가 막아 주는 것은 보통 `동시에 같은 행을 쓰는 물리적 충돌`이지, 애플리케이션이 `언제 읽은 값으로 계산했는지`까지 자동으로 판단해 주는 것은 아니기 때문입니다.

예를 들어 두 세션이 모두 먼저 `100`을 읽고, 이후 각각 `UPDATE account SET balance = 70`과 `UPDATE account SET balance = 50`을 실행한다고 가정해 보겠습니다.

- 두 번째 `UPDATE`는 잠시 대기할 수 있습니다.
- 하지만 첫 번째 트랜잭션이 커밋된 뒤에도 두 번째 쿼리는 여전히 자기 계산 결과인 `50`을 그대로 기록합니다.
- 즉, 쓰기 자체는 순서대로 처리되지만 계산의 기준이 오래되었기 때문에 `Lost Update`는 여전히 발생할 수 있습니다.

그래서 `쓰기 시점의 잠금`만으로는 부족할 수 있고, `읽는 시점부터 충돌을 관리하는 방식` 또는 `현재 값을 기준으로 원자적으로 갱신하는 방식`이 필요합니다.

## 3. 다른 이상 현상과의 차이

`Lost Update`는 종종 `Non-Repeatable Read`와 함께 언급되지만 성격이 다릅니다.

| 항목 | Lost Update | Non-Repeatable Read | Dirty Read |
| --- | --- | --- | --- |
| 핵심 문제 | 한쪽 변경이 다른 쪽 쓰기에 의해 사라짐 | 같은 트랜잭션 안에서 조회 결과가 달라짐 | 커밋되지 않은 값을 읽음 |
| 중심 충돌 | `write-write` | `read-write` | `read-write` |
| 대표 증상 | 재고, 잔액, 카운터 값이 틀어짐 | 같은 쿼리 결과가 다시 읽을 때 바뀜 | 롤백될 수도 있는 값을 기준으로 작업 |
| 주된 대응 | Lock, version check, atomic update | 더 높은 격리 수준, 스냅샷 읽기 | `Read Committed` 이상 |

즉, `Lost Update`는 읽기 일관성 문제라기보다 `동시에 수정하는 작업이 서로의 결과를 덮어쓰는 문제`에 더 가깝습니다.

## 4. Lost Update를 막는 대표적인 방법

### 비관적 락

가장 전통적인 방법은 읽는 시점부터 해당 행을 잠가 다른 수정 작업이 끼어들지 못하게 하는 것입니다.  
대표적으로 `SELECT ... FOR UPDATE` 같은 방식이 여기에 해당합니다.

이 방식은 충돌이 잦고 같은 데이터를 자주 갱신하는 환경에서 단순하고 확실합니다.

- 장점: 충돌을 사전에 막기 쉽습니다.
- 단점: 대기 시간이 늘고, 잘못 설계하면 Deadlock 가능성도 커집니다.

### 원자적 UPDATE

가능하다면 값을 먼저 읽어 애플리케이션에서 계산한 뒤 다시 쓰기보다, DB가 현재 값을 기준으로 한 번에 계산하도록 만드는 것이 좋습니다.

예를 들어 다음 두 방식은 차이가 큽니다.

- 위험한 패턴: `잔액 조회 -> 애플리케이션에서 계산 -> UPDATE balance = 계산값`
- 더 안전한 패턴: `UPDATE account SET balance = balance - 30 WHERE id = 1`

후자의 경우 DB가 최신 값을 기준으로 연산하므로, 단순한 증감 연산에서는 `Lost Update` 가능성을 크게 줄일 수 있습니다.

다만 "현재 값이 얼마 이상일 때만 차감"처럼 조건이 복잡하다면, 영향받은 행 수 확인이나 추가 잠금이 함께 필요할 수 있습니다.

### 낙관적 락

충돌이 드물고 요청 간 연결이 길게 끊기는 웹 환경에서는 `version` 컬럼을 두고 갱신 시점에 버전을 검사하는 방식이 많이 쓰입니다.

동작 방식은 단순합니다.

- 조회할 때 현재 `version`도 함께 읽는다
- 갱신할 때 `WHERE id = ? AND version = ?` 조건으로 수정한다
- 수정 성공 시 `version`을 증가시킨다
- 수정된 행 수가 `0`이면 누군가 먼저 바꿨다고 보고 재조회 또는 재시도한다

이 방식은 사용자가 수정 화면을 오래 띄워 두는 업무 시스템에서 특히 유용합니다.

- 장점: 락을 오래 잡지 않아도 됩니다.
- 단점: 충돌 시 재시도나 사용자 충돌 처리 로직이 필요합니다.

### 더 높은 격리 수준

가장 강하게 막으려면 `Serializable` 같은 높은 격리 수준을 사용할 수 있습니다.  
이 경우 DBMS는 직렬 실행과 충돌하는 패턴을 대기시키거나 실패시켜 `Lost Update`를 방지합니다.

하지만 모든 작업에 이를 기본 적용하는 것은 현실적으로 부담이 큽니다.

- 잠금 경합과 대기가 증가할 수 있습니다.
- 재시도 비용이 커질 수 있습니다.
- 조회가 많은 서비스에서는 처리량이 크게 떨어질 수 있습니다.

그래서 실무에서는 높은 격리 수준을 전역 기본값으로 올리기보다, 필요한 구간만 별도로 강화하는 경우가 많습니다.

## 5. MVCC가 있다고 자동으로 해결되는 것은 아니다

`MVCC`는 읽기와 쓰기가 서로 오래 막지 않도록 도와주지만, `Lost Update`를 자동으로 해결하는 장치는 아닙니다.

이유는 간단합니다.

- `MVCC`는 주로 `일관된 읽기`를 제공하는 데 강합니다.
- `Lost Update`는 `같은 데이터를 두 트랜잭션이 각각 수정하려는 쓰기 충돌`입니다.
- 두 번째 갱신이 오래된 읽기 결과를 기반으로 만들어졌다면, 스냅샷 읽기만으로는 문제를 막지 못할 수 있습니다.

즉, `MVCC`가 있어도 `Lost Update`를 막으려면 여전히 `Lock`, `version check`, `atomic update` 같은 장치가 필요합니다.

## 6. 실무에서 자주 쓰는 선택 기준

어떤 방법이 맞는지는 업무 특성에 따라 달라집니다.

- 재고, 잔액, 포인트처럼 충돌 비용이 큰 값:
  `원자적 UPDATE` 또는 `비관적 락`을 우선 고려하는 편이 안전합니다.
- 게시글 편집, 관리자 화면처럼 사용자가 값을 오래 보고 수정할 수 있는 화면:
  `낙관적 락(version)`이 현실적입니다.
- 경쟁이 매우 심하고 정합성이 최우선인 구간:
  일부 트랜잭션에 한해 더 높은 격리 수준이나 강한 잠금을 적용할 수 있습니다.

중요한 것은 `SELECT`로 읽은 값을 애플리케이션에서 계산한 뒤 그대로 `UPDATE`하는 패턴을 무심코 쓰지 않는 것입니다.  
이 패턴이 `Lost Update`의 가장 전형적인 출발점입니다.

## 정리

- `Lost Update`는 여러 트랜잭션이 같은 값을 기준으로 계산한 뒤, 마지막 쓰기가 먼저 쓰인 결과를 덮어써 버리는 현상입니다.
- 핵심 원인은 `오래된 읽기 결과를 기준으로 한 write-write 충돌`입니다.
- 기본 잠금이나 `MVCC`만으로 항상 막히는 것은 아니며, `비관적 락`, `원자적 UPDATE`, `낙관적 락`, `높은 격리 수준` 같은 대응이 필요합니다.
- 실무에서는 업무 특성에 맞게 전략을 고르되, 특히 `조회 후 계산 후 전체 갱신` 패턴을 경계하는 것이 중요합니다.
