# 물리적 저장 구조와 세그먼트 관리 메커니즘

## 개요

풀 테이블 스캔을 단순히 "테이블 전체를 읽는 방식"이라고만 이해하면 실제 동작을 놓치기 쉽습니다.  
데이터베이스는 테이블을 막연한 논리 객체로 다루지 않고, **세그먼트**, **익스텐트**, **데이터 블록**, **하이 워터 마크(HWM)** 같은 물리적 구조를 기준으로 관리합니다.

즉, 풀 테이블 스캔은 "데이터 파일 전체를 읽는 동작"이 아니라, **해당 테이블 세그먼트가 점유한 공간을 HWM까지 따라 읽는 동작**에 가깝습니다.  
이 구조를 이해하면 왜 풀 테이블 스캔이 생각보다 효율적일 수 있는지, 또 왜 삭제 후에도 스캔 비용이 바로 줄지 않는지를 함께 이해할 수 있습니다.

## 1. 테이블은 하나의 세그먼트입니다

데이터베이스에서 **세그먼트(segment)** 는 실제 물리 저장 공간을 차지하는 독립 관리 단위입니다.  
일반적인 테이블을 하나 생성하면, 데이터베이스는 이를 하나의 **테이블 세그먼트**로 관리합니다.

중요한 점은 테이블이라는 논리 객체와 세그먼트라는 물리 객체가 연결되어 있다는 것입니다.  
사용자는 `고객` 테이블을 보지만, 데이터베이스는 그 테이블이 어느 저장 공간을 얼마나 점유하고 있는지를 세그먼트 단위로 추적합니다.

또한 세그먼트는 테이블에만 존재하는 것이 아닙니다.

- 테이블은 테이블 세그먼트를 가집니다.
- 인덱스는 인덱스 세그먼트를 가집니다.
- 파티션 환경에서는 파티션별로 별도 세그먼트가 존재할 수 있습니다.

즉, 세그먼트는 "객체가 실제로 디스크 공간을 쓰는 방식"을 설명하는 핵심 개념입니다.

## 2. 익스텐트는 연속된 블록의 묶음입니다

세그먼트는 여러 개의 **익스텐트(extent)** 로 구성됩니다.  
익스텐트는 물리적으로 인접한 데이터 블록들의 집합입니다.

데이터베이스는 테이블에 행이 추가될 때마다 블록을 한 개씩 따로 할당하지 않습니다.  
대신 일정 수의 블록을 묶은 익스텐트 단위로 공간을 할당합니다.

이렇게 하는 이유는 다음과 같습니다.

- 공간 할당과 관리 오버헤드를 줄일 수 있습니다.
- 연속된 블록을 한 번에 다루기 쉬워집니다.
- 세그먼트가 커질 때 확장 단위를 일관되게 유지할 수 있습니다.

즉, 세그먼트가 커진다는 것은 보통 "새 블록을 한 개 얻는다"가 아니라, **새 익스텐트를 추가로 할당받는다**는 뜻입니다.

## 3. 데이터 딕셔너리는 공간의 지도 역할을 합니다

데이터베이스 내부에는 객체의 물리적 배치를 설명하는 메타데이터가 저장되어 있습니다.  
이 메타데이터 저장소를 일반적으로 **데이터 딕셔너리(data dictionary)** 라고 부릅니다.

여기에는 특정 세그먼트가 현재 어떤 데이터 파일의 어느 구간을 사용 중인지에 대한 정보가 기록됩니다.  
즉, 어떤 테이블이 어떤 익스텐트 목록을 소유하고 있는지에 대한 "공간의 지도"가 유지되는 것입니다.

예를 들어 `고객` 테이블에 대해 풀 테이블 스캔이 시작되면, 서버 프로세스는 먼저 이 메타데이터를 바탕으로 다음을 파악합니다.

- 해당 테이블 세그먼트가 존재하는지
- 어떤 익스텐트들을 소유하고 있는지
- 각 익스텐트가 어느 데이터 파일의 어느 블록 구간에 위치하는지

그다음 이 익스텐트 목록을 따라가며 실제 블록을 읽습니다.  
즉, 풀 테이블 스캔은 데이터 파일 전체를 무작정 읽는 것이 아니라, **그 테이블 세그먼트에 속한 익스텐트들만 찾아가서 읽는 방식**입니다.

## 4. 하이 워터 마크는 스캔의 경계선입니다

세그먼트에 익스텐트가 할당되었다고 해서 그 안의 모든 블록이 항상 실제 데이터로 꽉 차 있는 것은 아닙니다.  
그래서 데이터베이스는 각 세그먼트마다 **하이 워터 마크(HWM, High Water Mark)** 를 관리합니다.

HWM은 일반적으로 **해당 세그먼트에서 한 번이라도 사용된 적이 있는 블록의 상한선**으로 이해할 수 있습니다.  
풀 테이블 스캔은 이 경계선을 기준으로 어디까지 읽을지 결정합니다.

즉, 세그먼트에 공간이 더 할당되어 있더라도 HWM을 넘는 영역까지는 읽지 않습니다.  
아직 한 번도 사용되지 않은 블록은 스캔 대상이 아니기 때문입니다.

다만 여기서 한 가지를 엄밀하게 구분해야 합니다.

- **HWM 위쪽 블록**: 아직 사용되지 않았으므로 읽지 않습니다.
- **HWM 아래쪽 블록**: 현재 비어 있더라도 스캔 대상에 포함될 수 있습니다.

예를 들어 과거에 데이터가 들어갔다가 삭제된 블록은 지금은 비어 있어도, 한 번 사용된 적이 있다면 HWM 아래에 남아 있을 수 있습니다.  
이 경우 풀 테이블 스캔은 그런 블록도 읽게 됩니다.

그래서 대량 삭제가 발생했다고 해서 풀 테이블 스캔 비용이 즉시 줄어들지는 않습니다.  
세그먼트 재구성이나 공간 축소 작업이 없는 한, HWM 자체는 그대로 남아 있을 수 있기 때문입니다.

## 5. 풀 테이블 스캔은 실제로 어떻게 진행될까?

풀 테이블 스캔의 동작을 순서대로 정리하면 다음과 같습니다.

1. 서버 프로세스가 데이터 딕셔너리와 세그먼트 메타데이터를 통해 해당 테이블의 익스텐트 목록을 확인합니다.
2. 각 익스텐트가 위치한 데이터 파일과 블록 범위를 파악합니다.
3. 익스텐트들을 따라가며 블록을 순차적으로 읽습니다.
4. 읽기 범위는 HWM까지로 제한됩니다.
5. 읽어 온 블록에서 실제 조건에 맞는 행만 필터링합니다.

이 과정의 핵심은, 풀 테이블 스캔이 논리적으로는 "테이블 전체 조회"이지만 물리적으로는 **세그먼트의 사용 구간을 순차적으로 스캔하는 작업**이라는 점입니다.

## 정리

- 테이블은 물리적으로 하나의 세그먼트로 관리됩니다.
- 세그먼트는 여러 익스텐트로 구성되며, 익스텐트는 연속된 블록의 묶음입니다.
- 데이터 딕셔너리는 세그먼트가 어떤 익스텐트를 소유하는지 기록하는 공간의 지도 역할을 합니다.
- 풀 테이블 스캔은 이 익스텐트 목록을 따라가며 세그먼트의 블록을 읽습니다.
- 읽기 범위는 하이 워터 마크까지이며, HWM 위쪽의 미사용 블록은 읽지 않습니다.
- 다만 HWM 아래의 빈 블록은 읽을 수 있으므로, 삭제가 많아도 스캔 비용이 바로 줄어들지 않을 수 있습니다.

결국 풀 테이블 스캔의 실체는 "테이블 전체를 대충 다 읽는 방식"이 아니라, **세그먼트의 물리적 저장 구조를 따라 사용된 영역을 순차적으로 읽는 메커니즘**이라고 볼 수 있습니다.
